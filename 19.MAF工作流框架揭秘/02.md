# [MAF工作流框架揭秘-02]ExecutorBinding，还是Executor，你是否傻傻分不清楚？

我们已经习惯了将Workflow的功能节点称为`Executor`，这个说法其实是不太准确的。确切地说，Workflow的功能节点是一个`ExecutorBinding`对象，`ExecutorBinding`可以利用封装的`ExecutorFactory`来创建一个`Executor`实例，并利用后者执行具体的操作。接下来我们从`ExecutorBinding`作为切入点，看看执行的Worflow如何执行功能节点提供的操作。在这之前，我们得先来认识一些基础类型

## 1. 基础类型

在Workflow中，一个节点可以拥有多个上游节点，它会将上游节点的输出作为自身的输入。由于上游节点提供的输出类型可能不尽相同，由此决定了不同的处理逻辑，所以节点往往需要提供多个处理器。当Workflow执行到这个节点时，需要动态地根据输入的类型来选择合适的处理器，所以处理器的描述也需要包含**输入类型**。有人可能会说，类型难道不是直接通过Type对象来表达吗？当然是，但是我们还需要一套支持**序列化**的类型来描述输入输出相关的类型。

### 1.1 TypeId

`TypeId`本质上就是对`Type`的另一种描述方式，它包含了一个`Type`所属的程序集名称和类型名称。它提供了`IsMatch`方法来判断一个`Type`对象是否与这个`TypeId`匹配，`IsMatchPolymorphic`方法则进一步支持多态匹配，也就是说如果输入的`Type`是`TypeId`所描述的类型的子类或者实现了这个类型，那么也会被认为是匹配的。`TypeId`将`Type`代表的运行时类型转换成可移植类型（Portable Type）。

```csharp
public sealed class TypeId : IEquatable<TypeId>
{
    public string AssemblyName { get; }
    public string TypeName { get; }

    public TypeId(string assemblyName, string typeName);
    public TypeId(Type type);

    public bool IsMatch(Type type);
    public bool IsMatch<T>() => this.IsMatch(typeof(T));
    public bool IsMatchPolymorphic(Type type);
}
```

### 1.2 MessageTypeTranslator

`MessageTypeTranslator`提供了一组`Type`和`TypeId`之间的双向映射。当我们通过指定的一组`Type`对象构建一个`MessageTypeTranslator`对象时，后者会创建两个映射字典。实现的`GetDeclaredType`和`MapTypeId`方法分别利用这两个字典来实现`Type`和`TypeId`之间的转换。由于Workflow将节点的输出和输出视为消息，所以该类型以`MessageTypeTranslator`为名。

```csharp
internal sealed class MessageTypeTranslator
{
	public MessageTypeTranslator(ISet<Type> types);
	public TypeId? GetDeclaredType(Type messageType);
	public Type? MapTypeId(TypeId candidateTypeId);
}
```

### 1.3 PortableValue

`TypeId`通过**AssemblyName + TypeName**的方式来描述一个类型，所以它是一个**可移植的类型(Portable Type)**，而`PortableValue`可以视为此类型的一个实例。它包含了一个`TypeId`来描述这个值的类型，以及一个`object`类型的`Value`属性来存储这个值本身。`PortableValue`提供`IsType`和`Is<TValue>`方法来判断这个值是否为指定的类型，`AsType`和`As<TValue>`方法则用来进行类型转换。

```csharp
public sealed class PortableValue
{
	[JsonInclude]
	internal object Value { get; }
	public TypeId TypeId { get; }

	public PortableValue(object value);

	public TValue? As<TValue>();
	public object? AsType(Type targetType);

	public bool Is<TValue>();
	public bool Is<TValue>(out TValue? value);
	public bool IsType(Type targetType);
	public bool IsType(Type targetType, out object? value);
}
```

## 2. ExecutorBinding

如下所示的是`ExecutorBinding`这个类型的定义，可以看出这是一个抽象的`record class`。它实现了`IIdentified`接口，后者提供`Id`属性作为唯一标识。它同时实现了`IEquatable<IIdentified>`和`IEquatable<string>`接口，从提供的`Equals`方法的实现可以看出，两者都是基于**Id属性来判断是否相等**的，而且重写的`GetHashCode`方法也是基于`Id`属性来计算的。

```csharp
public abstract record class ExecutorBinding(
        string Id, 
        Func<string, ValueTask<Executor>>? FactoryAsync, 
        Type ExecutorType, 
        object? RawValue = null)
    : IIdentified,
      IEquatable<IIdentified>,
      IEquatable<string>
{
    public bool IsPlaceholder => this.FactoryAsync == null;
    public abstract bool IsSharedInstance { get; }
    public abstract bool SupportsConcurrentSharedExecution { get; }
    public abstract bool SupportsResetting { get; }

    public override string ToString() 
       => $"{this.Id}:{(this.IsPlaceholder ? ":<unbound>" : this.ExecutorType.Name)}";
    public virtual bool Equals(ExecutorBinding? other) 
        => other is not null && other.Id == this.Id;
    public bool Equals(IIdentified? other) =>
        other is not null && other.Id == this.Id;
    public bool Equals(string? other) =>
        other is not null && other == this.Id;
    public override int GetHashCode() => this.Id.GetHashCode();

    protected virtual ValueTask<bool> ResetCoreAsync() 
        => throw new InvalidOperationException("ExecutorBindings that support resetting must override ResetCoreAsync()");    
}
public interface IIdentified
{
	string Id { get; }
}
```

`ExecutorBinding`构造函数提供了四个属性成员：

- **Id**：唯一标识这个`ExecutorBinding`对象的字符串；
- **FactoryAsync**：一个可选的异步工厂方法，用于创建一个`Executor`实例，作为输入参数的字符串表示**SessionId**。如果这个属性为`null`，意味着这个`ExecutorBinding`是一个占位符（Placeholder），还没有绑定到具体的`Executor`实例；
- **ExecutorType**：这个`ExecutorBinding`所绑定的`Executor`实例的类型；
- **RawValue**：一个可选的原始值，可以用来存储与这个`ExecutorBinding`相关的任意数据。

`ExecutorBinding`还提供了三个抽象属性成员：

- **IsSharedInstance**：指示这个`ExecutorBinding`提供的`Executor`是否支持共享，这个属性决定了一个`ExecutorBinding`创建的`Executor`对象能否在多次调用中复用；
- **SupportsConcurrentSharedExecution**：在`IsSharedInstance`为`true`的前提下，这个属性进一步指示`ExecutorBinding`提供的`Executor`是否支持并发共享执行；
- **SupportsResetting**：指示这个`ExecutorBinding`提供的`Executor`是否支持状态重置。

### 2.1 Executor执行协议

`ExecutorBinding`利用其`FactoryAsync`工厂方法会创建一个`Executor`对象。MAF将针对`Executor`对象的执行抽象成一套协议，并由抽象类`Executor`的`ConfigureProtocol`方法来配置。如下面的代码片段所示，`ConfigureProtocol`方法接受一个`ProtocolBuilder`对象作为参数。顾名思义，`ProtocolBuilder`就是用来构建`Executor`执行协议的Builder。

```csharp
public abstract class Executor : IIdentified
{
    protected abstract ProtocolBuilder ConfigureProtocol(ProtocolBuilder protocolBuilder);
}
```

`Executor`执行协议通过如下这个名为`ExecutorProtocol`的内部类型来表示。

```csharp
internal sealed class ExecutorProtocol(MessageRouter router, ISet<Type> sendTypes, ISet<Type> yieldTypes)
{
	public MessageTypeTranslator SendTypeTranslator { get; }
	internal MessageRouter Router { get; }

	public bool CanHandle(Type type);
	public bool CanOutput(Type type);
	public ProtocolDescriptor Describe();
}
```

构建一个`ExecutorProtocol`对象需要提供如下三个对象：

- **MessageRouter**：通过选择合适的Handler来处理接收到的输入，进而在当前节点实现消息路由；
- **SendTypes**：当前节点生成的、发送给下游节点的消息类型集合；
- **YieldTypes**：当前节点生成的、反馈给调用者的消息类型集合（用户采用流式调用时实时得到的消息）。

`SendTypeTranslator`属性返回的`MessageTypeTranslator`通过`YieldTypes`返回的类型集合构建而成，用于提供相关类型在`Type`和`TypeId`之间的转换。在开始路由的时候，会调用`CanHandle`方法根据指定的输入类型来判断是否具有与之匹配的处理器。而另一个`CanOutput`方法则用来验证输出的类型是否在指定的`YieldTypes`集合中（采用多态匹配规则）。`Describe`方法将规则转换成`ProtocolDescriptor`描述对象：

```csharp
public class ProtocolDescriptor
{
	public IEnumerable<Type> Accepts { get; }
	public IEnumerable<Type> Yields { get; }
	public IEnumerable<Type> Sends { get; }
	public bool AcceptsAll { get; set; }
}
```

四个属性说明如下：

- **Accepts**：当前节点能够接受的输入类型集合；
- **Yields**：当前节点能够反馈给调用者的消息类型集合；
- **Sends**：当前节点能够发送给下游节点的消息类型集合；
- **AcceptsAll**：指示当前节点是否接受任意类型的输入，却决于是否定义了一个匹配所有类型的处理器；

`Executor`的`ConfigureProtocol`方法通过接受一个`ProtocolBuilder`对象来配置这个协议。`ProtocolBuilder`提供了一系列的方法来配置路由和输入输出相关的类型。

```csharp
public sealed class ProtocolBuilder
{	
	public RouteBuilder RouteBuilder { get; }

	public ProtocolBuilder SendsMessage<TMessage>() where TMessage : notnull;
	public ProtocolBuilder SendsMessageType(Type messageType);
	public ProtocolBuilder SendsMessageTypes(IEnumerable<Type> messageTypes);

	public ProtocolBuilder YieldsOutput<TOutput>() where TOutput : notnull;
	public ProtocolBuilder YieldsOutputType(Type outputType);
	public ProtocolBuilder YieldsOutputTypes(IEnumerable<Type> yieldedTypes);

	public ProtocolBuilder ConfigureRoutes(Action<RouteBuilder> configureAction);

    public ProtocolBuilder AddDelegateAttributeTypes(Delegate @delegate);
	public ProtocolBuilder AddMethodAttributeTypes(MethodInfo method);
	public ProtocolBuilder AddClassAttributeTypes(Type executorType);
}
```

几组方法说明如下：

- `SendsMessage<TMessage>`、`SendsMessageType`和`SendsMessageTypes`： 指定的类型会添加到`ExecutorProtocol`的`SendTypes`集合中，表示当前节点能够发送给下游节点的消息类型；
- `YieldsOutput<TOutput>`、`YieldsOutputType`和`YieldsOutputTypes`： 指定的类型会添加到`ExecutorProtocol`的`YieldTypes`集合中，表示当前节点能够反馈给调用者的消息类型；
- `ConfigureRoutes`： 接受一个`Action<RouteBuilder>`类型的参数，允许调用者通过这个`RouteBuilder`来配置消息路由规则；
- `AddDelegateAttributeTypes`、`AddMethodAttributeTypes`和`AddClassAttributeTypes`：当我们将作为处理器的委托、方法或者`Executor`类型作为参数调用这些方法时，它会解析上面标注的如下两个`Attribute`来添加相应的类型到`SendTypes`和`YieldTypes`集合中：

```csharp
[AttributeUsage(AttributeTargets.Class | AttributeTargets.Method, AllowMultiple = true, Inherited = true)]
public sealed class SendsMessageAttribute : Attribute
{
	public Type Type { get; }
	public SendsMessageAttribute(Type type)=> Type = type;
}

[AttributeUsage(AttributeTargets.Class | AttributeTargets.Method, AllowMultiple = true, Inherited = true)]
public sealed class YieldsOutputAttribute : Attribute
{
	public Type Type { get; }
	public YieldsOutputAttribute(Type type)=> Type = type;
}
```

### 2.2 消息路由

`ProtocolBuilder`提供了`ConfigureRoutes`方法来配置消息路由规则。此方法接受一个`Action<RouteBuilder>`类型的参数，允许调用者通过这个`RouteBuilder`来配置消息路由规则。我们先来看看作为路由处理器的委托是什么样子的。

#### 2.2.1 路由处理器委托

承载节点业务操作的路由处理器体现为具有如下签名的委托，它三个输入分别是：作为输入的消息对象、当前的工作流上下文以及接收取消通知的`CancellationToken`。它的输出是一个`CallResult`对象，表示处理器的执行结果。

```csharp
Func<object, IWorkflowContext, CancellationToken, ValueTask<CallResult>>

internal sealed class CallResult
{
	public bool IsVoid { get; init; }
	public object? Result { get; init; }
	public Exception? Exception { get; init; }
	public bool IsCancelled { get; init; }
	public bool IsSuccess => Exception == null && !IsCancelled;

	public static CallResult ReturnResult(object? result = null);
	public static CallResult ReturnVoid();
	public static CallResult Cancelled(bool wasVoid);
	public static CallResult RaisedException(bool wasVoid, Exception exception);
}
```

`CallResult`的属性说明如下：

- **IsVoid**：指示这个结果是否为`void`类型的结果；
- **Result**：处理器的返回结果对象，如果`IsVoid`为`true`，这个属性应该为`null`；
- **Exception**：处理器执行过程中抛出的异常对象，如果处理器执行成功，这个属性应该为`null`；
- **IsCancelled**：指示处理器的执行是否被取消；
- **IsSuccess**：指示处理器的执行是否成功。

`CallResult`还提供了四个静态方法来创建不同类型的结果对象：

- **ReturnResult**：创建一个包含结果对象的`CallResult`实例，`IsVoid`属性为`false`；
- **ReturnVoid**：创建一个表示`void`结果的`CallResult`实例，`IsVoid`属性为`true`；
- **Cancelled**：创建一个表示处理器执行被取消的`CallResult`实例，`IsCancelled`属性为`true`，`IsVoid`属性根据`wasVoid`参数设置；
- **RaisedException**：创建一个表示处理器执行过程中抛出异常的`CallResult`实例，`Exception`属性设置为传入的异常对象，`IsVoid`属性根据`wasVoid`参数设置；

#### 2.2.2 消息路由器

作为消息路由器的`MessageRouter`被定成如下这个内部类型。

```csharp
internal sealed class MessageRouter
{
	private record TypeHandlingInfo(Type RuntimeType, Func<object, IWorkflowContext, CancellationToken, ValueTask<CallResult>> Handler);

	private readonly Type[] _interfaceHandlers;
	private readonly ConcurrentDictionary<TypeId, TypeHandlingInfo> _typeInfos = new ConcurrentDictionary<TypeId, TypeHandlingInfo>();
	private readonly Func<PortableValue, IWorkflowContext, CancellationToken, ValueTask<CallResult>>? _catchAllFunc;

	public HashSet<Type> IncomingTypes { get; }
	internal bool HasCatchAll{ get; }
	public HashSet<Type> DefaultOutputTypes { get; }

	internal MessageRouter(
        Dictionary<Type, Func<object, IWorkflowContext, CancellationToken, ValueTask<CallResult>>> handlers, 
        HashSet<Type> outputTypes, 
        Func<PortableValue, IWorkflowContext, CancellationToken, ValueTask<CallResult>>? catchAllFunc);

	public bool CanHandle(object message);
	public bool CanHandle(Type candidateType);

	private Func<object, IWorkflowContext, CancellationToken, ValueTask<CallResult>>? FindHandler(Type messageType);

	public async ValueTask<CallResult?> RouteMessageAsync(
        object message, 
        IWorkflowContext context, 
        bool requireRoute = false, 
        CancellationToken cancellationToken = default);
}
```

调用构造函数来创建一个`MessageRouter`对象时，需要提供如下三个参数：

- **handlers**：一个字典对象，键是输入消息的类型，值是处理这个类型消息的处理器函数。该字典转换成一个`ConcurrentDictionary<TypeId, TypeHandlingInfo>`类型的`_typeInfos`字段来存储处理器信息，`TypeHandlingInfo`对象存储了输入消息的运行时类型和对应的处理器函数之间的映射关系。所有输入类型组成的`HashSet<Type>`会被赋值给`IncomingTypes`属性；
- **outputTypes**：一个类型集合，表示这个`MessageRouter`能够生成的输出消息类型。这个集合会被赋值给`DefaultOutputTypes`属性；
- **catchAllFunc**：一个可选的处理函数，当没有找到匹配的处理器时，会调用这个函数来处理消息。此委托对象会被赋值给`_catchAllFunc`字段。这个参数还会反映在`HasCatchAll`属性上。

消息路由最核心的操作就是根据输入消息的类型找到对应的处理器函数，这一操作实现在`FindHandler`方法中,具体逻辑如下：

- 首先根据输入消息的运行时类型来构造一个`TypeId`对象；
- 然后在`_typeInfos`字典中查找这个`TypeId`，如果找到了对应的`TypeHandlingInfo`对象，就返回其中的处理器函数；
- 如果没有找到，`_interfaceHandlers`数组中选择当前对象实现的接口，然后根据接口类型来构造`TypeId`对象并在`_typeInfos`字典中查找对应的处理器函数，如果找到了就返回；
- 如果还没有找到，将候选类型的基类作为新的候选类型继续上述查找过程，直到找到处理器函数或者没有更多的基类可供检查为止；

两个`CanHandle`方法用来确定这个`MessageRouter`是否能够处理指定类型的消息。如果`HasCatchAll`返回`true`或者`FindHandler`方法能够找到一个处理器函数，那么这个`MessageRouter`就能够处理这个类型的消息，此时`CanHandle`方法返回`true`，否则返回`false`。

消息路由的核心方法是`RouteMessageAsync`方法，它接受一个消息对象、一个工作流上下文对象、一个指示是否要求必须找到处理器的布尔值以及一个取消令牌作为参数。具体的路由逻辑如下：

- 如果作为输入参数的`message`是一个`PortableValue`对象，并且`_typeInfos`字典具有与之匹配的`TypeHandlingInfo`对象，则调用`AsType`方法将它转换成对应的CLR类型（`TypeHandlingInfo`的`Runtime`属性）；
- 根据输入消息类型调用`FindHandler`方法来查找对应的处理器函数，如果找到了就调用这个函数来处理消息，并返回处理结果；
- 如果没有找到处理器函数，并且`HasCatchAll`属性为`true`，就调用`_catchAllFunc`来处理这个消息，并返回处理结果；
- 如果`HasCatchAll`属性返回`false`，直接返回`null`表示没有找到处理器函数；
- 如果路由操作出现异常，则返回一个封装此异常的`CallResult`对象；

就目前的路由实现来说，`requireRoute`参数并没有被使用，但它的设计初衷是为了在某些场景下强制要求必须找到一个处理器函数来处理输入消息，如果没有找到就抛出异常或者返回一个特定的结果。不知道是刻意不用，还是说这是一个Bug。

#### 2.2.3 构建消息路由器

作为消息路由器的`MessageRouter`采用Builder模式来构建，对应的Builder类型为`RouteBuilder`。虽然作为处理器的委托类型具有固定的格式，但是为了编程上的便利，我们可以定义与之兼容的方法来处理请求，只需要内部将它们适配成符合要求的处理器函数即可。`RouteBuilder`提供了多种重载的`AddHandler`方法将具有不同签名的委托适配成符合要求的处理器函数并添加到路由规则中。适配生成的`Func<object,IWorkflowContext,CancellationToken,ValueTask<CallResult>>`委托将以输入类型作为键存储在`RouteBuilder`的`_typedHandlers`字段中。

```csharp
public class RouteBuilder
{
    private readonly Dictionary<Type, Func<object,IWorkflowContext,CancellationToken,ValueTask<CallResult>>> _typedHandlers = [];
    private readonly Dictionary<Type, Type> _outputTypes = [];
    private Func<PortableValue, IWorkflowContext, CancellationToken, ValueTask<CallResult>>? _catchAll;

	public RouteBuilder AddHandler<TInput>(
        Action<TInput, IWorkflowContext, CancellationToken> handler, 
        bool overwrite = false);
	public RouteBuilder AddHandler<TInput>(
        Action<TInput, IWorkflowContext> handler, 
        bool overwrite = false);
	public RouteBuilder AddHandler<TInput>(
        Func<TInput, IWorkflowContext, CancellationToken, ValueTask> handler, 
        bool overwrite = false);
	public RouteBuilder AddHandler<TInput>(
        Func<TInput, IWorkflowContext, ValueTask> handler, 
        bool overwrite = false);
	public RouteBuilder AddHandler<TInput, TResult>(
        Func<TInput, IWorkflowContext, CancellationToken, TResult> handler, 
        bool overwrite = false);
	public RouteBuilder AddHandler<TInput, TResult>(
        Func<TInput, IWorkflowContext, TResult> handler, 
        bool overwrite = false);
	public RouteBuilder AddHandler<TInput, TResult>(
        Func<TInput, IWorkflowContext, CancellationToken, ValueTask<TResult>> handler, 
        bool overwrite = false);
	public RouteBuilder AddHandler<TInput, TResult>(
        Func<TInput, IWorkflowContext, ValueTask<TResult>> handler, 
        bool overwrite = false);

    public RouteBuilder AddCatchAll(
        Func<PortableValue, IWorkflowContext, CancellationToken, ValueTask> handler, 
        bool overwrite = false);
	public RouteBuilder AddCatchAll(
        Func<PortableValue, IWorkflowContext, ValueTask> handler, 
        bool overwrite = false);
	public RouteBuilder AddCatchAll<TResult>(
        Func<PortableValue, IWorkflowContext, CancellationToken, ValueTask<TResult>> handler, 
        bool overwrite = false);
	public RouteBuilder AddCatchAll<TResult>(
        Func<PortableValue, IWorkflowContext, ValueTask<TResult>> handler, 
        bool overwrite = false);
	public RouteBuilder AddCatchAll(
        Action<PortableValue, IWorkflowContext, CancellationToken> handler, 
        bool overwrite = false);
	public RouteBuilder AddCatchAll(
        Action<PortableValue, IWorkflowContext> handler, 
        bool overwrite = false);
	public RouteBuilder AddCatchAll<TResult>(
        Func<PortableValue, IWorkflowContext, CancellationToken, TResult> handler, 
        bool overwrite = false);
	public RouteBuilder AddCatchAll<TResult>(
        Func<PortableValue, IWorkflowContext, TResult> handler, 
        bool overwrite = false);
    internal MessageRouter Build();
}
```

如果调用`AddHandler`方法指定的委托包含返回值，返回值类型将会作为输出类型收集起来存储在`RouteBuilder`的`_outputTypes`字段中。`AddCatchAll`方法则用来指定一个处理函数，当没有找到匹配的处理器时，会调用这个函数来处理消息。这个函数的输入参数是一个`PortableValue`对象，表示输入消息以及它的类型信息。这些方法会将输入的委托转换成`Func<PortableValue, IWorkflowContext, CancellationToken, ValueTask<CallResult>>`类型存在`_routeHandlers`字段中。`Build`方法将会使用这三个字段生成一个`MessageRouter`对象。

### 2.3 Executor的其他成员

到目前为止，我们只介绍了抽象类`Executor`的`ConfigureProtocol`方法，实际上它还提供了其他一些成员。

```csharp
public abstract class Executor : IIdentified
{	
    public string Id { get; }	
	protected ExecutorOptions Options { get; }
    internal bool IsCrossRunShareable { get; }

    internal ExecutorProtocol Protocol => field??=ConfigureProtocol(new ProtocolBuilder(DelayedPortRegistrations)).Build(Options);
    internal MessageRouter Router => Protocol.Router;	
	public ISet<Type> InputTypes => Router.IncomingTypes;
	public ISet<Type> OutputTypes => field ??= new HashSet<Type>(Protocol.Describe().Yields));

	protected Executor(string id, ExecutorOptions? options = null, bool declareCrossRunShareable = false)
	{
		Id = id;
		Options = options ?? ExecutorOptions.Default;
		IsCrossRunShareable = declareCrossRunShareable;
	}
	
    public ProtocolDescriptor DescribeProtocol()=>Protocol.Describe();
	public bool CanHandle(Type messageType)=>Protocol.CanHandle(messageType);
}

public class ExecutorOptions
{
	public static ExecutorOptions Default { get; } = new ExecutorOptions();
	public bool AutoSendMessageHandlerResultObject { get; set; } = true;
	public bool AutoYieldOutputHandlerResultObject { get; set; } = true;
	internal ExecutorOptions(){}
}
```

构造函数需要提供三个参数：

- **id**：唯一标识这个`Executor`对象的字符串；
- **options**：一个可选的`ExecutorOptions`对象，用于配置这个`Executor`对象的行为，如果不提供则使用默认配置。它提供了如下两个选项：
  - **AutoSendMessageHandlerResultObject**：一个布尔值，指示当处理器函数返回一个非`null`的结果对象时，是否自动将这个对象发送给下游节点；
  - **AutoYieldOutputHandlerResultObject**：一个布尔值，指示当处理器函数返回一个非`null`的结果对象时，是否自动将这个对象反馈给调用者；
- **declareCrossRunShareable**：一个布尔值，指示这个`Executor`对象是否可以在多次调用中被复用；

`Executor`内部属性`Protocol`通过`ConfigureProtocol`方法返回的`ProtocolBuilder`构建而成。表示消息路由器的`Router`属性以及表示输入和输出类型的`InputTypes`和`OutputTypes`属性均来源于此。用于创建`ProtocolDescriptor`描述对象和判断是否能够处理指定类型消息的`DescribeProtocol`和`CanHandle`方法也是基于`Protocol`对象来实现的。

`Executor`还提供了一个`InitializeAsync`方法，允许在执行协议之前进行一些异步的初始化操作。`Executor`核心执行逻辑实现在`ExecuteCoreAsync`方法中，后者会调用另一个重载的`ExecuteCoreAsync`方法。

```csharp
public abstract class Executor : IIdentified
{	    
	protected internal virtual ValueTask InitializeAsync(
        IWorkflowContext context, CancellationToken cancellationToken = default)
	    => default;

	public ValueTask<object?> ExecuteCoreAsync(
        object message, 
        TypeId messageType, 
        IWorkflowContext context, 
        CancellationToken cancellationToken = default)
        => ExecuteCoreAsync(message, messageType, context, WorkflowTelemetryContext.Disabled, cancellationToken);

	internal async ValueTask<object?> ExecuteCoreAsync(
        object message, 
        TypeId messageType, 
        IWorkflowContext context, 
        WorkflowTelemetryContext telemetryContext, 
        CancellationToken cancellationToken = default)
	{		
		var result = await Router.RouteMessageAsync(message, context, requireRoute: true, cancellationToken)
            .ConfigureAwait(continueOnCapturedContext: false);		
		
        if (result == null)
		{
			throw new NotSupportedException($"No handler found for message type {message.GetType().Name} in executor {GetType().Name}.");
		}
		if (!result.IsSuccess)
		{
			throw new TargetInvocationException($"Error invoking handler for {message.GetType()}", result.Exception);
		}
		if (result.IsVoid)
		{
			return null;
		}
		
		if (result.Result != null && Options.AutoSendMessageHandlerResultObject)
		{
			await context.SendMessageAsync(result.Result, cancellationToken).ConfigureAwait(continueOnCapturedContext: false);
		}
		if (result.Result != null && Options.AutoYieldOutputHandlerResultObject)
		{
			await context.YieldOutputAsync(result.Result, cancellationToken).ConfigureAwait(continueOnCapturedContext: false);
		}
		return result.Result;
	}
}
```

上面给出了`ExecuteCoreAsync`方法的核心核心代码（省去了基于Open Telemetry基于调用链跟踪的代码），具体的逻辑如下：

- 首先调用`Router`的`RouteMessageAsync`方法来路由输入消息并得到处理结果；
- 如果没有找到处理器函数来处理输入消息，`RouteMessageAsync`方法会返回`null`，此时抛出一个`NotSupportedException`异常；
- 如果处理器函数执行过程中抛出了异常，`RouteMessageAsync`方法会返回一个包含异常信息的`CallResult`对象，此时抛出一个`TargetInvocationException`异常；
- 如果处理器函数执行成功但没有返回结果（即`IsVoid`为`true`），直接返回`null`；
- 如果处理器函数执行成功并且返回了一个非`null`的结果对象
  - 如果`ExecutorOptions`的`AutoSendMessageHandlerResultObject`选项为`true`，就调用`IWorkflowContext`的`SendMessageAsync`方法将这个结果对象发送给下游节点；
  - 如果`ExecutorOptions`的`AutoYieldOutputHandlerResultObject`选项为`true`，就调用`IWorkflowContext`的`YieldOutputAsync`方法将这个结果对象反馈给调用者；
- 最后返回这个结果对象；

`Executor`还定义了四个虚方法，它们是`Executor`核心生命周期钩子（Hooks），允许开发者在消息批处理和状态持久化前后注入自定义逻辑。

```csharp
public abstract class Executor : IIdentified
{	    
	protected internal virtual ValueTask OnMessageDeliveryStartingAsync(
        IWorkflowContext context, 
        CancellationToken cancellationToken = default)
	    => default;
	protected internal virtual ValueTask OnMessageDeliveryFinishedAsync(
        IWorkflowContext context, 
        CancellationToken cancellationToken = default)
	    => default;
	protected internal virtual ValueTask OnCheckpointingAsync(
        IWorkflowContext context, 
        CancellationToken cancellationToken = default)
	    => default;
	protected internal virtual ValueTask OnCheckpointRestoredAsync(
        IWorkflowContext context, 
        CancellationToken cancellationToken = default)
	    => default;	
}
```

四个钩子方法的说明如下：

- **OnMessageDeliveryStartingAsync**：在开始处理输入消息之前调用，允许开发者在这里执行一些准备工作，比如记录日志、设置上下文数据等；
- **OnMessageDeliveryFinishedAsync**：在完成处理输入消息之后调用，允许开发者在这里执行一些清理工作，比如记录日志、清除上下文数据等；
- **OnCheckpointingAsync**：在执行状态持久化之前调用，允许开发者在这里执行一些操作，比如记录日志、修改状态数据等；
- **OnCheckpointRestoredAsync**：在状态恢复之后调用，允许开发者在这里执行一些操作，比如记录日志、重新初始化状态数据等。

## 3. 自定义Executor

如果我们要继承`Executor`来实现一个自定义的`Executor`，重写`ConfigureProtocol`方法来配置这个`Executor`的执行协议是必不可少的。但是针对这个方法的实现由两种形式，一种是我们通过代码自行定义，另一种就是通过Source Generator来自动生成。

### 3.1 手工重写ConfigureProtocol方法

我们可以采用如下的方式在自定义的`Executor`类型中重写`ConfigureProtocol`方法来配置这个`Executor`的执行协议。如下面的演示程序所示，我们定义了两个`Executor`类型，分别是`GreetyExecutor`和`OutputExecutor`。前者的`ConfigureProtocol`方法通过`RouteBuilder`添加了一个处理字符串类型输入的处理器，并且指定了这个处理器的输出类型也是字符串类型。后者的`ConfigureProtocol`方法则添加了一个处理字符串类型输入并且输出同样为字符串类型的处理器。我们将这两个`Executor`对象通过`WorkflowBuilder`连接成一个简单的`Workflow`，并且执行这个`Workflow`来验证它们的功能。

```csharp
var greety = new GreetyExecutor();
var output = new OutputExecutor();
var workflow = new WorkflowBuilder(greety)
    .AddEdge(source: greety, target: output)
    .WithOutputFrom(output)
    .Build();
var run = await InProcessExecution.Default.RunAsync(workflow, "World");
var result = run.NewEvents.OfType<WorkflowOutputEvent>().Single().Data!;
Debug.Assert(result.Equals("Hello, World!"));

internal class GreetyExecutor() : Executor(id: "Greety")
{
    protected override ProtocolBuilder ConfigureProtocol(ProtocolBuilder protocolBuilder)
    {
       return protocolBuilder.ConfigureRoutes(routeBuilder=>routeBuilder.AddHandler<string,string>(Handle));
       static string Handle(string message, IWorkflowContext context) => $"Hello, {message}!";
    }
}

internal class OutputExecutor() : Executor(id: "Output")
{
    protected override ProtocolBuilder ConfigureProtocol(ProtocolBuilder protocolBuilder)
    {
        return protocolBuilder.ConfigureRoutes(routeBuilder => routeBuilder.AddHandler<string, string>((input, _)=> input));
    }
}
```

通过上面分析`Executor`的`ExecuteCoreAsync`方法的实现，我们知道由于`ExecutorOptions`的`AutoSendMessageHandlerResultObject`和`AutoYieldOutputHandlerResultObject`选项默认都是`true`，所以当处理器函数返回一个非`null`的结果对象时，这个结果对象会被自动发送给下游节点并且反馈给调用者。所以`GreetyExecutor`注册的处理器函数的返回值会被自动发送给`OutputExecutor`来处理，并且最终被反馈给`Workflow`的调用者。我们也可以按照如下的方式在注册的`HandleAsync`方法中手动调用`IWorkflowContext`的`SendMessageAsync`方法来发送消息。

```csharp
internal class GreetyExecutor() : Executor(id: "Greety")
{
    protected override ProtocolBuilder ConfigureProtocol(ProtocolBuilder protocolBuilder)
    {
        protocolBuilder.SendsMessage<string>();
        return protocolBuilder.ConfigureRoutes(routeBuilder=>routeBuilder.AddHandler<string>(HandleAsync));
        static ValueTask HandleAsync(string message, IWorkflowContext context)
        { 
            return context.SendMessageAsync($"Hello, {message}!");
        }
    }
}
```

由于`Executor`的执行严格按照`ExecutorProtocol`来进行，输出对象的类型必须在`ExecutorProtocol`的描述中声明。由于现在我们注册的`HandleAsync`方法没有返回值，所以`ProtocolBuilder`不会自动将输出类型添加到`ExecutorProtocol`的描述中，因此我们需要通过调用`SendsMessage<string>`方法来显式地将这个输出类型添加到`ExecutorProtocol`的描述中。

### 3.2 通过Source Generator生成ConfigureProtocol方法

如果采用Source Generator的方式，我们执行按照如下的方式定义路由处理函数`Handle`，并在上面标注`MessageHandlerAttribute`就可以了。由于我们需要利用Source Generator来生成`ConfigureProtocol`方法，所以必需将`GreetyExecutor`定义成一个`partial`类型。

```csharp
internal partial class GreetyExecutor() : Executor(id: "Greety")
{
    [MessageHandler]
    string Handle(string name, IWorkflowContext context) => $"Hello, {name}!";
}
```

如下所示的就是Source Generator生成的代码，我们可以看到在生成的`ConfigureProtocol`方法，它的定义与上面我们手工重写的`ConfigureProtocol`方法完全一致。

```csharp
// <auto-generated/>
#nullable enable

using System;
using System.Collections.Generic;
using Microsoft.Agents.AI.Workflows;

using RouteBuilder = Microsoft.Agents.AI.Workflows.RouteBuilder;
partial class GreetyExecutor
{
    protected override ProtocolBuilder ConfigureProtocol(ProtocolBuilder protocolBuilder)
    {
        return protocolBuilder.ConfigureRoutes(ConfigureRoutes);
        void ConfigureRoutes(RouteBuilder routeBuilder)
        {
            routeBuilder
                .AddHandler<string, string>(this.Handle);
        }
    }
}
```

`MessageHandlerAttribute`类型定义如下，它是一个方法级别的Attribute，允许我们在方法上标注这个Attribute来指示Source Generator将这个方法作为一个路由处理函数来处理。如果`Send`和`Yield`数据类型与处理器函数的输入输出类型不一致，我们还可以通过`Send`和`Yield`属性来显式地指定发送和反馈的消息类型。

```csharp
[AttributeUsage(AttributeTargets.Method, AllowMultiple = false, Inherited = false)]
public sealed class MessageHandlerAttribute : Attribute
{
    public Type[]? Yield { get; set; }
    public Type[]? Send { get; set; }
}
```

如果将上面标注`MessageHandlerAttribute`的`Handle`方法改成如下所示的异步方法`HandleAsync`，并且手工调用`IWorkflowContext`的`SendMessageAsync`方法来发送消息，那么确实的`Send`类型就需要利用`MessageHandlerAttribute`的`Send`属性来显式声明。

```csharp
internal partial class GreetyExecutor() : Executor(id: "Greety")
{
    [MessageHandler(Send = [typeof(string)])]
    ValueTask HandleAsync(string name, IWorkflowContext context) 
        => context.SendMessageAsync($"Hello, {name}!");
}
```

### 3.3 定义多个路由处理函数

由于MessageRouter严格按照输入类型来路由消息，所以如果我们需要处理多种类型的输入消息，我们就需要定义多个路由处理函数。如下所示的就是一个定义了两个路由处理函数的`GreetyExecutor`，它们分别处理字符串类型和`NameTimePair`类型的输入消息。

```csharp
internal partial class GreetyExecutor() : Executor(id: "Greety")
{
    [MessageHandler(Send = [typeof(string)])]
    ValueTask HandleAsync(string name, IWorkflowContext context) 
        => context.SendMessageAsync($"Hello, {name}!");

    [MessageHandler(Send = [typeof(NameTimePair)])]
    ValueTask HandleAsync(NameTimePair nameAndTime, IWorkflowContext context)
    {
        var (name, time) = nameAndTime;
        return context.SendMessageAsync($"Good {time}, {name}!");
    }
}
```

在下面的演示程序中，我们构建了一个包含上面这个`GreetyExecutor`的`Workflow`，并且执行这个`Workflow`来验证它能够正确地处理两种不同类型的输入消息。从输出结果我们可以看到，当输入消息是字符串类型时，它会调用第一个处理器函数来处理这个消息；当输入消息是`NameTimePair`类型时，它会调用第二个处理器函数来处理这个消息。顺便说一下，Workflow对象的状态会在执行过程中被更新，所以两次调用不能复用同一个Workflow对象。

```csharp
using Microsoft.Agents.AI.Workflows;
using System.Diagnostics;

var greety = new GreetyExecutor();
var output = new OutputExecutor();
var workflow = new WorkflowBuilder(greety)
    .AddEdge(source: greety, target: output)
    .WithOutputFrom(output)
    .Build();
var run = await InProcessExecution.Default.RunAsync(workflow, "World");
var result = run.NewEvents.OfType<WorkflowOutputEvent>().Single().Data!;
Debug.Assert(result.Equals("Hello, World!"));

workflow = new WorkflowBuilder(greety)
    .AddEdge(source: greety, target: output)
    .WithOutputFrom(output)
    .Build();
run = await InProcessExecution.Default.RunAsync(workflow, new NameTimePair { Name = "Jayden", Time = "morning" });
result = run.NewEvents.OfType<WorkflowOutputEvent>().Single().Data!;
Debug.Assert(result.Equals("Good morning, Jayden!"));
```
