# [基于OpenEvals的自动化评估-13]Agent执行轨迹评估[LLM-as-a-Judge]

[基于OpenEvals的自动化评估-12:Agent执行轨迹评估](https://blog.csdn.net/JaydenAI/article/details/163654240)介绍的轨迹评估很简单，它首先确定待评估的消息列表与作为基准的列表在消息数量上相等、角色上一一匹配。如果涉及工具调用，在根据指定的工具调用列表匹配模式和参数匹配模式对工具调用进行比较。其实Agent执行轨迹也可以借助LLM的力量，利用创建的基于**LLM-as-a-Judge**的评估器来评估。

## 1. LLM-as-a-Judge的评估器的创建

我们可以调用如下这个`create_trajectory_llm_as_judge`和`create_async_trajectory_llm_as_judge`函数来创建用于Agent轨迹评估的`SimpleEvaluator`和`SimpleAsyncEvaluator`对象，该函数的大部分参数都与[基于OpenEvals的自动化评估-02:LLM-as-a-Judge](https://blog.csdn.net/JaydenAI/article/details/163554430)中介绍的的`create_llm_as_judge`和`create_async_llm_as_judge`函数是一致的。

```python
def create_trajectory_llm_as_judge(
    *,
    prompt: str
    | Runnable
    | Callable[
        ..., list[ChatCompletionMessage]
    ] = TRAJECTORY_ACCURACY_PROMPT_WITH_REFERENCE,
    model: Optional[str] = None,
    feedback_key: str = "trajectory_accuracy",
    judge: Optional[
        Union[
            ModelClient,
            BaseChatModel,
        ]
    ] = None,
    continuous: bool = False,
    choices: Optional[list[float]] = None,
    use_reasoning: bool = True,
    few_shot_examples: Optional[list[FewShotExample]] = None,
) -> SimpleEvaluator

def create_async_trajectory_llm_as_judge(
    *,
    prompt: str
    | Runnable
    | Callable[
        ..., list[ChatCompletionMessage]
    ] = TRAJECTORY_ACCURACY_PROMPT_WITH_REFERENCE,
    model: Optional[str] = None,
    feedback_key: str = "trajectory_accuracy",
    judge: Optional[
        Union[
            ModelClient,
            BaseChatModel,
        ]
    ] = None,
    continuous: bool = False,
    choices: Optional[list[float]] = None,
    use_reasoning: bool = True,
    few_shot_examples: Optional[list[FewShotExample]] = None,
) -> SimpleAsyncEvaluator:
```

具体参数说明如下：

- **prompt**:定义评估提示词模板，类型可以是字符串，也可以是类似于`PromptTemplate`这样的`Runnable`对象（可以采用LCEL表达式于LLM进行连接），或者是一个用于返回LLM输入的消息列表的函数。如果以字符串定义提示词，可以包含如下的占位符:
  - {inputs}
  - {outputs}
  - {reference_outputs}
  - {由kwargs指定的参数名称}
- **feedback_key**：评估结果中存储的字段名，默认为`trajectory_accuracy`；
- **judge**/**model**: 用于提供用来实施评估的LLM；
- **system**： 系统提示词；
- **continuous**：评估结果是否是连续值：
  - **True**： 输出为`0~1`的连续浮点数；
  - **False**： 输出为布尔值。
- **choices**：如果希望评估结果采用指定的选项，可以利用此参数指定一个列表，比如`choices=[0.0, 0.5, 1.0]`意味着最终得分只有指定的三种选择；
- **use_reasoning**：是否要求模型输出评分理由：
  - **True**：输出包含解释；
  - **False**：只输出评分。
- **few_shot_examples**: 用于在提示词中加入`few-shot`示例，提升评估一致性。

在调用`SimpleEvaluator`/`SimpleAsyncEvaluator`进行评估的时候，定义在评估提示词模板的占位符会被同名的参数替换。如果使用`model`参数指定包含提供商的模型标准名称，方法内部会利用标准的URL创建代表LangChain LLM组件的`BaseChatModel`对象。如果需要连接自定义URL指向的LLM部署地址，或者需要对LLM组件对象进行定制，可以直接利用`judge`参数指定一个`BaseChatModel`对象。也可以直接执行一个`ModelClient`对象，`ModelClient`是OpenEvals针对LLM客户端组件的表达，但是此时依然需要利用model参数指定模型名称。

## 2. 默认提示词

从`create_trajectory_llm_as_judge`函数的参数定义可以看出，它默认使用的提示词通过常量**TRAJECTORY_ACCURACY_PROMPT_WITH_REFERENCE**表示。从命名可以看出，这是一个包含`{reference_outputs}`占位符作为评估基准的提示词模板，具体内容如下：

```markdown
You are an expert data labeler.
Your task is to grade the accuracy of an AI agent's internal trajectory.

<Rubric>
  An accurate trajectory:
  - Makes logical sense between steps
  - Shows clear progression
  - Is relatively efficient, though it does not need to be perfectly efficient
  - Is semantically equivalent to the provided reference trajectory
</Rubric>

Based on the following reference trajectory:

<reference_trajectory>
{reference_outputs}
</reference_trajectory>

Grade this actual trajectory:

<trajectory>
{outputs}
</trajectory>
```

定义在提示词中的评估规则（Rubric）定义了四条黄金标准，它定义了什么才算是一条**准确的轨迹**：

- **逻辑连贯性（Logical sense between steps）**：Agent的前一步行动和后一步行动之间必须有因果关系或合理的推导逻辑。如果第一步是**搜索用户购买记录**，第二步如果是**根据记录计算总金额**就符合逻辑；如果是**突然去搜索天气**就是逻辑断层;
- **步骤递进性（Clear progression）**：轨迹必须在**往前推进**任务，而不是在原地打转或陷入死循环。每一步都应该让Agent离最终目标更近;
- **相对高效性（Relatively efficient）**：允许Agent犯一点点小错或走一两步弯路（宽容度），但不接受极其冗长、试错无数次的低效轨迹;
- **语义等价性（Semantically equivalent to reference）**：这是最核心的硬性指标。实际轨迹调用的工具、思考的业务方向，在语义和实质内容上必须与`{reference_outputs}`（参考轨迹）保持高度一致。路径可以不完全一模一样，但核心逻辑和手段必须等价。

## 3. 针对LangChain Agent的评估

我们将[基于OpenEvals的自动化评估-12:Agent执行轨迹评估](https://blog.csdn.net/JaydenAI/article/details/163654240)演示的针对LangChain Agent的评估移植到这里，并切换成基于基于**LLM-as-a-Judge**的评估。我们将评估的核心操作定义在`eval`函数中，它会根据默认的提示词、用来连接LLM（`gpt-5.4-mini`）的`ChatOpenAI`对象以及传入的关键字参数，调用`create_async_trajectory_llm_as_judge`函数创建一个基于**LLM-as-a-Judge**的`SimpleAsyncEvaluator`对象。最后将指定的输出和引用输出作为参数调用这个评估器，并将评估结果以JSON形式输出。

```python
from  typing import cast
from openevals import create_async_trajectory_llm_as_judge
from langchain_openai  import ChatOpenAI
from langchain_core.messages import HumanMessage, AIMessage,ToolMessage,AnyMessage
from openevals.prompts.conversation import AGENT_TONE_PROMPT
from langchain.agents import create_agent
from langchain.tools import tool
from dotenv import load_dotenv
import asyncio,json

load_dotenv()

judge = ChatOpenAI(model="gpt-5.4-mini")
async def eval( *, 
    outputs:list[AnyMessage],
    reference_outputs: list[AnyMessage]|None = None,
    **kwargs):
    evaluator = create_async_trajectory_llm_as_judge(
        continuous= True,       
        judge= judge,
        **kwargs)
    result = await evaluator(outputs= outputs, reference_outputs=reference_outputs)
    print(json.dumps(result,ensure_ascii=False, indent=2)) 

@tool
def look_up_location_code(city:str)->str:
    """提取指定城市的位置代码
    Args:
        city: 城市名称

    Returns:
        指定城市对应的位置代码
    """

    return "location-123"

@tool
def get_weather(location_code:str) ->str:
    """提取指定位置代码所在地的天气
        Args:
            location_code: 位置代码
    
        Returns:
            天气信息
        """
    return "晴，气温25度"

agent = create_agent(
    model=ChatOpenAI(model="gpt-5.4-mini"),
    tools= [look_up_location_code, get_weather])

async def main():
   referenced_messages = [
        HumanMessage("..."),
        AIMessage(content="", tool_calls=[{"name": "look_up_location_code", "args": {"city": "苏州"}, "id": "call-001"}]), 
        ToolMessage(content="location-123", tool_call_id="call-001"),
        AIMessage(content="",tool_calls=[{"name": "get_weather", "args": {"location_code": "location-123"}, "id": "call-002"}]),
        ToolMessage(content="", tool_call_id="call-002"),
        AIMessage(content="...")]

   result = await agent.ainvoke(input={"messages":[{"role":"user", "content":"今天苏州是晴天吗？"}]})
   messages =cast(list[AnyMessage], result.get("messages"))
   for message in messages:
       message.pretty_print()
   await eval(outputs = messages, reference_outputs= referenced_messages)

asyncio.run(main())
```

我们在调用`create_agent`函数的时候注册了两个工具函数，`look_up_location_code`用来提取指定城市的位置代码，`get_weather`则根据指定位置代码获取所在地的天气信息。当我们调用这个Agent查询指定城市的天气时，正常的执行轨迹应该是：

- LLM在接收到作为原始查询的`HumanMessage`后，利用返回的`AIMessage`下发针对`look_up_location_code`工具函数的调用，作为参数的`city`为解析出来的城市名；
- Agent在本地完成工具执行后，将城市对应的位置代码以`ToolMessage`的形式发送给LLM；
- LLM再次以`AIMessage`的形式下发针对`get_weather`工具函数的调用，参数为得到的位置代码；
- Agent执行工具，将天气信息以`ToolMessage`的形式上传LLM；
- LLM将获得的天气信息整理成最终的答复，并以`AIMessage`的形式返回给Agent。

调用`eval`函数实施评估时指定的`reference_outputs`消息列表正式采用上面这个轨迹创建的。在对Agent最终输出的对话历史实施评估之前，我们还输出了每一条消息的内容，具体输出如下：

## 4. 无基准的轨迹评估

除了默认的包含评估基准、通过常量**TRAJECTORY_ACCURACY_PROMPT_WITH_REFERENCE**表示的提示词，OpenEvals还定义了另一个名为**TRAJECTORY_ACCURACY_PROMPT**的常量，并通过它定义了如下这个不含`{reference_outputs}`占位符的提示词模板。

```markdown
You are an expert data labeler.
Your task is to grade the accuracy of an AI agent's internal trajectory.

<Rubric>
  An accurate trajectory:
  - Makes logical sense between steps
  - Shows clear progression
  - Is relatively efficient, though it does not need to be perfectly efficient
</Rubric>

First, try to understand the goal of the trajectory by looking at the input
(if the input is not present try to infer it from the content of the first message),
as well as the output of the final message. Once you understand the goal, grade the trajectory
as it relates to achieving that goal.

Grade the following trajectory:

<trajectory>
{outputs}
</trajectory>
```

与默认的包含评估基准的提示词相比，这个无基准提示词具有如下的特点：

- **移除了最终对错的绝对绑架，聚焦于目标相关性**：它要求裁判模型不要死板地检查最终答案是否完美，而是检查整条轨迹的行动，是否都在为了达成那个目标而努力。它允许Agent最终失败（例如因为工具报错或外部服务器断网），但只要Agent的整个推理和工具调用链条是合乎逻辑、不断递进且高效的，裁判依然会给轨迹的**准确性（Accuracy）**打高分;
- **引入了目标逆向推导机制**: 由于这个评估只输入了{outputs}，因此提示词赋予了裁判**逆向推导**的能力，即让裁判通过阅读第一条消息（通常是用户的提问）和最后一条消息（Agent的最终回答），自己去脑补并定义出这个任务的**终极目标**是什么。

在移除了`reference_outputs`的对比要求后，评估规则被精简到了最纯粹的三驾马车：

- **逻辑性（Logical sense）**：步骤A到步骤B是否讲得通？（例如：查完城市代码 ➔ 查天气，通过；查完城市代码 ➔ 查股价，不通过）；
- **递进性（Clear progression）**：是不是每一步都在剥洋葱一样逼近真相，而不是在原地无限循环；
- **高效性（Relatively efficient）**：有没有废话和多余的工具调用。

在前面演示程序的基础上，我们需要将`main`函数做如下的修改，并能将切换到使用**TRAJECTORY_ACCURACY_PROMPT**提示词的无基准的轨迹评估上。

```python
async def main():
   result = await agent.ainvoke(input={"messages":[{"role":"user", "content":"苏州当前的晴天吗？"}]})
   messages =cast(list[AnyMessage], result.get("messages"))
   for message in messages:
       message.pretty_print()
   await eval(outputs = messages,  prompt= TRAJECTORY_ACCURACY_PROMPT)
```

毫无疑问，对于这个简单的Agent，其对话对话代表的执行规则肯定能够通过评估，并且能得高分：

```json

The steps are logically consistent, clearly progressive, and efficient with no unnecessary detours. Thus, the score should be: 1.0.",

## 5. 聚焦工具选择的评估

除了上述的两个严格意义上的基于Agent执行轨迹的提示词，OpenEvals还通过常量**TOOL_SELECTION_PROMPT**定义了如下一个重点关注工具选择的提示词。与前面讨论的**轨迹评估**关注Agent的整体思考和逻辑递进不同，基于工具选择的评估是一种更加聚焦的局部精细化审计。它把LLM的纯文本思考先放在一边，专门把Agent的**工具调用**切片提取出来进行显微镜式的审查。

```markdown
You are an expert data labeler. Your task is to grade the accuracy of an AI agent's tool selection during the resolution of a user query.

<Rubric>
Accurate tool selection:
- Uses the most appropriate tool for each step given the context
- Avoids unnecessary or redundant tool calls
- Uses tools in a logical order where dependencies exist
- Is semantically equivalent to the provided reference tool sequence, if present
</Rubric>

<Instructions>
1. Grade the following thread, evaluating whether the agent selected the right tools in the right order to resolve the user's query efficiently.
2. Evaluate both the choice of tools and whether any tools were unnecessary, missing, or could have been replaced with a more appropriate alternative
</Instructions>

Please grade the following trajectory according to the above instructions:

<trajectory>
{outputs}
</trajectory>
```

在复杂的Agent系统中，大模型最容易犯的错误之一就是**工具滥用**或**工具误用**。例如有能直接查到精准结果的工具，它偏不用，非要调用网络搜索去网页里捞。已经拿到了数据，却还要重复调用同一个工具。在没有拿到A工具的返回参数前，强行调用依赖该参数的B工具（顺序错误导致报错）。这个提示词就是为了揪出Agent在利用外部世界（API/数据库/函数）时的这些低效或错误行为。这个评估程序要求裁判大模型（Judge）对 {outputs} 中的工具序列进行以下四个维度的核对：

- **上下文自适应性**：检查Agent是否在特定的上下文状态下，选择了最完美、最对口的那个工具，而不是凑合能用的工具;
- **零冗余性**：严厉打击**废动作**。如果Agent连续调用同一个接口，或者调用了对解决问题毫无帮助的工具，在这里会被判定扣分;
- **拓扑依赖与逻辑顺序**：检查上下游工具的因果关系。如果顺序反了，就是严重的逻辑不合格；
- **基准等价性**：如果提供了标准答案，实际调用的工具链在核心功能和效果上必须与标准答案等价。

针对上面演示的针对Agent的两次调用，虽然因用户提问的方式不同导致了Agent生成基于不同轨迹的消息列表，但是从工具选择的角度都是合理的。如下的演示程序和生成的评估结果充分体现了这一点。
