# [DeepSeek Harness插件内核-04]事件总线完美解决各模块通信问题

作为Cordis的核心通信枢纽，所有插件与服务之间的松耦合协作均由其驱动。在Cordis架构中，插件之间通常不直接相互调用，而是通过事件总线服务进行跨模块通信。具体的事件总线服务体现为一个`EventsService`对象，`Context`的`events`字段返回的正是这个对象。值得一提的是，针对事件的注册借助了Fiber的力量实现了注册事件的自动化解除。如果希望深入了解 Cords的事件总线，需要对Fiber具有基本的认识，相关内容可以参阅前一篇文章[DeepSeek Harness插件内核-03:利用Fiber管理Context和插件的生命周期](https://blog.csdn.net/JaydenAI/article/details/164075891)。

## 1. Context下的EventsService

`EventsService`的构造函数在执行时额外添加了一个`Tracker`对象作为字段，该对象的`property`和`noShadow`字段分别为`ctx`和`true`，对应字段成员的Key采用常量`symbols.tracker`返回的`Symbol`。这个额外添加的字段与Context基于Proxy机制动态解析上下文成员策略有关，我们会在本系列后续文章中对此进行详细介绍，这里我们只需要知道通过这个小花招可用使我们访问`ctx.events.ctx`时可用得到当前的Context（而不是调用构造函数传入的`Context`，实际上构造函数根本就没有使用传入的`Context`）就可以了。

```typescript
class EventsService {
  constructor(private ctx: Context) {
    defineProperty(this, symbols.tracker, {
      property: 'ctx',
      noShadow: true,
    })
  ...
  }
}

class Context {
  constructor() {
    this.events = new EventsService(self)
  }
```

## 2. 监听事件的钩子

采用`Pub/Sub`模式设计的`EventsService`利用`_hooks`字段返回一个`Record<keyof any, Hook[]>`类型的对象来存储注册的事件监听器。从`Record`的定义可以看出，`_hooks`字段返回的是一个Key类型为`string|number|Symbol`，Value类型为`Hook`数组的字典。`Hook`是对`EventOptions`类型的扩展，我们可以利用它的`ctx`和`callback`字段得到当前的Context和作为监听器的回调函数。这个字典提供了事件和注册的监听处理器之间的映射关系。

```typescript
class EventsService {
  _hooks: Record<keyof any, Hook[]> = {}
}

type Record<K extends keyof any, T> = {
    [P in K]: T;
};

export interface Hook extends EventOptions {
  ctx: Context
  callback: (...args: any[]) => any
}

export interface EventOptions {
  prepend?: boolean
  global?: boolean
}
```

当注册作为事件监听处理器的`Hook`时，可以指定定义在`EventOptions`中的如下两个字段：

- **prepend**：是否前置追加。当有多个插件或模块订阅了同一个事件时，默认情况下，事件总线会按照代码运行的先后顺序将监听器推入队列（即`push`尾部追加）。如果设置了`prepend: true`，则会将当前监听器直接插入到该事件队列的最前端（即`unshift`头部追加）;
- **global**: 是否全局生效。Cordis框架最核心的特点是支持上下文隔离。当一个主Context派生出多个互相隔离的子Context时，各个子上下文内部的事件默认是**局部**的。如果一个事件监听器设置了`global: true`，意味着它将打破隔离屏障，无论事件是从哪一个子上下文、或者哪一个插件内部被触发的，这个监听器都一定能接收到并执行。

## 3. 事件监听器的注册

事件监听器的注册可以通过`EventsService`的如下三个方法来完成：

```typescript
class EventsService {
  register(label: string, hooks: Hook[], callback: any, options: EventOptions): () => void
  on(name: string | symbol, listener: (...args: any) => any, options?: boolean | EventOptions) 
  once(name: string, listener: (...args: any) => any, options?: boolean | EventOptions) 
}
```

三个方法说明如下：

- **register**：这是**最底层**的核心实现方法，用于将一个通用的监听器记录持久化;
- **on**：这是最常用的**公共 API**，用于让当前Fiber上下文监听一个特定的事件；
- **once**：这是基于`on`方法的高级封装，用于只捕获事件的**第一次触发**。

### 3.1 register

`register`方法是整个事件系统中最核心事件注册方法。它会调用当前`Fiber`的`effect`方法将提供的回调函数添加到指定的`hooks`列表中，并在当前`Fiber`终结时调用`unregister`方法解除当前的事件注册。

```typescript
class EventsService {
  register(label: string, hooks: Hook[], callback: any, options: EventOptions): () => void {
    const method = options.prepend ? 'unshift' : 'push'
    return this.ctx.fiber.effect(() => {
      hooks[method]({ ctx: this.ctx, callback, ...options })
      return () => this.unregister(hooks, callback)
    }, label)
  }

  unregister(hooks: Hook[], callback: any) {
    const index = hooks.findIndex(hook => hook.callback === callback)
    if (index >= 0) {
      hooks.splice(index, 1)
      return true
    }
  }
}
```

四个参数说明如下：

- **label**：诊断标签。Cordis拥有强大的诊断与调试系统，这个标签会在性能分析、内存泄漏排查、热重载链路追踪时，直接在控制台或可视化面板中显示；
- **hooks**：监听器数组。它传入的是存储结构体的数组引用，这允许`register`方法直接对其进行就地修改；
- **callback**：回调函数。这是用户真正想要执行的事件处理函数；
- **options**：事件选项。控制监听器的行为的`EventOptions`对象。

### 3.2 on

`on`法是面向开发者最常用的公共API。它的核心职责包括在安全的生命周期内，对用户的监听器进行合规性审查、动态绑定和拦截校验，完整实现如下所示：

```typescript
class EventsService {
  on(name: string | symbol, listener: (...args: any) => any, options?: boolean | EventOptions) {
    if (typeof options !== 'object') {
      options = { prepend: options }
    }

    this.ctx.fiber.assertActive()
    listener = this.ctx.reflect.bind(listener)
    const result = this.bail(this.ctx, 'internal/listener', name, listener, options)
    if (result) return result

    const hooks = this._hooks[name] ||= []
    const label =`ctx.on(${typeof name === 'string' ? JSON.stringify(name) : name.toString()})`
    return this.register(label, hooks, listener, options)
  }
}
```

`on`方法最终依然是调用`register`方法来完成最终的事件注册。传入的`label`通过格式化`name`参数表示的事件名称生成，而`Hook`数组来源于`EventsService`自身的`_hooks`字段，只需要将`name`参数作为Key将`Hook`数组提取出来即可。`on`方法传入的`options`可以是一个`EventOptions`对象， 也可以是一个布尔值。如果是后者，将视为`EventOptions`的`prepend`字段，也就是说用来控制注册的事件处理器是放在队列前面还是后面。

传统事件监听器的`this`通常指向`EventEmitter`实例。但Cordis中的`on`方法通过`reflect.bind`将监听器与当前注册它的`this.ctx`进行了隐式绑定。当这个事件在未来被某个服务触发时，执行的`listener`内部如果访问`this`，它拿到的不是全局上下文，也不是触发事件的上下文，而是当时注册这个事件的那个特定`Fiber`的上下文。这实现了多智能体、多插件之间的作用域隔离。

`on`方法的特殊之处还在于它在真正调用`register`方法来完成最终的事件注册之前，先调用`bail`方法触发一个名为`internal/listener`的内部审查事件。如果任何一个内部审查员（拦截插件）丢出了一个结果，整个注册流程就会在这里被强行中止（熔断），并直接返回该结果。在Cordis事件系统中，派发事件有多种方式,而`bail`是一种**一旦有结果，立即停止**的熔断派发机制：

- 它会依次执行所有监听了`internal/listener`事件的钩子函数;
- 如果这些钩子函数都返回`undefined`（即不干预），程序就会继续往下走;
- 只要有任意一个钩子函数返回了非`undefined`的值（即触发了拦截），`bail`方法 就会立即中止后续所有钩子的执行，并将这个值作为`result`返回。

### 3.3 once

`once`方法是基于`on`方法实现的一个非常精妙、紧凑的高级封装。它的核心职责是注册一个**阅后即焚**的事件监听器，确保用户的回调函数在事件第一次触发后，能够安全地完成自我注销（自我清理），同时绝不影响事件的正常执行。从如下的实现可以看出，**阅后即焚**是通过闭包的方式实现的：它调用`on`方法完成事件注册并返回用于接触注册的函数，这个函数会在注册的回调中被执行，进而确保回调操作不会继续执行。

```typescript
class EventsService {
  once(name: string, listener: (...args: any) => any, options?: boolean | EventOptions) {
    const dispose = this.on(name, function (...args: any[]) {
      dispose()
      return listener.apply(this, args)
    }, options)
    return dispose
  }
}
```

## 4. 事件的分发

`EventsService`包含了一系列完整的事件分发方法。这些方法通过底层的`dispatch`机制，提供了从同步到异步、从并发到流式的全方位事件驱动能力。

```typescript
class EventsService {
  dispatch(type: string, args: any[]) 
  async parallel(...args: any[]) 
  emit(...args: any[]) 
  async serial(...args: any[]) 
  bail(...args: any[]) 
  waterfall(...args: any[]) 
}
```

相关方法说明如下：

- **dispatch**：它是系统内置的核心过滤器，负责解析事件参数并分离出特定的上下文环境。只有通过作用域安全校验（如沙箱隔离）的有效监听器才会被分发出来，并强制绑定调用者的`this`指针；
- **emit**：它采用**同步非阻塞**的方式顺次执行所有筛选出来的监听器。系统触发该事件后便会立即结束，完全不会等待异步监听器（Promise）的执行结果；
- **parallel**：它是专门为**异步多任务并发**设计的并行分发方法。系统会同时启动所有回调并等待它们全部执行完毕，最后统一捕获并抛出可能存在的聚合错误；
- **serial**：它用于**异步串行**的场景，会严格按照监听器在队列中的先后顺序依次执行并等待。一旦某个异步节点返回了非`undefined`的有效值，后续流程便会立刻中断并将其作为最终结果返回；
- **bail**：它是`serial`方法的**同步高速版本**，通常在需要**一票否决**的预检和安全审查场景中被调用。它会以同步的方式顺次调用监听器，只要有任意一个拦截器给出了明确的表态，整个分发链路就会瞬间熔断；
- **waterfall**：它巧妙地实现了类似洋葱模型的中间件控制流，将多个监听器组合成环环相扣的执行链条。外部的监听器会优先执行，并且它们必须显式调用系统生成的`next()`回调才能将控制权传递给下一层。

### 4.1 dispatch

`EventsService`的`dispatch`方法是其事件分发和钩子执行的核心逻辑。

```typescript
class EventsService {
  dispatch(type: string, args: any[]) {
    const thisArg = typeof args[0] === 'object' || typeof args[0] === 'function' ? args.shift() : null
    const name: string = args.shift()
    if (!name.startsWith('internal/')) {
      this.emit('internal/dispatch', type, name, args, thisArg)
    }
    const filter = thisArg?.[Context.filter]
    return (this._hooks[name] || [])
      .filter(hook => hook.global || !filter || filter.call(thisArg, hook.ctx))
      .map(hook => hook.callback.bind(thisArg))
  }
}
```

通过简单的几行代码，`dispatch`实现如下的功能：

- **动态参数解析 + 提取执行上下文**：该方法支持一种灵活的调用约定。它首先检查`args`数组的第一个元素。如果第一个元素是对象或函数，它会被作为执行构造函数的执行上下文（`this`），否则执行上下文为`null`。接着从剩余的参数中提取事件名称，此时`args`剩下的部分将作为调用构造函数的参数；
- **内部生命周期事件广播**： 如果是一个常规务事件（事件名称不采用`internal/`作为前缀），它会先触发一个`internal/dispatch`事件。这允许开发人员编写专门的调试插件来捕获、记录或拦截整个应用中发生的所有事件分发行为;
- **构造函数的过滤**: 如果第一步解析出来作为的执行上下文不为`null`，并且通过`Context.filter`这个`Symbol`返回了一个过滤器函数。对于非全局Hook（global字段被设置为true），则将候选Hook的Context作为参数调用它，进而过滤出符合条件的Hook列表；
- **执行上下文的绑定**: 调用Hook回调函数的bind方法绑定第一步解析出来的执行上下文（`this`）。

### 4.2 emit

`emit`是最基础的同步事件触发方法。它的核心逻辑非常精简，完全复用了我们前面分析的`dispatch`方法。

```typescript
class EventsService {
  emit(...args: any[]) {
    this.dispatch('emit', args).map(cb => cb(...args))
  }
}
```

从定义可以看出`emit`的设计特点：

- `emit`内部使用的是单纯的遍历。如果钩子函数是一个异步函数（返回`Promise`），`emit`不会等待它执行完毕，而是会直接触发下一个钩子；
- 由于没有对`cb(...args)`的返回值进行收集或处理，事件的发起者无法得知钩子函数执行后返回了什么结果。

在如下的演示程序中，我们针对事件`foobar`注册了两个异步执行的处理器`foo`和`bar`，它们分别模拟2秒和1秒的异步等待，我们在会在处理器执行的开始和结束时生成相应的输出。我们最终调用`emit`方法分发事件`foobar`。从输出可以看出，注册的两个处理时同时执行的。

```typescript
import { Context } from '@deepseek-ai/cordis'

const delay = (ms: number) => new Promise(resolve => setTimeout(resolve, ms));
const context = new Context();

function createListener(
    name: string, 
    elapsed:number,
    returnValue: any = undefined):(...args: any) => any{
    return async (...args)=>{
        console.log(`Handler ${name} starts to execute with arguments ${args}`);
        await delay(elapsed);
        console.log(`Handler ${name}'s execution stops.`);
        return returnValue;
    };
}

context.events.on("foobar",createListener("foo", 2000));
context.events.on("foobar",createListener("bar", 1000));
context.events.emit("foobar","a","b","c");
```

输出：

```text
Handler foo starts to execute with arguments a,b,c
Handler bar starts to execute with arguments a,b,c
Handler bar's execution stops.
Handler foo's execution stops.
```

### 4.3 serial

`serial`方法是异步串行（顺序）触发事件的核心实现。与前面的`emit`（同步）不同，`serial`采用的是**一个接一个等待**的串行执行模式，并且引入了非常关键的熔断机制。

```typescript
class EventsService {
  async serial(...args: any[]) {
    for (const cb of this.dispatch('serial', args)) {
      const result = await cb(...args)
      if (isBailed(result)) return result
    }
  }
}

export function isBailed(value: any) {
  return value !== null && value !== false && value !== undefined
}
```

我们将上面演示程序中用于分发事件的`emit`方法替换成如下的`serial`方法，会发现注册的两个事件处理器会按照注册的顺序依次执行：

```typescript
...
context.events.serial("foobar","a","b","c");
```

输出：

```bash
Handler foo starts to execute with arguments a,b,c
Handler foo's execution stops.
Handler bar starts to execute with arguments a,b,c
Handler bar's execution stops.
```

如果我们让第一个执行的处理函数返回一个非`null|undefined|false`的值，将会触发熔断机制，此时第二个处理器将不会执行：

```typescript
...
context.events.on("foobar",createListener("foo", 1000, true));
context.events.on("foobar",createListener("bar", 500));
context.events.serial("foobar","a","b","c");
```

输出：

```bash
Handler foo starts to execute with arguments a,b,c
Handler foo's execution stops.
```

### 4.4 parallel

`parallel`方法拥有极其严谨的健壮性设计。它不仅实现了异步并发，还解决了Node.js/前端开发中常见的异步错误丢失和多错误同时抛出的难题。

```typescript
class EventsService {
  async parallel(...args: any[]) {
    const results = await Promise.allSettled(this.dispatch('emit', args).map(async cb => cb(...args)))
    const errors = results.filter((result): result is PromiseRejectedResult => result.status === 'rejected')
    if (errors.length) throw new AggregateError(errors.map(error => error.reason))
  }
}
```

最然`parallel`方法最终还是调用`dispatch`方法完成最终的事件分发，但是它在此基础提供了如下的增强功能:

- 调用`Promise.allSettled`强制等待所有插件的异步流程全部结束（无论成功还是失败），并将每个插件的执行状态（`fulfilled`或`rejected`）和原因包裹在对象中返回；
- 通过`.filter()`筛选出所有状态为`rejected`的失败结果；
- 把多个错误打包成一个单一的`AggregateError`对象抛出，外部调用者通过捕获这个`AggregateError`，可以通过其`.errors`字段看到每一个插件报错的完整堆栈信息。

由于`parallel`返回一个`Promise<void>`对象，所以整个事件分发结束标志应该是这个`Promise`执行结束的那一刻，下面的演示程序体现了`emit`和`parallel`方法针对这一点的不同：

```typescript
let start = Date.now();
console.log("Emit based dispatch starts")
context.events.emit("foobar","a","b","c");
console.log(`Elapsed for emit: ${Date.now() - start}`)

await delay(1000);
start = Date.now();
console.log("\nParallel based dispatch starts")
await context.events.parallel("foobar","a","b","c");
console.log(`Elapsed for parallel: ${Date.now() - start}`)
```

输出:

```text
Emit based dispatch starts
Handler foo starts to execute with arguments a,b,c
Handler bar starts to execute with arguments a,b,c
Elapsed for emit: 3
Handler bar's execution stops.
Handler foo's execution stops.

Parallel based dispatch starts
Handler foo starts to execute with arguments a,b,c
Handler bar starts to execute with arguments a,b,c
Handler bar's execution stops.
Handler foo's execution stops.
Elapsed for parallel: 1013
```

### 4.5 bail

`bail`方法是**纯同步**、支持**熔断**机制的事件触发方法。它在结构上与我们之前解读的`serial`非常相似，但它们之间有一个本质的区别：`serial`是异步串行的（支持`await`），而`bail`是纯同步串行的，专门用于不需要任何异步等待、但需要插件提供拦截或返回结果的场景。

```typescript
class EventsService {
  bail(...args: any[]) {
    for (const cb of this.dispatch('bail', args)) {
      const result = cb(...args)
      if (isBailed(result)) return result
    }
  }
}

export function isBailed(value: any) {
  return value !== null && value !== false && value !== undefined
}
```

在如下的这个演示程序中，貌似注册的两个事件处理函数都返回`undefined`，照例说应该它们应该都会执行。但是事实上这是两个异步函数，返回的是`Promise<undefined>`，所以依然只有第一个事件处理函数会执行。

```typescript
import { Context } from '@deepseek-ai/cordis'

const delay = (ms: number) => new Promise(resolve => setTimeout(resolve, ms));
const context = new Context();

function createListener(
    name: string, 
    elapsed:number,
    returnValue: any = undefined):(...args: any) => any{
    return async (...args)=>{
        console.log(`Handler ${name} starts to execute with arguments ${args}`);
        await delay(elapsed);
        console.log(`Handler ${name}'s execution stops.`);
        return returnValue;
    };
}

context.events.on("foobar",createListener("foo", 2000));
context.events.on("foobar",createListener("bar", 1000));
context.events.bail("foobar","a","b","c");

```

输出

```text
Handler foo starts to execute with arguments a,b,c
Handler foo's execution stops.
```

### 4.6 waterfall

普通的事件监听是**并行**”或**独立**执行的，而`waterfall`（瀑布/流水线）模式允许每一个注册的事件处理函数控制是否将控制权传递给下一个函数。该方法的核心功能是实现类似中间件的洋葱模型或流水线机制。

```typescript
class EventsService {
  waterfall(...args: any[]) {
    const cbs = this.dispatch('waterfall', args)
    const inner = args.pop()
    const next = () => {
      const cb = cbs.shift() ?? inner
      return cb(...args)
    }
    args.push(next)
    return next()
  }
}
```

在如下的演示程序中，我们定义了用来创建事件监听器的`createListener`函数，参数`name`和`shortCut`分别代表监听器名称和就此**短路**。如果`shortCut`为`true`，监听函数会从参数列表中弹出最后一个用来调用后续监听器的函数，并将其返回结果作为返回值，否则直接将当前监听器名称作为返回值。

```typescript
import { Context } from '@deepseek-ai/cordis'

const context = new Context();
const events = context.events;
function createListener(
    name: string, 
    shortCut: any = false):(...args: any) => any{
    return (...args)=>{
        if (!shortCut){
            const next = args.pop() as any;
            return next();
        }
        else {
            return name
        }
    };
}

let foo =events.on("event",createListener("foo"));
let bar = events.on("event",createListener("bar", true));
let baz = events.on("event",createListener("baz"));
console.log(`result = ${events.waterfall("event","args...", ()=>"final")}`);

foo();
bar();
baz();
foo =events.on("event",createListener("foo"));
bar = events.on("event",createListener("bar"));
baz = events.on("event",createListener("baz", true));
console.log(`result = ${events.waterfall("event","args...", ()=>"final")}`);

foo();
bar();
baz();
foo =events.on("event",createListener("foo"));
bar = events.on("event",createListener("bar"));
baz = events.on("event",createListener("baz"));
console.log(`result = ${events.waterfall("event","args...", ()=>"final")}`);
```

我们从创建的Context中提取`EventsService`，并调用`createListener`函数创建了三个监听函数注册到它上面。针对三个依次注册的监听函数`foo`、`bar`和`baz`，我们模拟了三种场景，前两次将短路节点设置在`bar`和`baz`上面，最后依次没有设置短路节点。我们通过调用`waterfall`方法将订阅的事件分发出去，并得到了不同的结果：

```bash
result = bar
result = baz
result = final
```
