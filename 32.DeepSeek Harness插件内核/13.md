# [DeepSeek Harness插件内核-13]插件在ReistryService的注册

Cordis中，**万物皆插件** ，但是插件的定义简单至极，用来调用插件执行和管理器周期的`Fiber`才是核心所在。在通过[DeepSeek Harness插件内核-10：Fiber是如何管理插件生命周期的](https://jaydenai.blog.csdn.net/article/details/164335518) 完成了针对插件和`Fiber`的深度介绍之后，我们介绍一下用来注册插件的`RegistryService`服务。

## 1. 注册的插件如何存储？

通过前面系列文章的介绍，我们知道通过`ReigstryService`的`plugin`方法可以注册如下三种类型的插件，并会调用`resolve`方法将她们统一转换成一个函数。

```typescript
export class RegistryService {
  resolve(plugin: Plugin): Function | undefined {
    try {
      if (typeof plugin === 'function') return plugin
      if (isApplicable(plugin)) return plugin.apply
    } catch {}
  }
}

export namespace Plugin {
  export interface Base<T = any> {
    name?: string
    Config?: StandardSchemaV1<any, T>
    inject?: Inject
    provide?: string | string[]
    intercept?: Dict<boolean>
  }

  export interface Function<T = any> extends Base<T> {
    (ctx: Context, config: T): any
  }

  export interface Constructor<T = any> extends Base<T> {
    new (ctx: Context, config: T): any
  }

  export interface Object<T = any> extends Base<T> {
    apply(ctx: Context, config: T): any
  }
}

export type Inject<M = Dict> = (keyof M)[] | { [K in keyof M]?: M[K] }
```

针对同一个插件函数（表示最终通过`resolve`方法生成的`Function`）的第一次注册将会伴随着`Plugin.Runtime`的创建，后者的`callback`字段返回的就是此函数。除此之外，如果注册是指定了插件名称，它会体现在`name`字段上，另一个`Config`字段返回的`StandardSchemaV1`可以用来检验提供的插件配置的结构。注册的每个插件实例都会对应一个`Fiber`对象，针对当前函数注册的实例会被存储在`fiber`字段返回的`DisposableList<Fiber>`列表中。

```typescript
export namespace Plugin {
  export interface Runtime {
    name?: string
    fibers: DisposableList<Fiber>
    callback: globalThis.Function
    Config?: StandardSchemaV1
  }
}

export class RegistryService {
  private _counter = 0
  private _internal = new Map<Function, Plugin.Runtime>()；

  constructor(public ctx: Context) {
    defineProperty(this, symbols.tracker, {
      property: 'ctx',
      noShadow: true,
    })
  }
}
```

`RegistryService`会使用`_internal`字段返回的字典来存储注册的插件，该字典的Key和Value分别是插件函数和对应的`Runtime`对象。除此之外，它还有一个通过`_counter`表示的插件注册计数器。该计数器将会作为注册插件对应`Fiber`的`uid`，对于每一次插件注册，该计数器都会自增。

上面的代码一并给出了`RegistryService`的构造函数的定义，可以看出它为`symbols.tracker`字段设置一个`Tracker`对象，并将其`property`字段设置为`ctx`，意味着当前的`Context`将会绑定到它的`ctx`字段上，具体原理可以参考我的文章[DeepSeek Harness插件内核-07:Context全面解析](https://blog.csdn.net/JaydenAI/article/details/164191913)。`Tacker`的`noShadow`设置为`true`，意味着在调用其方法的时候提供的`Context`不会附加**影子上下文**。

## 2. 两种插件注册方式

插件的常规注册指的是调用`Plugin`方法来注册插件。从如下的代码可知，调用该方法除了必须提供三种形式之一的插件之外，我们还可以提供插件的配置。另一个参数指定的函数用来获取或者构建当前调用堆栈，默认提供的是如下定义的`buildOuterStack`函数。

```typescript
export class RegistryService {
  plugin(plugin: Plugin, config?: any, getOuterStack = buildOuterStack()) {
    const callback = this.resolve(plugin)
    if (!callback) throw new Error('invalid plugin, expect function or object with an "apply" method, received ' + typeof plugin)
    this.ctx.fiber.assertActive()

    let runtime = this._internal.get(callback)
    if (!runtime) {
      let name = plugin.name
      if (name === 'apply') name = undefined
      runtime = { name, callback, fibers: new DisposableList(), Config: plugin.Config }
      this._internal.set(callback, runtime)
    }

    const fiber = new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, getOuterStack)
    const wrapped = Object.create(fiber) as Fiber & PromiseLike<Fiber>
    wrapped.then = (onFulfilled, onRejected) => {
      return fiber.await().then(onFulfilled, onRejected)
    }
    return wrapped
  }
}

export function buildOuterStack(offset = 0) {
  const outerError = new Error()
  return () => outerError.stack!.split('\n').slice(3 + offset)
}
```

在将提供的原始插件通过`resolve`方法转换成通过的插件函数，并确认当前`Fiber`为激活状态之后，`plugin`方法会试着利用该返回从`_internal`字典中提取对应的`Runtime`对象，如果不存在就创建一个。接下来针对`Fiber`的创建是`plugin`方法的核心操作，调用`Fiber`构造函数传入的参数包括：

- 当前`Context`;
- 提供的可选配置；
- 注入服务（这里为空）；
- 创建的`Runtime`；
- 构建或者获取当前调用堆栈的函数

我们在[DeepSeek Harness插件内核-10：`Fiber`是如何管理插件生命周期的](https://jaydenai.blog.csdn.net/article/details/164335518)逐行分析过`Fiber`构造函数的实现。如果满足插件执行的要求，即插件对象的`inject`字段提供的注入服务全部就绪，创建的`Fiber`会提供它绑定的`Context`和配置执行插件函数。否则会进入`Fiber`构建的状态机流转循环。

最后四行代码的核心意图非常巧妙，它是一种经典的**双态（Dual-state）代理设计模式**。它的核心目的是让`plugin`方法的返回值既是一个可以立即同步使用的`Fiber`实例（同步态），又是一个可以通过`await`或`.then()`异步等待插件加载就绪的`Promise`对象（异步态）。

[DeepSeek Harness插件内核-12：这算Cordis一个大BUG吗?(续)](https://jaydenai.blog.csdn.net/article/details/164357893) 我们介绍了Cordis针对**先注入声明，后调用消费**的依赖注入策略，如果调用`plugin`方法并希望同时提供依赖服务的注入声明，注册的插件只能采用**对象形式**。如果希望采用最简单的**函数形式**，可以调用如下这个`inject`方法。

```typescript
export class RegistryService {
  inject(inject: Inject, callback: Plugin.Function<void>) {
    return this.plugin({ inject, apply: callback, name: callback.name })
  }
}
export type Inject<M = Dict> = (keyof M)[] | { [K in keyof M]?: M[K] }
```

`inject`方法提供的服务注入声明可以是以来服务名称列表，也可以是包含服务配置的字典。方法内部会插件回调函数和提供的服务注入声明转换成对象形式的产检，最终还是调用`plugin`方法实施注册。

## 3. 其他方法

除了最为核心的用来注册插件的`plugin`和`inject`方法，以及将三种形式的插件统一转换成函数的`resolve`方法外，`RegistryService`还提供了一系列额外的方法，这些方法基本是围绕针对`_counter`和`_internal`这两个字段的读写实现。

```typescript
export class RegistryService {
  private _counter = 0
  private _internal = new Map<Function, Plugin.Runtime>()

  get counter() {
    return ++this._counter
  }

  get size() {
    return this._internal.size
  }

  get(plugin: Plugin) {
    const key = this.resolve(plugin)
    return key && this._internal.get(key)
  }

  has(plugin: Plugin) {
    const key = this.resolve(plugin)
    return !!key && this._internal.has(key)
  }

  delete(plugin: Plugin) {
    const key = this.resolve(plugin)
    const runtime = key && this._internal.get(key)
    if (!runtime) return
    this._internal.delete(key)
    for (const fiber of runtime.fibers) {
      fiber.dispose()
    }
    return runtime
  }

  keys() {
    return this._internal.keys()
  }

  values() {
    return this._internal.values()
  }

  entries() {
    return this._internal.entries()
  }

  forEach(callback: (value: Plugin.Runtime, key: Function) => void) {
    return this._internal.forEach(callback)
  }
}
```

- **counter**： 在注册插件之前被调用，利用自证的计数器作为插件绑定`Fiber`对象的`uid`；
- **size**：回去当前注册插件函数（非插件实例）的数量；
- **get**： 根据指定的插件提取对应的`Runtime`；
- **has**：确定指定的插件是否被注册；
- **delete**：借助指定插件所有实例的注册，它不仅仅是将对应的`Runtime`从`_internal`字典中移除，还会调用每个插件实例对应`Fiber`对象的`dispose`方法将销毁，同时实施存续期间收集的清理工作；
- **keys/values/entries**： 针对_internal的Key、Value和KV的迭代；
- **forEach**： 针对每个`Runtime`和插件函数执行指定的回调。
