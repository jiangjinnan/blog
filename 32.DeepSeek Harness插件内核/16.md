# [DeepSeek Harness插件内核-16]Cordis究竟定义了哪些内部事件

实现在`EventsService`的事件总线是Cordis的通信网络，也是DeepSeek Harness基于通信的基础设施。运行中的Cordis很多基础的功能要求涉及的模块相互协作，必然会使用到一些内部定义的事件。虽然被标识为内部事件，并不意味着它们不能为我们自定义的插件所用，所以我们有必要来了解它们。这些内部事件名称都以`internal/`作为前缀，对应的处理函数的签名定义在如下这个`Events`接口上。由于[DeepSeek Harness插件内核-15：再谈Cordis的事件总线](https://blog.csdn.net/JaydenAI/article/details/165708590)已经对`internal/update`、`internal/listener`和`internal/dispatch`进行过深入介绍，这里只关注剩下这些。

```typescript
export interface Events {
  'internal/plugin'(fiber: Fiber): void
  'internal/status'(fiber: Fiber, oldValue: FiberState): void
  'internal/service'(this: Context, name: string, value: any): void
  'internal/update'(this: Fiber, config: any, noSave: boolean, next: () => void | Promise<void>): void | Promise<void>
  'internal/get'(ctx: Context, name: string, error: Error, next: () => any): any
  'internal/set'(ctx: Context, name: string, value: any, error: Error, next: () => boolean): boolean
  'internal/listener'(this: Context, name: string, listener: any, prepend: boolean): void
  'internal/dispatch'(mode: DispatchMode, name: string, args: any[], thisArg: any): void
}
```

## 1. internal/plugin

在如下两种场景下以emit方式触发此事件：

- 调用`RegistryService`的`plugin`方法中完整插件注册；
- `Fiber`的`dispose`方法被调用。

涉及的相关代码如下所示。当`Fiber`的构造函数在完成针对`dispose`方法的设置后，会调用`emit`方法触发此事件。设置的`dispose`方法会将`uid`设置为`null`，并调用`emitPluginDisposed`方法以`emit`形式调用`EventsService`的`dispatch`方法实现针对此事件的分发。

```typescript
export class Fiber {  
  constructor(
    public parent: Context,
    config: any,
    public inject: Dict<any>,
    public runtime: Plugin.Runtime | null,
    getOuterStack: () => string[]) {
    if (runtime) {   
      this.dispose = parent.fiber.effect(() => {
        ...
        return async () => {
          this.uid = null
          emitPluginDisposed(this.context, this)
          ...
        }
      }, 'ctx.plugin()')

      try {
        this.context.emit('internal/plugin', this)
      } catch (error) {
        ...
      }
      ...
    }
  }
}

function emitPluginDisposed(context: Context, fiber: Fiber) {
  const args: any[] = ['internal/plugin', fiber]
  let callbacks: Function[]
  try {
    callbacks = context.events.dispatch('emit', args)
  } catch (error) {
    ...
  }
  ...
}
```

事件携带唯一的参数就是当前`Fiber`对象，我们按照如下的方式利用`Fiber`的`uid`来区分两种场景：

```typescript
import { Context, Fiber } from '@deepseek-ai/cordis'

const ctx = new Context()
ctx.on("internal/plugin", (fiber: Fiber) => {
    console.log(`
Receive 'internal/plugin' event
fiber.runtime.name: ${fiber.runtime?.name}
fiber.uid: ${fiber.uid}`)
})

const fiber = ctx.plugin({
    name: "foobar",
    apply(ctx: Context) {
      console.log("Execute plugin foobar...")
      return ()=> console.log("Dispose plugin foobar...")
    }
})

await fiber.await()
fiber.dispose()
process.stdin.resume()
```

输出：

```bash
Receive 'internal/plugin' event
fiber.runtime.name: foobar
fiber.uid: 1
Execute plugin foobar...

Receive 'internal/plugin' event
fiber.runtime.name: foobar
fiber.uid: null
Dispose plugin foobar...
```

## 2. internal/status

此事件以`emit`形式触发用来通知某个`Fiber`的状态发生了改变，该事件的具体触发实现在`Fiber`如下所示的`_updateState`方法中，两个事件参数分别表示当前`Fiber`和之前的状态。

```typescript
export class Fiber {  
  private _updateState(callback: () => void | FiberState) {
    const oldState = this.state
    this.state = callback() ?? this._getState()
    if (oldState === this.state) return
    this.context.emit('internal/status', this, oldState)
    ...
  }
}
```

在如下的演示程序中，我们模拟了几种改变`Fiber`状态的场景。我们在根`Context`中通过注册此事件输出`Fiber`的状态转换。我们注册了一个注入了依赖服务`foo`和`bar`的插件，并先后注册了这两个依赖服务。然后再解除针对`bar`服务的注册，最终调用`Fiber`对象的`dispose`方法。从输出可以看出这些行为导致了`Fiber`相应状态的变换。

```typescript
import { Context, Fiber, FiberState} from '@deepseek-ai/cordis'
const FiberStateNames: Record<FiberState, string> = {
    [FiberState.PENDING]: 'PENDING',
    [FiberState.LOADING]: 'LOADING',
    [FiberState.ACTIVE]: 'ACTIVE',
    [FiberState.FAILED]: 'FAILED',
    [FiberState.DISPOSED]: 'DISPOSED',
    [FiberState.UNLOADING]: 'UNLOADING',
};
const ctx = new Context()
ctx.on("internal/status", (fiber: Fiber, oldState:FiberState) => 
    console.log(`${FiberStateNames[oldState]}=>${FiberStateNames[fiber.state]}`))

const fiber = ctx.plugin({
    name: "foobar",
    inject:["foo", "bar"],
    apply(ctx: Context) {
      console.log("Execute plugin foobar...")
      return ()=> console.log("Dispose plugin foobar...")
    }
})
await fiber.await()
console.log("\nregiser service 'foo' and 'bar'")
ctx.provide("foo",{})
const unregister = ctx.provide("bar",{})

await fiber.await()
console.log("\nunregister service 'bar'")
unregister()

await fiber.await()
console.log("\ndispose fiber")
fiber.dispose()
```

输出：

```bash
regiser service 'foo' and 'bar'
PENDING=>LOADING
Execute plugin foobar...
LOADING=>ACTIVE

unregister service 'bar'
ACTIVE=>UNLOADING
Dispose plugin foobar...
UNLOADING=>PENDING

dispose fiber
PENDING=>UNLOADING
UNLOADING=>DISPOSED
```

## 3. internal/config

此事件用来通知插件的配置发生了改变，事件的触发具有如下面代码所示的两种场景。

- 直接调用`Fiber`的`update`方法修改对应插件的配置；
- 在发生重载的时候。

两种情况都会调用同一个方法`_resolveConfig`以`waterfall`的形式触发此事件，并将新的配置作为第一个参数提供的`next`函数直接返回该配置对象。

```typescript
export class Fiber {  
  private _resolveConfig(config: any) {
    config = this.context.waterfall(this, 'internal/config', config, () => config)
    return this.runtime ? resolveConfig(this.runtime, config) : config
  }

  private async _reload() {
    this.store = { ...this._store }
    const oldEpoch = this._runner.epoch
    try {
      ...
      if (this._runner.epoch === oldEpoch) {
        this.config = this._resolveConfig(this._config)
        await this._execute(this._runner)
        this._error = undefined
      }
    } catch (reason) {
      ...
    }
    ...
  }

update(config: any, noSave = false) {
    ...
    config = this._resolveConfig(config)
    ...
  }
}
```

在如下的演示程序中，我们在根`Context`上注册了此事件并输出插件的当前更新的配置。我们注册的插件同样注入`foo`和`bar`两个服务，并将初始配置设置为`{value:"123"}`。我们模拟了三种触发事件的场景：

- 插件依赖的所有服务第一次全员上线；
- 依赖服务被卸载后重新上线；
- 调用`Fiber`的`update`方法手工修改插件配置。

```typescript
import { Context, Fiber} from '@deepseek-ai/cordis'
const ctx = new Context()
ctx.on("internal/config", function( this:Fiber, config, next:()=>any) {
   console.log(`[internal/config]${this.runtime?.name}: {value: ${config?.["value"]}}` ) 
   return next()
})

const fiber = ctx.plugin({
    name: "foobar",
    inject:["foo", "bar"],
    apply(ctx: Context, config:{value: string}) {
      console.log(`Execute plugin foobar with config value '${config.value}'`)
      return ()=> console.log("Dispose plugin foobar...")
    }
},{value: "123"})

await fiber.await()
console.log("\nregiser service 'foo' and 'bar'")
ctx.provide("foo",{})
const unregister = ctx.provide("bar",{})

await fiber.await()
console.log("\nunregister service 'bar'")
unregister()

await fiber.await()
console.log("\nregiser service 'bar'")
ctx.provide("bar",{})

await fiber.await()
console.log("\nupdate plugin's config")
fiber.update({value: "456"})
```

输出：

```log

[internal/config]foobar: {value: 123}
Execute plugin foobar with config value '123'

regiser service 'bar'
[internal/config]foobar: {value: 123}
Execute plugin foobar with config value '123'

update plugin's config
[internal/config]foobar: {value: 456}
Dispose plugin foobar...
[internal/config]foobar: {value: 456}

```

## 4. internal/service

当`ReflectService`通过`provide`方法注册新的服务，或者注册服务被解除时，会触发此事件对外通知服务注册发生改变。事件的触发具体实现在`ReflectService`的`notify`中，该事件以`emit`形式发出，当前`Context`会作为执行事件处理函数的上下文对象（`this`），后面的参数会写道服务的注册名称和服务对象。由于服务具有隔离性，所以`notify`方法会默认提供一个针对`symbols.isolate`字典的过滤函数。

```typescript
export class ReflectService {
  provide(name: string, value?: any, check?: () => boolean) {
    return this.ctx.fiber.effect(() => {
      ...
      if (this.ctx.fiber.state === FiberState.ACTIVE) {
        this.notify([name])
      }
      return async () => {
        const fibers = this.notify([name])
      }
    }, `ctx.provide(${JSON.stringify(name)})`)
  }

  notify(names: string[], filter = (ctx: Context, name: string) => ctx[symbols.isolate][name] === this.ctx[symbols.isolate][name]) {
    ...
    for (const name of names) {
      const self: Context = Object.create(this.ctx)
      self[symbols.filter] = (target: Context) => filter(target, name)
      this.ctx.events.emit(self, 'internal/service', name, this._getImpl(name, false)?.value)
    }
    return fibers
  }
}
```

在如下的演示程序中，我们在根`Context上`注册了此事件，并输出服务的注册名称、服务对象和所在插件的名称。接下来我们以嵌套的方式注册了两个插件`plugin1`和`plugin2`，并在对应的插件函数中注册了命名为`service1`和`service2`的服务对象。当正常启动之后，我们调用第二个插件对应`Fiber`对象的`dispose`方法，它会解除针对`service2`的注册。所以我们总过会接收到针对两个服务的三个事件。

```typescript
import { Context, Fiber} from '@deepseek-ai/cordis'
const ctx = new Context()
ctx.on("internal/service", function( this:Context, name:string, value) {
  const service = value as {foo:string, bar:string}
  const pluginName = this.fiber.runtime?.name
  console.log(`[internal/service@${pluginName}]${name}: {foo: ${service.foo}, bar:${service.bar}}`) 
})

let fiber1: Fiber, fiber2:Fiber

fiber1 = ctx.plugin({
  name: "plugin1",
  apply(ctx:Context){
    const dispose = ctx.provide("servce1",{foo:"111",bar:"111"})
    fiber2 = ctx.plugin({
        name: "plugin2",
        apply(ctx: Context){
          return ctx.provide("server2",{foo:"222",bar:"222"})
        }
      }
    )
    return ()=>dispose()
  }
})

await fiber1.await()
console.log("\ndispose fiber2")
fiber2!.dispose()
```

输出：

```bash
[internal/service@plugin1]servce1: {foo: 111, bar:111}
[internal/service@plugin2]server2: {foo: 222, bar:222}

dispose fiber2
[internal/service@plugin2]server2: {foo: 222, bar:222}
```

## 5. internal/get & internal/set

我们知道Cordis中使用的`Context`仅仅是一个代理，具体的代理处理器定义在`ReflectService`的静态字段`handler`。从它的`get`和`set`方法可以看出：如果从代理读取或写入一个没有真正定义在`Context`对象上的字段时，它会调用`EventsService`的`waterfall`方法分别触发一个`internal/get`和`internal/set`事件。前者的参数提供当前`Context`、字段名称和宜昌对象，后者进一步将设置的值添加到参数列表中。

```typescript
export class ReflectService {
  static handler: ProxyHandler<Context> = {
    get: (target, prop, ctx: Context) => {
      ...
      try {
       ...
        return ctx.events.waterfall('internal/get', ctx, prop, error, () => {
          ...          
        })
      } catch (e: any) {
        throw e === error ? enhanceError(e) : e
      }
    },

    set: (target, prop, value, ctx: Context) => {
      ...
      try {
        ...
        return ctx.events.waterfall('internal/set', ctx, prop, value, error, () => {
          return ctx.reflect.set(prop, value, error)
        })
      } catch (e: any) {
        throw e === error ? enhanceError(e) : e
      }
    }
  }
}
```

在如下的演示程序中，我们定义了一个名为`FoobarService`的服务类型，并调用`provide`方法创建了一个对象以服务名称`foobar`注册到根`Context`上。为了便于操作，我们在`Context`接口上声明了一个同名的字段。随后我们以嵌套的形式注册了`plugin1`和`plugin2`两个插件，对应的函数会对`ctx.foobar`分别执行读写操作。注册的事件处理函数会针对这两项操作输出相应的内容，

```typescript
import { Context, symbols, Tracker} from '@deepseek-ai/cordis'

class FoobarService{
  [symbols.tracker]: Tracker={
    property:"ctx",
    noShadow: true
  }
  constructor(public ctx: Context, public foo:string, public bar:string){    
  }
}
declare module '@deepseek-ai/cordis'{
  interface Context{
    foobar: FoobarService
  }
}

const ctx = new Context()
ctx.provide('foobar',new FoobarService(ctx, '111', '111'))

ctx.on("internal/get", function(ctx:Context, name:string, _:Error, next: () => any) {
  const  pluginName = ctx.fiber.runtime?.name
  console.log(`[internal/get@${pluginName}]${name}`) 
  return next()
})
ctx.on("internal/set", function(ctx:Context, name:string, value:any , _:Error, next: () => any) {
  const  pluginName = ctx.fiber.runtime?.name
  const service = value as {foo:string, bar:string}
  console.log(`[internal/set@${pluginName}]${name}:{foo:${service.foo}, bar:${service.bar}}`) 
  return next()
})
const fiber = ctx.plugin({
  name: "plugin1",
  apply(ctx:Context){
    const foobar = ctx.foobar
    console.assert(foobar.foo == "111" && foobar.bar =="111")
    ctx.plugin({
        name: "plugin2",
        apply(ctx: Context){
          ctx.foobar = new FoobarService(ctx, "222","222");
        }
      }
    )
  }
})

await fiber.await()
```

输出：

```bash
[internal/get@plugin1]foobar
[internal/set@plugin2]foobar:{foo:222, bar:222}
```
