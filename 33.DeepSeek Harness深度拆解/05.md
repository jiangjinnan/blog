# [DeepSeek Harness深度拆解-05]补丁文件向插件树的转变

在Cordis的世界里，一切皆插件，所以将Cordis作为**心脏**的DSH来说，分层应用补丁文件的目的即使为了构建具有层次结构的插件树（这里所谓的插件树并不是说这个树的节点会对应一个具体的插件对象，而是说这棵树的结构与最终构建的插件对象所在的`Context`结构一致）。通过[DeepSeek Harness深度拆解-04:完整的插件配置树如何构建？](https://jaydenai.blog.csdn.net/article/details/165428487)的介绍，我们知道DSH按照应用的顺序依次提供如下四种补丁文件：

- 由注册到Profile的包提供的补丁文件；
- Profile自身提供的补丁文件；
- DSH运行时目录中定义的供所有Profile共享的补丁文件；
- 启动DSH以命令行参数`--patch`指定的一组补丁文件。

每个补丁文件都提供一组`PatchOptions`列表，每个`PatchOptions`代表一个插件或者作为容器的插件组。接下来我们就来看看这些`PatchOptions`列表是如何转变成插件树，以及当配置改变的时候如何刷新插件树。

## 1. 插件在Cordis上下文中的位置

在[DeepSeek Harness深度拆解-03:创建一个新的Profile提供自定义插件](https://jaydenai.blog.csdn.net/article/details/165427804)中，我通过一个例子演示了如何利用定制的Profile来执行自定义的插件。我们利用注册在Profile的包构建了如下的插件补丁：

```yaml
- insert:
    - id: plugin1
      name: '@jaydenai/foo'
      config:
        source: package.json
    - id: plugin2
      name: '@jaydenai/bar'
      config:
        source: package.json
    - id: group1
      name: cordis:group
      group: true
      config:         
        - id: plugin3
          name: '@jaydenai/baz'
          config:
            source: package.json
        - id: group2
          name: cordis:group
          group: true
          config:         
            - id: plugin4
              name: '@jaydenai/qux'
              config:
                source: package.json
```

以此Profile启动程序后，注册的四个插件会将自身在整个插件树的路径以如下的形式数出来（省略由配置提供的`source`）：

```bash
Loader>Include>foo
Loader>Include>bar
Loader>Include>Group>baz
Loader>Include>Group>Group>qux
```

可以看出所有的插件前面都有`Loader`和`Include`这两个共同的祖先。由于我们输出的是作为插件运行时的`Plugin.Runtime`名称，所以`Loader`和`Include`本质上就是两个**插件**的名称。由于`baz`被至于一个**插件组**中，所有前面出现一个`Group`节点，这意味所谓的插件组本质上也是Cordis的插件。插件`qux`被置于一个**嵌套的插件组**中。所有的这些类型，以及`PatchOptions`的`insert`字段涉及的`EntryOptions`都来源于`@deepseek-ai/cordis-plugin-loader`包。顾名思义，这包用来加载或者重载插件，接下来介绍的绝大部分类型都定义在这个包中。

## 2. 插件树在DSH中的表示

`@deepseek-ai/cordis-plugin-loader`包使用`EntryTree`来表示插件树，而插件树的一个节点通过`Entry`类型表示，另一个`EntryGroup`对象表示插件组。

### 2.1 Entry

一个`Entry`对应前面介绍的一个`EntryOptions`（对应于字段`options`），所以一个`Entry`可能对应一个真正的**插件**，也可能对应一个**插件组**（比如前面实例利用`cordis:group`定义的插件组），甚至可以代表整颗插件树。我们可以利用`parent`字段得到当前`Entry`所在插件组的`EntryGroup`对象。一个`Entry`总是会置于一个`EntryGroup`中，所以它的`parent`字段总是存在。

```typescript
export class Entry {
  static readonly key = Symbol.for('cordis.entry')

  public ctx: Context
  public fiber?: Fiber
  public parent!: EntryGroup
  public options = {} as EntryOptions
  public subgroup?: EntryGroup
  public subtree?: EntryTree

  constructor(public loader: Loader) {
    this.ctx = loader.ctx.extend({ [Entry.key]: this })
    this.context.emit('loader/entry-init', this)
  }
  async init()
}
```

如上面的代码所示，一个`Entry`对象通过指定的`Loader`对象创建而成。在初始化过程中，它会从`Loader`提取当前`Context`，并调用`extend`方法创建一个子`Context`绑定到自身的`ctx`字段上。当前创建的`Entry`会设置为该Context的`Entry.key`（这是一个`Symbol`）字段。值得一提的是，由于Cordis下针对`Context`的动态跟踪能力，同一个`Loader`对象会动态提供当前`Context`，而不是统一提供初始化`Loader`对象时的那个根`Context`，否则岂不就变成了所有插件都注册到同一个根`Context`上了？至于其他三个字段，分别在如下三种场景中被初始化：

- **fiber**： 如果当前`Entry`代表一个插件（`cordis:group`虽然代表一个组，但是对应的`Group`也是一个插件），会在用于初始化的`init`方法中调用`RegistryService`的`plugin`方法完成插件的注册，返回的`Fiber`对象会赋值给它。随后，当前`Entry`会赋值给`Fiber`的`entry`字段。也就是说`Fiber`和`Entry`之间会实现双向绑定；
- **subtree**：在根据`Context`创建`EntryTree`的时候，如果能够利用`Entry.key`从`Context`中提取`Entry`对象，当前的`EntryTree`对象会赋值给`Entry`对象的这个字段，我们就知道它代表一棵完整的插件树；
- **subgroup**：在根据`Context`创建`EntryGroup`的时候，如果能够利用`Entry.key`从`Context`中提取`Entry`对象，当前的`EntryGroup`对象会赋值给`Entry`对象的这个字段，我们就知道它代表一个插件组。

`Entry`还提供如下的属性和方法：

```typescript
export class Entry {
  get context(): Context;
  get id() ;
  get disabled();
  evaluate(expr: string);
  async refresh();
  async update(options: Partial<EntryOptions>, create = false, force = false);
  async init() ;
}
```

上述成员说明如下：

- **context**: 返回`ctx`字段；
- **id**：返回`EntryOptions`的`id`，若父树上下文的`fiber`有`entry`，则用 分隔符`:`拼接父Id前缀，形成层级Id；
- **disabled**: 确定当前条目或其任一祖先对应的`EntryOptions`是否被禁用。插件组永远视为启用状态；
- **evaluate**：在当前`Entry`的上下文中执行表达式，用于求值`!!js`表达式（`EntryOptions`的字段可以使用`!!js`表达式来定义）；
- **refresh**： 如果`fiber`不存在并且不是`disabled`状态，会调用`init`方法来刷新。

`update`是`Entry`类最核心的方法，负责合并新配置、按需重启插件(组)。它的三个参数分别表示为：

- **options**：代表新配置的`EntryOptions`对象的部分字段。`create = true`时它被视为完整`EntryOptions`，否则会与当前配置进行合并；
- **create**：`true`表示直接将指定的`options`直接作为新配置，`false`则表示把`options`合并到旧配置上；
- **force**：即使没有任何字段变化，也强制执行后续流程，即跳过**无差异直接返回**"的短路。

`update`方法之所以如此重要，是因为动态感知并应用变更的插件配置的热重载就是通过它实现的。具体的流程主要分为如下几个阶段：

- **阶段 1**：构造作为候选配置的`EntryOptions`，通过`candidate`表示；
  - 如果`create = true`，`candidate`就是提供的`options`参数；否则从旧配置拷贝，然后逐字段合并`options`，  其中值为`null/undefined`的字段表示删除此字段；
  - 对`candidate`的键排序，保证后续比较和序列化稳定。
- **阶段 2**：计算差异，得到更新的字段名称列表，通过`diff`表示：
  - 深度比较`candidate`和`this.options`并收集发生该表的字段名称集合`diff`;
  - 如果两者完全没有差异且`force`为`false`，直接返回。
- **阶段 3**：按当前`Fiber`状态分四条路径进行处理:
  - 路径 A：如果此前没有运行中的`Fiber`，说明这是首次启动或之前已停止，直接调用`init`方法进行初始化；
  - 路径 B：如果`candidate`被禁用，调用当前`Fiber`的`dispose`方法将其终结；
  - 路径 C：如果变化的字段不包含`name`、`inject`、`group`这三个重要的字段，就不需要重启`Fiber`，直接调用原地打补丁并更新变化的部分即可；
  - 路径 D：若上述三个字段发生改变,会执行如下的流程：
    - 如果`name`字段发生改变，从下面介绍的`EntryTree`对象的`import`方法导入模块，并解包得到新的插件类型。否则可以沿用现有的插件函数；
    - 调用现有的`Fiber`的`dispose`方法；
    - 重新注册插件，并创建新的`Fiber`对象。

在开启热重载开关的情况下，配置的改变最终导致对应`Entry`对象的`update`方法被调用。在完成了状态更新和执行完待清理工作之后，它会重新实施插件注册的工作，前提利用`disabled`属性确定插件并没有被禁用。

### 2.2 EntryTree

表示插件树的`EntryTree`为具有如下定义的抽象类。当`EntryTree`根据指定的`Context`被创建的时候，同样会调用`extend`方法创建一个子`Context`对象，并创建一个`EntryGroup`作为根绑定到`root`字段上。如果当前`Context`中存在一个`Entry`对象，会将自己赋值给它的`subtree`字段。当我们使用`cordis:include`包含另一个补丁文件时，由于会注册对应的`Include`插件(派生自`EntryTree`)，所以它通过`subtree`字段以子树的形式挂在当前`Entry`上。表示整棵树节点的`Entry`对象以字典的形式存储在`store`字段上，`Key`为`Entry`的`id`。`enableLogs`是是否输出诊断日志的开关。

```typescript
export abstract class EntryTree {
  public ctx: Context
  public enableLogs?: boolean
  public root: EntryGroup
  public store: Dict<Entry> = Object.create(null)

  constructor(ctx: Context) {
    this.ctx = ctx.extend({ baseUrl: ctx.baseUrl })
    this.root = new EntryGroup(this.ctx, this)
    const entry = this.ctx.fiber.entry
    if (entry) entry.subtree = this
  }
}
```

`EntryTree`提供了如下众多的属性和方法。

```typescript
export abstract class EntryTree {
  static readonly sep = ':'
  get context(): Context ;
  entries(): Generator<Entry, void, void> ;
  getTasks() ;
  async await() ;
  ensureId(options: Partial<EntryOptions>) ;
  resolve(id: string) ;
  resolveGroup(id: string | null) ;
  async create(options: Omit<EntryOptions, 'id'>, parent: string | null = null, position = Infinity);
  async remove(id: string) ;
  async update(id: string, options: Omit<EntryOptions, 'id' | 'name'>, parent?: string | null, position?: number) 
  import(name: string, getOuterStack?: () => string[]) 
  abstract write(): void
}
```

上述成员说明如下：

- **context**：对`this.ctx`的只读访问器，提供更语义化的别名；
- **entries**：生成器方法，深度优先遍历当前树及其所有嵌套子树中的所有`Entry`。遍历顺序是先当前层的每个`Entry`，若该`Entry`有子树则递归进入。是`getTasks`、`await`等方法的底层依赖；
- **getTasks**：返回当前树及所有子树中待处理的导入任务和生命周期任务；
- **await**：等待整棵树进入稳定状态，这是一个反复收敛的过程，因为等待任务完成可能触发新任务；
- **ensureId**：确保`options.id`存在。若没有，则随机生成一个8位十六进制字符串，并检查当前树`store`中是否已存在，直到不冲突为止，返回最终Id；
- **resolve**：根据Id解析出`Entry`，支持用`EntryTree.sep`分隔的嵌套Id；
- **resolveGroup**：解析出一个`EntryGroup`。若`id`为`null`，返回`this.root`；否则调用`resolve(id)`得到`Entry`，若该`Entry`没有`subgroup`则抛错，否则返回`entry.subgroup`；
- **create**：在指定`EntryGroup`中创建新`Entry`，三个参数分别为：
  - option：不含`id`的`Entry`选项；
  - parent：为父`EntryGroup`的（`null`表示根`EntryGroup`）；
  - position：为插入位置（默认末尾）。
- **remove**：停止并移除一个`Entry`。解析`Entry`后调用`entry.parent.remove(id)`，再调用`entry.parent.tree.write()`持久化；
- **write**：抽象方法，持久化当前树的状态。具体实现由子类提供（例如写入文件系统），内存中的树可以实现为空操作。

在前面介绍`Entry`的`update`方法时我们提到，当`EntryOptions`的`name`字段发生改变，它会调用`EntryTree`的`import`方法导入新的插件类型。具体来说若`name`以`"cordis:"`开头（比如`cordis:include`和`cordis:group`），则利用后面的部分(`include`和`group`)从`this.ctx.loader.builtins`字典中提取对应的对象（`Include`和`Group`插件函数）。若`name`以`"."`开头则用`new URL(name, baseUrl).href`动态`import`；否则直接调用`import(name)`。

`Entry`的`update`是通过`EntryTree`的同名方法驱动执行的。除此之外，`EntryTree`的`update`方法还可以将指定的`Entry`移动到另一个`EntryGroup`。该方法的四个参数分别为：

- **id**： 代操作的目标`Entry`Id；
- **options**： 为要更新的字段（不含`id`和`name`）；
- **parent**：为目标父`EntryGroup`的Id（`undefined`表示不移动）；
- **position**： 为移动后的插入位置/索引。

`EntryTree`的`update`方法会调用`resolve`方法根据参数`id`将目标`Entry`解析出来。如果指定了`parent`，它会调用`resolveGroup`将对应的`EntryGroup`解析出来作为`Entry`的`parent`。随后调用`Entry`的`update`方法实施强制更新(`force`参数被设置成`true`, `create`参数设置成`false`)。不管怎样，作为`Entry`原来`parent`的`EntryGroup`（如果没有转移，和当前一致）总是发生了变化，此时需要调用其`write`方法将新的状态保存起来。如果发生了转移，还会调用新`parent`的`EntryGroup`的`write`方法。

### 2.3 EntryGroup

表示插件组的`EntryGroup`定义如下，包含其中的`Entry`对象的`EntryOptions`被添加到`data`字段返回的列表中。创建`EntryGroup`时总是会指定当前`Context`和他所属的`EntryTree`。构造函数不会创建子`Context`，如果`Context`中包含`Entry`，当前对象将会赋值到它的`subgroup`字段上，表明当前`Entry`是一个子插件组。指定的`Context`和`EntryTree`被直接绑定到`ctx`和`tree`字段上。

```typescript
export class EntryGroup {
  public data: EntryOptions[] = []
  constructor(public ctx: Context, public tree: EntryTree) {
    const entry = ctx.fiber.entry
    if (entry) entry.subgroup = this
  }
}
```

`EntryGroup`提供了如下众多的属性和方法。

```typescript
export class EntryGroup {
  static readonly key = Symbol.for('cordis.group');
  get context(): Context ;
  async create(options: Omit<EntryOptions, 'id'>) ;
  unlink(options: EntryOptions) ;
  async remove(id: string, isDispose = false) ;
  async update(config: EntryOptions[]) ;
  async stop() ;
}
```

上述成员说明如下：

- **key**：插件和组对于Cordis来说都是插件，所以提供静态自读字段`key`来区分插件组；
- **context**：对 `this.ctx`的只读访问器，提供更语义化的别名；
- **create**：在`EntryGroup`内创建一个`Entry`，返回`Entry`的Id。由于调用构造函数时使用的是`tree`字段返回的`EntryTree`，所以创建的`Entry`会存储到当前`EntryTree`的`store`字典中。指定的options将会作为参数调用`Entry`的`update`方法实施更新；
- **unlink**：从`data`中移除指定的 `EntryOptions`；
- **remove**：移除指定Id的`Entry`。具体的操作包括从`EntryTree`的`store`字段中将`id`标识的`Entry`移除，并通过回收`Entry`调用绑定`Fiber`对象的`dispose`方法。
- **update**：用新的配置数组整体更新`EntryGroup`,最终的更新本质上是便利每个`EntryOptions`，并将其作为参数调用`create`方法完成的。在将`options`赋值给`data`字段之前，对于原来包含在`data`中，但在`options`中缺失的`EntryOptions`，会调用`remove`方法将对应的`Entry`移除并实施清理；
- **stop**：停止当前`EntryGroup`中的所有`Entry`。遍历 `this.data`，对每个`options.id`调用`this.remove(options.id, true)`。

### 2.4 Group

还记得演示实例中输出的插件路径吗（比如`Loader>Include>Group>Group>qux`），作为路径节点的`Group`对应的插件类型就是如下这个同名类型。从构造函数可以看出，`Group`插件的配置是一个`EntryOptions`的列表。按照基类的构造函数的逻辑，当前`Group`对象会赋值给当前`Entry`的`subgroup`字段，我们便知道当前`Entry`表示一个插件组。`Group`通过静态字段`EntryGroup.key`会设置为`true`，也是强调这个作为插件代表一个插件组。随后它通过订阅内部事件`internal/update`，通过调用`update`方法将更新的插件配置（一组`EntryOptions`对象）应用到内嵌的插件上。

```typescript
export class Group extends EntryGroup {
  static initial: Omit<EntryOptions, 'id'>[] = []
  static readonly [EntryGroup.key] = true

  constructor(public ctx: Context, public config: EntryOptions[]) {
    super(ctx, ctx.fiber.entry!.parent.tree)
    ctx.on('internal/update', config => this.update(config))
  }

  async* [Service.init]() {
    yield () => this.stop()
    await this.update(this.config)
  }
}
```

对于这种以类型注册的插件，最终会调用`symbols.init`（`Service.init`引用同一个`Symbol`）方法并将其返回的函数作为卸载时的清理函数。可以看出`Group`在这样的方法利用`yield`返回了一个生成器，意味着初始化的时候会调用`update`完成了针对初始配置的应用，在卸载时则会调用`stop`方法。

## 3. Include插件

从演示实例中输出的插件路径（比如`Loader>Include>Group>Group>qux`）可知，通过在各种形式的补丁文件中注册的插件都位于在`Include`插件对应的`Context`内部。换句话说，它们本质上都是通过`Incude`插件负责注册和维护。我们在[DeepSeek Harness深度拆解-04:完整的插件配置树如何构建？](https://blog.csdn.net/JaydenAI/article/details/165428487)演示了通过将`PatchOptions`的`name`字段设置为`cordis:include`，并将定义在另一个补丁文件构建的插件树包含进来，此时创建的就是`Include`插件。顾名思义，`Include`插件存在的目的就是为直接**将在指定的插件树包含进来**，它具有如下这个专属的配置类型。

```typescript
export namespace Include {
  export interface Config {
    path: string
    initial?: any[]
    patches?: PatchOptions[]
    enableLogs?: boolean
  }
}
```

`Include.Config`接口定义的四个配置选项说明如下：

- **path**：提供的用来构建插件树的补丁文件路径，对应的文件可以是`yaml`和可以是`json`；
- **initial**：如果`path`指定的文件不存在，就先在该路径创建文件，并把`initial`定义的列表作为初始数据写入这个文件。随后再重新读取该文件并应用；
- **patches**：在文件原始数据之上做增量修改，读取后叠加的运行时补丁；
- **enableLogs**：诊断日志输出开关。

我抽取出定义在`Include`中的几个核心成员来介绍这个插件的执行流程。当构造函数执行的时候，会从作为配置的`Include.Config`对象中提取补丁文件的路径，并结合`Context`的`baseUrl`解析出文件的路径作为`filename`字段，然后转换成`file:///`形式的URL设置到当前`Context`的`baseUrl`字段上。接下来它通过订阅`internal/update`事件应用更新的配置。为了避免并发操作带来的问题，`Include`将更新操作转换成Task添加到**队列**中，然后以串行的方式依次执行它们保证状态的一致性。具体来说，它利用`applyPatches`方法通过比较现有的`EntryOptions`（对应`data`字段）和当前更新的`EntryOptions`，最终提取出需要更新的`EntryOptions`列表，通过调用作为根的`EntryGroup`对象(对应`EntryTree`的`root`字段)的`update`方法实施更新。

```typescript
export class Include extends EntryTree {
  private data?: EntryOptions[]
  public filename: string
  constructor(ctx: Context, public config: Include.Config) {
    super(ctx)
    this.filename = fileURLToPath(new URL(this.config.path, this.ctx.baseUrl))
    ...
    this.ctx.baseUrl = new URL('.', pathToFileURL(this.filename)).href

    ctx.on('internal/update', async (config, _, next) => {
      if (config.path !== this.config.path) return next()
      await this.enqueue(async () => {
        const data = this.applyPatches(this.data!, config.patches)
        await this.root.update(data)
        this.config = config
      })
    })
  }

  async* [Service.init]() {
    let candidate: ReadCandidate
    try {
      candidate = (await this.read(true))!
    } catch (error) {
      if (!(error instanceof ConfigFileError) || error.stage !== 'read' || (error.cause as NodeJS.ErrnoException)?.code !== 'ENOENT') throw error
      if (this.config.initial) {
        await this._writeFile(this.config.initial as any)
        candidate = (await this.read(true))!
      } else {
        throw new Error(`config file not found: ${this.filename}`)
      }
    }

    yield () => this.stop()
    await this.apply(candidate)
  }
  async stop()
  private apply(candidate: ReadCandidate)
  private applyPatches(data: EntryOptions[], patches?: PatchOptions[]): EntryOptions[]
  private enqueue<T>(task: () => Promise<T>): Promise<T> 
}

interface ReadCandidate {
  content: string
  data: EntryOptions[]
}
```

在通过常量`Service.init`定义的初始化方法中，它会读取指定的补丁文件，并转换成`ReadCandidate`对象。接下来该对象作为参数调用`apply`方法，后者会调用作为根的`EntryGroup`对象的`update`方法将配置转换成真正的插件体系。

## 4. Loader

`Loader`应该算是DSH加载的第一个插件，它和上面介绍的`Include`一样，都是对`EntryTree`的扩展，所以它本质上可以表示一棵**插件树**。它同时也作为Cordis的一个基础服务。

### 4.1 配置

作为一个插件，`Loader`使用如下所示的`Loader.Config`接口来表示插件配置。该接口有定义了唯一的可选字段`baseUrl`，用于解析相对插件说明符和配置文件路径，通常是`file://`协议的URL或目录路径。`baseUrl`是整个加载体系的路径锚点。没有它，相对路径的插件和配置都无从解析。它是可选的原因是，如果所有插件说明符和配置路径都是绝对路径（或包名），就不需要它。

```typescript
export namespace Loader {
  export interface Config {
    baseUrl?: string
  }
  export interface Intercept {
    await?: boolean
  }
}
```

作为服务，`Loader`使用如下这个`Loader.Intercept`接口来表示服务配置。如果注入此服务的插件在`Loader`启动期间使用它，此时它管理的`Entry`可能还在陆续被导入和初始化，就可能读到不完整的插件树。为了解决这个问题，我们可以将`Intercept`的`await`字段设置为`true`，那么依赖方要就会`Loader`的所有`Entry`加载完成后，才会将状态从`Pending`变为`Active`。如下面的代码所示，`Loader`将`Loader.Intercept`声明通过`Service.config`（`Symbol`类型的常量）标识的服务配置。

```typescript
export class Loader extends EntryTree {
  declare [Service.config]: Loader.Intercept
  ...
}
```

### 4.2 初始化

`Loader`利用`name`字段将自身命名为`loader`。它的`builtins`字段是一个字典，前面我们介绍`Entry`的`update`方法时，我们说倘若提供的`EntryOptions`改变了表示插件名的`name`字段，并且`name`以`cordis:`作为前缀，它会将提出此前缀的名称作为`Key`，并利用它尝试从`ctx.loader.builtins`字典中提取预定义的插件。这个字典就指向`Loader`的`builtins`字段，DSH启动过程中会在这个字典中添加两个映射，Key分别为`include`和`group`，对应的值分别为前面介绍的`Include`和`Group`类型。这就是为什么补丁文件定义的`PatchOptions`/`EntryOptions`在将`name`字段设置成`cordis:includ`e和`cordis:group`，会自动注册`Include`和`Group`插件的原因。

```typescript
export class Loader extends EntryTree {
  public name = 'loader'
  public builtins: Dict<any> = Object.create(null)
  constructor(ctx: Context, public config: Loader.Config = {}) {
    super(ctx)
    if (config.baseUrl) {
      this.ctx.baseUrl = config.baseUrl
    }
    const self = this

    defineProperty(this, Service.tracker, {
      associate: 'loader',
      property: 'ctx',
      noShadow: true,
    })

    ctx.reflect.provide('loader', this, this[Service.check])   
    ...
    ctx.plugin(isolate)
  }

    [Service.check]() {
    const config: Loader.Intercept = Service.prototype[Service.resolveConfig].call(this)
    if (config.await && this.getTasks().length) return false
    return true
  }
}
```

在`Loader`的构造函数被执行的时候，如果提供的`Loader.Config`对象的`baseUrl`进行了设置，该URL将会赋值给当前的`Context`。我们之所以说`Loader`具有插件和服务双重角色，是因为它在构造函数中通过调用`ReflectService`的`provide`方法将自己注册为命名为`loader`的服务。服务注册的状态检验函数对应通过`Service.check`这个`Symbol`标识的方法，从其定义可以印证了前面介绍的作为服务配置的`Loader.Intercept`的`await`字段的作用。由于它将`Service.tracker`进行了如下的设置，意味着当我们在注入了`loader`服务的插件中针对`ctx.loader.XXX`这种形式的调用，将会自动转发给`Loader`对象，并且不会受影子上下文的干扰：

- **associate**：loader；
- **property**：ctx；
- **noShadow**：true

在构造函数的最后，它会注册一个通过`isolate`函数表示的插件。篇幅所限，这里就不对此插件的定义进行单独介绍了，我们只需了解它的作用是为为每个`Entry`安装上下文拦截（`intercept`）与隔离（`isolate`）机制，让不同 `Entry`可以拥有各自独立的服务实例，并在运行时安全地切换、重载、回收这些服务绑定。一句话概括：它让`EntryOptions`的`intercept`和`isolate`两个配置项真正生效。

构造函数在完成服务注册之后还会执行四个针对Cordis事件总线的订阅：

- **internal/config**：当某个插件上线（`Fiber`被激活），插件配置如果包含`!!js`表达式（比如`{greeting: !!js process.env.GREETING}`），订阅的处理器会调用`interpolate`方法针对当前`Context`进行插值处理，即对表达式求值让插件能够得到真实的值(`!!js process.env.GREETING`会被替换成对应环境变量的值)；
- **internal/update**：前置的处理函数将`Fiber`对应的插件配置更新应用到对应的`Entry`(`options.config`)上，并持久化配置树，后置的处理器单纯用来输出对应的诊断日志；
- **internal/plugin**：将`Entry`附加到新注册插件对应的`Fiber`上，并将`Fiber`注入服务的配置应用到`Entry`对象上，最后针对`Fiber.dispose`方法的调用（排除其他场景），禁用对应的`Entry`并持久化配置树。

```typescript
export class Loader extends EntryTree {
  constructor(ctx: Context, public config: Loader.Config = {}) {
    ...
    ctx.on('internal/config', function (this: Fiber, _config, next) {
      const config = next()
      if (!this.entry || this.parent.fiber?.entry === this.entry) return config
      const plugin = this.runtime?.callback as Record<PropertyKey, unknown> | undefined
      if (plugin?.[EntryGroup.key]) return config
      return interpolate(this.ctx, config)
    }, { global: true })

    ctx.on('internal/update', async function (config, noSave, next) {
      if (!this.entry || noSave || this.parent.fiber?.entry === this.entry) return next()
      await next()
      const unparse = this.runtime?.Config?.['simplify']
      this.entry.options.config = unparse ? unparse(config) : config
      this.entry.parent.tree.write()
    }, { global: true, prepend: true })

    ctx.on('internal/update', function (config, _, next) {
      if (!this.entry || this.parent.fiber?.entry === this.entry) return next()
      self.showLog(this.entry, 'reload')
      return next()
    }, { global: true })

    ctx.on('internal/plugin', (fiber) => {
      if (fiber.parent[Entry.key] && !fiber.entry) {
        fiber.entry = fiber.parent[Entry.key]
        Inject.resolve(fiber.entry!.options.inject, fiber.inject)
      }

      // 2. handle self-dispose
      // We only care about `ctx.fiber.dispose()`, so we need to filter out other cases.
      // case 1: fiber is created
      if (fiber.uid) return

      // case 2: fiber is not tracked by loader
      if (!fiber.entry) return

      // case 3: fiber is a child plugin under the entry (not the entry's root fiber)
      if (fiber.parent.fiber?.entry === fiber.entry) return

      // case 4: fiber is disposed on behalf of plugin deletion (such as plugin hmr)
      // self-dispose: ctx.fiber.dispose() -> fiber / runtime dispose -> delete(plugin)
      // plugin hmr: delete(plugin) -> runtime dispose -> fiber dispose
      if (!ctx.registry.has(fiber.runtime!.callback)) return

      // case 5: the entry's tree is being disposed
      const treeOwner = fiber.entry.parent.tree.ctx.fiber
      if (!treeOwner.uid || treeOwner.state === FiberState.UNLOADING) return

      // case 6: Loader is replacing or removing this exact fiber
      if (fiber.entry._disposing) return

      this.showLog(fiber.entry, 'unload')

      // case 7: fiber is disposed by loader behavior
      // such as inject checker, config file update, ancestor group disable
      if (fiber.entry.disabled) return

      fiber.entry.options.disabled = true
      fiber.entry.parent.tree.write()
    })
    ctx.plugin(isolate)
  }
}
```

## 5. 从启动流程插件的注册

当我们以指定的Profile启动DSH时，内部会执行如下这个`runProfile`函数。这个函数很复杂，我们只截取了能够简单表达插件树加载、注册和热重载相关部分的代码。在构建出`ComposedProfile`对象之后，它按照预定义的顺序将四组`PatchOptions`列表组合在一起，这些内容在前面几篇文章中有消息的介绍。接下来就是将它们与Profile所在`cordis.yaml`文件的路径作为参数调用`boot`函数启动DSH，并得到根`Context`。

export async function runProfile(options: RunProfileOptions): Promise<{ ctx: Context; shutdown: ProcessShutdown }> {

DSH正常启动之后，如果`patchReload`配置选项被设置为`live`，它会启动热重载功能。如果缺少热重载两个必要的服务（`hmr`和`timer`），会调用`Loader`的`create`方法创建它们。最后利用`watchUserPatches`方法分别监控Profile补丁文件和DSH运行时根目录补丁文件，一旦文件发生更新，将及时应用到DSH上。对于真正启动DSH的`boot`函数，我们也仅仅列出能够说明大致流程的代码。从下面给出的代码片段可以看出，它会创建并最终返回的根`Context`，然后将`Loader`注册为它的第一个插件，这就是为什么前面演示实例中打印出的每个插件路径都以`Loader`居首的根源所在。

```typescript
export async function boot(
  binName: string,
  absoluteConfigPath: string,
  patches?: PatchOptions[],
  prepare?: (ctx: Context) => Promise<void> | void,
  bareModuleBaseUrl?: string,
): Promise<Context> {
  const ctx = new Context()
  ...
  try {
    ...
    await ctx.plugin(Loader)
    ...
    await mountRootInclude(ctx, absoluteConfigPath, patches, bareModuleBaseUrl)
    await ctx.get('loader')?.await()
    if (ctx.get('loader') === undefined) return ctx
    await assertEntriesActivated(ctx, binName)
    return ctx
  } catch (cause) {
    ...
}
```

插件注册的核心实现在`mountRootInclude`函数。正如我们在前面多次提到的，`Include`和`Group`这两个特殊的插件类型会被注册到`Loader`的`builtins`字典上，对应的Key正是`include`和`group`，所以我们才能以`cordis:group`创建插件组，利用`cordis:include`包含补丁文件。

```typescript
export async function mountRootInclude(
  ctx: Context,
  absoluteConfigPath: string,
  patches: readonly PatchOptions[] = [],
  bareModuleBaseUrl?: string,
): Promise<Entry | undefined> {
  ctx.loader.builtins.include = bareModuleBaseUrl === undefined
    ? Include
    : class HostResolvedRootInclude extends Include {
      ...
      }
    }

  ctx.loader.builtins.group = Group

  const includeConfig: Include.Config = {
    path: pathToFileURL(absoluteConfigPath).href,
    ...patches.length > 0 ? { patches: [...patches] } : {},
  }
  const rootInclude: EntryOptions = {
    id: 'include',
    name: 'cordis:include',
    config: includeConfig,
  }
  const includeId = await ctx.loader.create(rootInclude)
  const loader = ctx.get('loader')
  if (loader === undefined) return undefined
  const entry = loader.resolve(includeId)
  bootstrapIncludes.set(ctx, entry)
  return entry
}
```

接下来一个`Include.Config`被创建出来，它的`path`字典正是当前`Profile`下的`cordis.yaml`文件的绝对路径（该文件内容一般为一个空数据）和所有的`PathOptions`列表。随后以这个`Include.Config`作为`config`创建了一个`EntryOptions`，其`id`和`name`分别为`include`和`cordis:include`。这个`EntryOptions`会作为参数传入`Loader`对象的`create`在根上创建一个`Entry`对象。按照我们熟知的逻辑，由于`EntryOptions`的`name`字段为`cordis:include`,最终会注册`Include`插件。而`Include`插件自身是扩展`EntryTree`的一棵插件树，所以它在初始化过程中整颗插件树被真正构建出来。所有`Include`是在`Loader`之下注册的第二个插件，演示程序输出的路径也体现了这一点。
