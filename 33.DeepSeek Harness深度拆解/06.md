# [DeepSeek Harness深度拆解-06]在自定义插件中体现LLM的动态路由

DSH本质是一个Agent开发框架，**Agent = LLM + Harness**，所以作为Agent大脑的LLM永远是最重要的部件。DeepSeek Harness针对LLM的设计体现在它针对LLM的动态路由上：我们可以配置针对不同厂商的不同模型，并根据提供的输入动态选择对应的LLM发起调用。接下来我们就来体验一下这个特性。至于LLM动态路由的实现原理，在[下一篇](https://jaydenai.blog.csdn.net/article/details/166202277)提供了详细介绍。

## 1. LLM是Cordis的一个服务

`@deepseek-ai/dsh-llm`中针对`Conext`接口定义了如下这个针对`llm`字段的声明，对应类型为`LlmRuntime`。`LlmRuntime`是一个类，它扩展自`TypertRemoteService`抽象类，后者则扩展了作为服务的基类`Service`。`TypertRemoteService`是针对**Typert**的远程服务基类，我们可以通过派生这个类型定义一些可需要远程访问的RPC，为需要做的就是在对应的方法上标注`@Remote`装饰器，Typert会根据这个装饰器为我们生成RPC承载相关的代码和用来调用RPC的客户端代码。如果插件需要为浏览器端提供远程服务，就需要采用这种方式。`LlmRuntime`定义的`listProviders`和`listConfigurableProviders`方法是为了让我们以`web`Profile启动DSH时，能够在LLM配置界面中看到已经激活和候选的LLM供应商。

```typescript
declare module '@deepseek-ai/cordis' {
  interface Context {
    llm: LlmRuntime
  }
}

export class LlmRuntime extends TypertRemoteService { 
  constructor(ctx: Context) {
    super(ctx, 'llm')
  }

  @Remote
  listProviders(): LlmProviderInfo[] {
    return [...this.adapters.values()].map(({ provider }) => ({ ...provider }))
  }

  @Remote
  listConfigurableProviders(): LlmConfigurableProvider[] {
    return [...this.directory.values()].map(entry => ({ ...entry, settingsPath: [...entry.settingsPath] }))
  }
}
```

在`LlmRuntime`的构造函数中，通过调用基类的构造函数以名称`llm`进行了注册，上面为`Context`声明的`llm`字段就指向此服务。和其他Agent框架一样，所谓的LLM本质上是一个用来调用LLM API的代理对象。考虑到针对`LLM`的调用大多是耗时操作，采用流式消息交换的方式无疑是更好的选择，不然我们就看不到所有Agent上逐字输出的效果了。`LlmRuntime`亦是如此，具体体现如下这个`stream`方法中。针对`stream`方法输入和输出类型，以及其他成员的介绍，我们将在后续文章中提供，现在我们知道这么多就可以了。

```typescript
export class LlmRuntime extends TypertRemoteService { 
    stream(options: GenerateOptions): AsyncIterable<StreamChunk>
}
```

## 2. 在一个插件中调用LLM

既然LLM以服务的形式被注册到`Context`上，我们就能够将它注入到自定义的插件中进行消费。为了能够采用一种单纯的方式启动DSH，不采用`web`和`headless`作为Profile，而是采用我们自己定义的一个名为`basic`的Profile，这个Profile的创建方式很简单，直接在拷贝`$DSH_HOME/profiles/web`，并将目录名称改为`basic`，然后按照如下方式修改`package.json`：除了修改`name`字段外，我们还剔除`@deepseek-ai/dsh-web-app`这个包，只保留最基础的`@deepseek-ai/dsh-base`包。

```json
{
  "name": "dsh-profile-basic",
  "private": true,
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base"
      ],
      "patchReload": "live"
    }
  }
}
```

为了便于Debug，我们依然采用源码的方式启动DSH。我们在根目录上创建一个名为`./explor`的目录，并在其中定义插件和对应的补丁文件，具体的目录结构为：

```markdown
./explor
├── src
|   └── llm_explor.ts
├── cordis.patch.yml
├── package.json
└── tsconfig.json
```

`./explor/src/llm_explor.ts`定义了如下这个名为`llm_explor`的插件。插件函数很简单，我们以指定的提示词创建了一个角色为`user`的消息，并封装成`GenerateOptions`对象，其中指定了模型及其供应商。我们将其作为参数调用`ctx.llm`的`stream`方法，并以异步的形式遍历接收到的`StreamChunk`，并并输出其内容。

```typescript
import { Context } from '@deepseek-ai/cordis'
import { GenerateOptions,createUserMessage, UserMessage } from '@deepseek-ai/dsh-llm'
import { error } from 'console'

export const name = "llm_explor"
export async function apply(ctx:Context){    
    const prompt = "鉴于管仲更多地被作为一个名臣的形象被数值，是否导致《管子》一书的价值被远远低估？"
    const message: UserMessage = createUserMessage({
      content: [{ type: 'text', text: prompt }],
      source: { kind: 'user' },
    })
    const options: GenerateOptions = {
        provider: "deepseek-official",
        model:"deepseek-v4-pro",
        messages:[message]        
    }

    for await (const chunk of ctx.llm.stream(options)){
        if(chunk.type == "text-delta"){
            process.stdout.write(chunk.text)
        }
        else if (chunk.type == "finish" && chunk.reason.kind == "error"){
           console.log(chunk.reason.failure.message)
           return
        }
    }
}
```

对应的插件补丁文件`./explor/cordis.patch.yml`定义如下，我们直接`llm_explor.ts`的绝对路径设置为`name`。由于Cordis采用只有显式注入后才能服务消费的原则，我们利用`inject`注入的`llm`服务。照理说`credentials`本不需要注入，但是插件执行的无序性（插件只能依赖服务，确保所有依赖服务全员上下文才会执行）会导致当我注册的插件在执行的时候，对应的LLM适配器还没有注册。由于LLM适配器注册都会使用`credentials`服务提供凭证，不得以添加了这个注入来**延迟执行**。

```yaml
- insert:
  - id: llm_explor
    name: 'E:\dsh\deepseek-harness\explor\src\llm_explor.ts'
    inject: ['llm','credentials']
```

## 5. GenerateOptions

调用`LlmRuntime`的`stream`方法代表一次针对LLM的调用，作为输入的`GenerateOptions`是一个**单次模型请求**的完整参数对象，调用LLM时把所有需要的信息打包成一个`GenerateOptions`对象。由于`GenerateOptions`是对调用抽象化LLm请求的定义，所以每个Agent框架中你都会发现这些熟悉的字段。

```typescript
export interface GenerateOptions {
  provider: string
  model: string
  reasoningEffort?: ReasoningEffortId
  messages: Message[]
  system?: string
  tools?: ToolSchema[]
  temperature?: number
  maxTokens?: number
  stop?: string[]
  signal?: AbortSignal
  sessionId?: Branded<'SessionId'>
  purpose?: 'compaction' | 'session-title'
}
```

各种字段成员说明如下：

- **provider**：已注册的针对不同LLM提供商的路由名，用来选择具体的适配器实例；
- **model**：具体要调用的模型名；
- **reasoningEffort**：针对当前这个模型选择的推理强度（由适配器自己定义可选值）；
- **messages**：作为核心输入的代表对话历史的消息列表，
- **system**：系统提示词；
- **tools**：可用工具的Schema；
- **temperature**：采样温度，控制随机性；
- **maxTokens**：最大生成Token数；
- **stop**：停止序列。模型一旦生成其中任一字符串就立即停止，且该字符串本身不会出现在输出中；
- **signal**：用于取消/中止本次请求的信号；
- **sessionId**：将多次对话纳入同一个Session的ID；
- **purpose**：对辅助模型调用的、与provider无关的分类。适配器可据此映射为隐藏元数据或专门的生成策略。目前仅两种取值：
  -`'compaction'`：压缩（如上下文压缩）；
  -`'session-title'`：生成会话标题。

`reasoningEffort`和`sessionId`字段返回的`ReasoningEffortId`和`Branded<T>`类型定义如下。`Branded<'X'>`本质是`string`，但类型系统把它当作一个带独特标记的字符串，从而让编译器帮你区分语义不同、底层相同的值，把运行时的字符串升级成**编译期的强约束标识符**。`tools`字段返回一个`ToolSchema`列表来描述工具的名称和参数结构。

```typescript
export type ReasoningEffortId = Branded<'ReasoningEffortId'>
declare const BRAND: unique symbol
export type Branded<B extends string> = string & { readonly [BRAND]: B }

export interface ToolSchema {
  name: string
  description: string
  parameters: Record<string, unknown>
}
```

## 6. 消息系统

由于LLM采用绑定到某种角色的消息来组织对话，作为对话历史的消息列表作用LLM最重要的输入，所以和其他Agent框架一样，DSH也定义了对应的类型来描述各种消息。如下是最基本的`Message`接口的定义：

```typescript
export interface Message {
  readonly id: MessageId
  readonly role: 'system' | 'user' | 'assistant'
  readonly content: ContentBlock[]
  readonly source: MessageSource
}
export type MessageId = Branded<'MessageId'>
```

四个字段说明如下：

- **id**：消息的唯一标识，类型为`Branded<'MessageId'>`；
- **role**：消息绑定的三种角色；
- **content**：消息的内容列表；
- **source**：消息的来源。

### 6.1 消息的来源

`Message`的`source`字段表达的概念在很多Agent框架中是没有的，它返回类型为`MessageSource`，体现了四种典型的消息来源：用户输入、插件生成、模型响应和工具执行结果。

```typescript
export type MessageSource = MessageSourceMap[keyof MessageSourceMap]
export interface MessageSourceMap {
  user: { kind: 'user' }
  plugin: { kind: 'plugin'; plugin: string } & ContextFormed
  model: ModelMessageSource
  tool: ToolMessageSource
}
export interface ModelMessageSource extends AssistantProvenance {
  kind: 'model'
}

export interface ToolMessageSource {
  kind: 'tool'
  callId: ToolCallId
}
export type ToolCallId = Branded<'ToolCallId'>
```

### 6.2 消息的内容

消息的荷载内容通过一组`ContentBlock`列表。`ContentBlock`类型定义如下，它是六种具体的`ContentBlock`类型的联合。

```typescript
export type ContentBlock = ContentBlockMap[ContentBlockType]
export type ContentBlockType = keyof ContentBlockMap
export interface ContentBlockMap {
  'text': TextBlock
  'reasoning': ReasoningBlock
  'image': ImageBlock
  'file': FileBlock
  'tool-call': ToolCallBlock
  'tool-result': ToolResultBlock
}

export interface TextBlock {
  type: 'text'
  text: string
}
export interface ReasoningBlock {
  type: 'reasoning'
  text: string
}
export interface ImageBlock {
  type: 'image'

}

}

```

六种具体的`ContentBlock`类型简单说明如下：

- **TextBlock**：单纯的文本内容；
- **ReasoningBlock**： 专门指LLM推理的文本内容；
- **ImageBlock**：图片内容；
- **FileBlock**： 任意文件内容；
- **ToolCallBlock**：LLM响应的工具调用内容；
- **ToolResultBlock**：工具执行后的结果内容。

### 6.3 各种具体消息类型

除了`Message`这个表示消息的基本接口，DSH还定义了`UserMessage`、`AssistantMessage`和`SystemMessage`三个针对`user`、`assistant`和`system`三种角色的消息类型。同样采用`user`作为角色，`ToolResultMessage`表示携带工具执行结果的消息。

## 7. StreamChunk

`LlmRuntime`的`stream`方法通过返回的`AsyncIterable<StreamChunk>`以流的形式实时返回LLM生成的内容。`StreamChunk`是一个很典型的 流式事件**判别联合类型（discriminated union）**。它描述的是一条消息在逐步生成的过程中，后端往前端（或模型往调用方）吐出来的一个个片段。

```typescript
export type StreamChunk =
  | { type: 'block-start'; index: number; blockType: ContentBlockType }
  | { type: 'text-delta'; index: number; text: string }
  | { type: 'reasoning-delta'; index: number; text: string }
  | { type: 'tool-call-delta'; index: number; id: ToolCallId; name?: string; argumentsDelta: string }
  | { type: 'block-end'; index: number; block: ContentBlock }
  | { type: 'usage'; usage: TokenUsage }
  | {
    type: 'finish'
    reason: FinishReason
    replayState?: ReplayEnvelope
  }

export interface ReplayEnvelope {
  response: unknown
  blocks?: readonly unknown[]
}
```

六种以type字段区分的具体片段说明如下：

- **block-start**： 一个内容块开始；
- **text-delta**： 模型在逐字逐句生成正文，每生成一小段就发一个`text-delta`。前端把这些 text 追加到第`index`个块后面，就形成了打字机效果；
- **reasoning-delta**： 模型在逐字逐句生成推理内容（如思维链），每生成一小段就发一个`reasoning-delta`。结构与`text-delta`相同，但语义上属于**思考过程**而非最终回答，前端通常把推理内容单独折叠渲染；
- **tool-call-delta**： 模型决定调用工具，工具调用的参数被一点点拼出来，每拼出一小段就发一个`tool-call-delta`。携带`id`（工具调用标识）、`name?`（工具名，可能先到或后到）和`argumentsDelta`，前端需要把这些增量累加，最后拼成完整参数；
- **block-end**： 某个块结束，携带`index`和这个块**最终成型**的完整内容块。作用是兜底/校正—，用权威的完整内容块覆盖前面拼出来的碎片，避免拼接出错；
- **usage**： 用量统计，Token耗用的统计信息。和内容无关，是计费/监控用的元数据，可能出现在流的中途，也可能在结尾；
- **finish**： 整个流结束，携带`reason`（为什么结束，如正常结束、达到长度上限、工具调用、内容过滤等）和可选的`replayState`（重放状态，用于记录/重放这次生成的上下文）。收到它就说明不会再有内容了，这是流的终止事件；

`usage`类型的片段利用同名字段返回如下这个`TokenUsage`对象输出各种类型的耗用的统计信息。

```typescript
export interface TokenUsage {
  inputTokens: number
  outputTokens: number
  totalTokens?: number
  cacheReadTokens?: number
  cacheWriteTokens?: number
  reasoningTokens?: number
}
```

`finish`类型的片段利用`reason`字段返回如下这个`FinishReason`对象返回如下5种导致输出流结束的原因：

```typescript
export interface FinishReasonMap {
  'stop': { kind: 'stop' }
  'tool-calls': { kind: 'tool-calls' }
  'max-tokens': { kind: 'max-tokens' }
  'aborted': { kind: 'aborted'; failure: LlmFailure }
  'error': { kind: 'error'; failure: LlmFailure }
}

export type FinishReason = FinishReasonMap[keyof FinishReasonMap]
```

五种原因说明如下：

- **stop**： 模型自然结束生成，正常说完了想说的话，这是最常见的结束原因；
- **length**： 达到了最大 token 长度限制，模型还没说完就被强制截断，输出可能不完整；
- **tool-calls**： 模型决定调用工具，本轮生成暂停，等工具执行完拿到结果后再继续下一轮生成；
- **content-filter**： 内容被安全/合规过滤器拦截，输出被中断，通常伴随拒答或截断；
- **error**： 生成过程中发生错误（如上游服务异常、超时、解析失败等），流被异常终止，属于非正常结束。
