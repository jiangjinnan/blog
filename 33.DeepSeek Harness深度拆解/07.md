# [DeepSeek Harness深度拆解-07]LLM的动态路由实现原理揭秘

[DeepSeek Harness深度拆解-06:体验DSH针对LLM的动态路由](https://jaydenai.blog.csdn.net/article/details/166201752)我们通过在自定义的插件调用`LlmRuntime`服务，并通过修改`GenerateOptions`的方式实现针对LLM的切换，这就是DSH被称为**动态LLM路由**的特性，接下来我们就来介绍一下这一重要特性是如何实现的。实际上整个LLM路由就实现在`LlmRuntime`这个类型中，虽然该类型定义了很多方法，但是其核心体现在如下所示的三个字段上。

```typescript
export class LlmRuntime extends Service {
  private adapters = new Map<string, AdapterRegistration>()
  private directory = new Map<string, LlmConfigurableProvider>()
  private discoveries = new Map<string,(request: LlmModelDiscoveryRequest) => Promise<readonly LlmDiscoveredModel[]>>()
}
```

我们简单地概括一下三个`Map`类型字段的作用：

- **adapters**：注册不同LLM供应商实现的LLM适配器；
- **directory**: 登记系统里有哪些供应商可以被用户配置。当我们以`web`的方式启动DSH时，用户在前端配置LLM供应商时看到的供应商列表就来源于这里；
- **discoveries**：LLM发现函数表。登记怎么动态发现某个供应商有哪些可用模型。因为很多供应商的模型列表是运行时才能拿到的，所以这里等级的是函数而不是静态数据。

## 1. LLM供应商目录

我们先从简单的LLM供应商目录说起，也就是`directory`字段返回的值类型为`LlmConfigurableProvider`的字典。`LlmConfigurableProvider`这个接口利用如下的字段描述了LLM供应商的基本信息。

```typescript
export interface LlmConfigurableProvider {
  provider: string
  displayName: string
  settingsNs: string
  settingsPath: readonly string[]
  declared?: boolean
  error?: string
}
```

各字段说明如下：

- **provider**：供应商标识，同时作为LLM路由的Key；
- **displayName**：供应商显示名称；
- **settingsNs**：供应商配置所在的命名空间，避免key冲突；
- **settingsPath**：从命名空间的根到这个供应商的配置对象的路径；
- **declared**：是否被显式声明。表达的意思是拥有这条路由的适配器，是不是仅仅因为配置声明了它，才知道它存在：
  - `true` ：适配器仅仅因为配置才知道它；
  - `false`：适配器出厂就带这条路由，不是用户配置声明的;
  - `undefined`:适配器根本不关心路由是自带的还是配置声明的，它不做这个区分。
- **error**：一条配置诊断信息。表示这条供应商路由的配置有问题，但不代表整个供应商彻底不可用。

`LlmRuntime`定义了如下两个与之相关的方法，`registerConfigurableProviders`方法用来提供针对`LlmConfigurableProvider`注册，`listConfigurableProviders`方法则负责将注册的`LlmConfigurableProvider`列出来。`registerConfigurableProviders`返回的**注册句柄**通过`DirectoryRegistrationHandle`表示。它本身是一个函数，直接调用可以用来撤销当前的注册，则符合Cordis一贯的设计风格。我们还可以调用它的`replace`方法用新的`LlmConfigurableProvider`列表替换这次注册的内容。

```typescript
export class LlmRuntime extends Service {
  registerConfigurableProviders(entries: readonly LlmConfigurableProvider[])
    : DirectoryRegistrationHandle 
  listConfigurableProviders(): LlmConfigurableProvider[] 
}

export interface DirectoryRegistrationHandle {
  (): void
  replace(entries: readonly LlmConfigurableProvider[]): void
}
```

我们修改[DeepSeek Harness深度拆解-06:体验DSH针对LLM的动态路由](https://jaydenai.blog.csdn.net/article/details/166201752)提供的插件（`./explor/src/llm_explor.ts`），并采用如下的方式调用`ctx.llm`的`listConfigurableProviders`方法得到当前可配置LLM供应商列表，并序列化成JSON输出。


## 2. LLM信息动态发现

通过调用`LlmRuntime`的`registerConfigurableProviders`方法将指定的`LlmConfigurableProvider`列表添加到`directory`字典中，提供一种针对可配置LLM供应商的静态注册方式。在确定了供应商之后，还需要提取该供应商提供的LLM列表，此时我们就可以需要在`discoveries`字段中注册一个用来发现LLM列表的函数。这个函数的输入通过如下这个`LlmModelDiscoveryRequest`接口表示，它的所有字段都是可以缺省的，具体是否需要提供依赖于具体的实现。

```typescript
interface LlmModelDiscoveryRequest {
  provider?: string
  baseURL?: string
  api?: string
  apiKey?: string
}
```

四个字段说明如下：

- **provider**：LLM供应商ID，同时也作为LLM路由的Key；
- **baseURL**：远程服务的终结点地址；
- **api**：终结点使用的协议说明;
- **apiKey**: 作为用户凭证的API-Key。

发现返回一个`Promise<readonly LlmDiscoveredModel[]>`，`LlmDiscoveredModel`接口用来描述被发现的单个LLM，四个字段分别表示LLM的ID、名称、最大上下文窗口和支持的最大Token数。

```typescript
interface LlmDiscoveredModel {
  id: string
  name?: string
  contextWindow?: number
  maxTokens?: number
}
```

`LlmRuntime`提供了如下的`registerModelDiscovery`方法来注册LLM发现函数，另一个`discoverModels`方法会根据提供的供应商配置命名空间和`LlmModelDiscoveryRequest`返回一个`Promise<LlmDiscoveredModel[]>`对象。

```typescript
export class LlmRuntime extends Service {
  registerModelDiscovery(
    settingsNs: string,
    discover: (request: LlmModelDiscoveryRequest) => Promise<readonly LlmDiscoveredModel[]>)

  async discoverModels(
    settingsNs: string,
    request: LlmModelDiscoveryRequest,
  ): Promise<LlmDiscoveredModel[]> 
}
```

为了演示针对LLM的发现，我们修改了上面演示程序的插件。如下面的代码所示，我们调用`ctx.llm`的`discoverModels`方法以`llm-pi-ai`作为配置的命名空间获取基于`Azure OpenAI`供应商提供的所有LLM。从输出来看，这个实现是有问题的，我输入的是Mircorosft Foundry项目基于Azure OpenAI的地址和`apiKey`，它本应该返回我实际部署的LLM列表，但是它返回的是整个供应商支持的LLM列表。这样的列表会出现在Web界面上供你选择，如果你选择了一个没有部署的LLM，自然是无法访问的。

## 3. 注册LLM适配器

DSH将针对LLM的调用抽象成`LlmRuntime`的`stream`方法，所有不同供应商需要针对抽象的LLM提供各自的适配。`@deepseek-ai/dsh-llm`为这个适配器定义了如下这个`LlmAdapter`接口：

```typescript
export abstract class LlmAdapter {
  providerInfo(provider: string): LlmProviderInfo {
    return { id: provider, name: provider }
  }
  providerRetryPolicy(_provider: string): ResolvedRetryPolicy | undefined {
    return undefined
  }
  listModels(_provider: string): Promise<readonly LlmModelInfo[]> {
    return Promise.resolve([])
  }
  resolveModel(
    provider: string,
    model: string,
    _signal?: AbortSignal,
  ): Promise<LlmResolvedModelInfo> {
    return Promise.resolve({ provider, id: model, name: model })
  }
  abstract stream(options: GenerateOptions): AsyncIterable<StreamChunk>
}
```

定义在这个接口的五个方法说明如下：

- **providerInfo**：根据提供的供应商名称提供相应的描述信息；
- **providerRetryPolicy**：提供指定供应商的在调用LLM失败后采用的重试策略；
- **listModels**：列出指定供应商的模型列表；
- **resolveModel**：根据指定供应商名称和模型ID解析出具体模型信息；
- **stream**： 必须实现的流式调用LLM的方法，`LlmRuntime`的`stream`方法调用的正是此方法。

### 3.1 供应商描述

`providerInfo`方法返回的供应商信息通过如下这个`LlmProviderInfo`接口表示，它只有表示供应商ID和显示名称的两个字段。

```typescript
export interface LlmProviderInfo {
  id: string
  name: string
}
```

### 3.2 失败重试策略

`providerRetryPolicy`方法返回的失败重试策略通过`ResolvedRetryPolicy`接口表示，它是针对`ResolvedNormalRetryPolicy`和`ResolvedAlwaysRetryPolicy`两个接口的联合，它们分别表示条件（只在遇到特定错误码时重试，且最多重试`maxRetries`次）和无条件重试策略（不管什么错误，都重试）。

```typescript
export type ResolvedRetryPolicy = ResolvedNormalRetryPolicy | ResolvedAlwaysRetryPolicy
export interface ResolvedNormalRetryPolicy extends ResolvedRetryBackoff {
  readonly mode: 'normal'
  readonly maxRetries: number
  readonly retryableCodes: readonly string[]
}
export interface ResolvedAlwaysRetryPolicy extends ResolvedRetryBackoff {
  readonly mode: 'always'
}
export interface ResolvedRetryBackoff {
  readonly initialDelayMs: number
  readonly maxDelayMs: number
  readonly jitterRatio: number
}
```

`ResolvedNormalRetryPolicy`和`ResolvedAlwaysRetryPolicy`两个接口都派生自`ResolvedRetryBackoff`，后者提供了如下三个描述重试策略的字段：

- **initialDelayMs**：首次重试的等待时间（毫秒）；
- **maxDelayMs**：等待时间的上限（毫秒）；
- **jitterRatio**：抖动比例（在计算出的等待时间上加一点随机扰动，避免大量客户端同时重试造成"惊群"）。

### 3.3  LLM描述

`listModels`返回的LLM信息分别通过如下这个`LlmModelInfo`接口表示，它会提供供应商Id、模型Id、名称和描述，以及支持的模态等基本信息。LLM支持的模态通过`ModelModality`类型表示，目前只支持文本和图片。

```typescript
export interface LlmModelInfo {
  provider: string
  id: string
  name: string
  description?: string
  inputModalities?: readonly ModelModality[]
}

export type ModelModality = ModelModalityMap[keyof ModelModalityMap]
export interface ModelModalityMap {
  text: 'text'
  image: 'image'
}
```

`resolveModel`方法返回的`LlmResolvedModelInfo`接口是对`LlmModelInfo`扩展，会进一步提供LLM的上下文窗口和推理强度相关的信息，涉及的相关接口如下所示。

```typescript
export interface LlmResolvedModelInfo extends LlmModelInfo {
  context?: LlmModelContext
  defaultMaxTokens?: number
  reasoning?: LlmModelReasoningInfo
}

export interface LlmModelContext {
  contextWindow: number
}

export interface LlmModelReasoningInfo {
  efforts: readonly LlmReasoningEffortInfo[]
  defaultEffort?: ReasoningEffortId
}

export interface LlmReasoningEffortInfo {
  id: ReasoningEffortId
  name: string
  description?: string
}
```

### 3.4 适配器的注册和LLM路由

我们可以调用`LlmRuntime`的`registerAdapter`方法为指定的一个或者多个供应商注册`LlmAdapter`适配器，本篇文章着重介绍的LLM路由注册就体现在这里。方法返回的注册句柄通过`AdapterRegistrationHandle`接口，它本质是是一个可以用来撤销注册的函数，我们也可以将其作为对象调用其`replace`方法来重新注册绑定的路由。

```typescript
export class LlmRuntime extends Service {
    registerAdapter(providers: string[], adapter: LlmAdapter): AdapterRegistrationHandle
}
interface AdapterRegistrationHandle {
  (): void
  replace(providers: string[]): void
}
```

我们总是调用`LlmRuntime`的`stream`方法以流的方式调用LLM。从如下给出的针对`stream`方法的实现可知，最终调用的就是对应`LlmAdapter`的同名方法。由于中间会利用事件总线以`waterfall`的形式来触发最终的调用，如果具有拦截甚至中断调用的需求，可以通过注册`llm/stream`事件来实现。事件处理函数可以获取表示完整LLM请求的`GenerateOptions`对象。

```typescript
export class LlmRuntime extends Service {
  stream(options: GenerateOptions): AsyncIterable<StreamChunk> {
    return this.streamWithRegistration(options)
  }

  private streamWithRegistration(
    options: GenerateOptions,
    prepared?: { registration: AdapterRegistration; config: LlmCallConfig }): AsyncIterable<StreamChunk> {
    return this.ctx.waterfall(
      this,
      'llm/stream',
      options,
      () => this.adapterStream(options, prepared),
    )
  }

  private async * adapterStream(
    options: GenerateOptions,
    prepared?: { registration: AdapterRegistration; config: LlmCallConfig }): AsyncGenerator<StreamChunk> {
    try {
      const registration = prepared?.registration ?? this.registration(options.provider)
      ...
      const adapter = registration.adapter
      const stream = adapter.stream(this.forAdapter(resolvedOptions, adapter))
      iterator = stream[Symbol.asyncIterator]()
    } 
    catch (error: unknown) {
      yield adapterFailureChunk(error, options.signal)
      return
    }
    ...
  }
}
```

## 4. 两个官方实现

作为所有Profile基础包的`@deepseek-ai/dsh-base`利用提供的补丁文件`@deepseek-ai/dsh-base/cordis.patch.yml`定义了如下两个插件，它们在启动的时候不仅会调用`ctx.llm`的`registerAdapter`方法这个各自的适配器，还是调用其他方法来注册LLM供应商和LLM发现函数。

```yaml
- insert:
    - id: llm-pi-ai
      name: '@deepseek-ai/dsh-llm-pi-ai'
    - id: llm-deepseek
      name: '@deepseek-ai/dsh-llm-deepseek'    
```

`llm-deepseek`插件直连DeepSeek 官方API，使用原生`fetch`加`eventsource-parser`处理SSE帧，自行持有翻译逻辑，不依赖完整SDK。`dsh-llm-pi-ai`插件承载其他所有提供方（OpenAI、Anthropic、Google等）。通过`@earendil-works/pi-ai`库动态解析配置的`provider/model` 对，把网关或自托管服务器的差异归为配置而非代码。
