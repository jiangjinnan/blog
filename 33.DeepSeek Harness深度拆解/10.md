# [DeepSeek Harness深度拆解-10]工具如何定义和注册

工具对于Agent的作用不言而喻。虽然不同的Agent框架针对工具具有不同的定义和注册方式，但是工具的大部分描述信息是为LLM提供的，因为最终决定调用哪个工具决定于LLM针对推理任务的理解和当前可用工具的描述，所以DSH针对工具的定义也不会有什么太特别的地方。如果硬要说特别的化，那就是源于DSH建立在Cordis之上，需要以插件的形式调用相应的服务来注册工具。这篇文章我们将通过一系列的实例来体现工具定义和注册的编程模式。

## 1. 在自定义插件中定义和注册工具

为了便于Debug，我们依然采用源码的方式启动DSH。我们在根目录上创建一个名为`./explor`的目录，并在其中定义插件和对应的补丁文件，具体的目录结构如下。我们在[DeepSeek Harness深度拆解-06：在自定义插件中体验LLM的动态路由](https://blog.csdn.net/JaydenAI/article/details/166201752)就是采用这种方式来体现LLM的动态路由机制的。

```markdown
./explor
├── src
|   └── tool_explor.ts
├── cordis.patch.yml
├── package.json
└── tsconfig.json
```

工具的定义和注册都体现在`./explor/src/tool_explor.ts`这个`.ts`文件中。如代码所示，我们具体注册的是一个通过`ToolDefinition`接口表示的**工具定义**，该接口基于与工具相关的大部分类型都由`@deepseek-ai/dsh-tools`这个包提供。我们按照此接口定义了一个用来根据指定城市提供天气信息的工具，并利用字段`name`、`description`和`parameters`指定了工具的名称、描述和输入参数的JSON Schema。`output`字段利用`schema`提供工具输出对象的结构，render提供了一个函数将工具函数返回的对象转换成LLM能够识别的内容。

```typescript
import { Context } from '@deepseek-ai/cordis'
import {ToolDefinition} from '@deepseek-ai/dsh-tools'

export const name = "tool_explor"
export async function apply(ctx:Context){   
  const tool: ToolDefinition = {
    name: 'get_weather',
    description: "Get the specified city's weather information.",
    parameters: {
      type: 'object',
      properties: {
      city: { type: 'string', description: 'The city to look up weather for.' },
    },
    required: ['city'],
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value: string) => [{ type: 'text', text: value }],
    },
    async execute(args:any, _) {
      return `It is 20 °C raining in ${args.city} right now.`
    },
  }  
  ctx.tools.register(tool)
}
```

至于工具在本地的执行逻辑，则直接定义在`execute`字段对应的函数中。作为模拟，我们返回一个固定的天气信息。我们定义的这个`ToolDefinition`对象最终需要利用`ctx.tools`返回的`ToolRuntime`对象的`register`方法进行注册。顾名思义，作为工具执行的运行时，`ToolRuntime`是与工具相关的最核心的类型，我们将在后续的文章对它进行系统介绍。针对上面定义的插件，我们修改了对应的补丁文件`./explor/cordis.patch.yml`。

```yaml
- insert:
  - id: tool_explor
    name: 'E:\dsh\deepseek-harness\explor\src\tool_explor.ts'
    inject: ['tools']
```

## 2. 调用defineTool函数定义工具

虽然工具定义以`ToolDefinition`接口的方式定义，但是按照这个结构自行构建工具还是比较繁琐，所以`@deepseek-ai/dsh-tools`还提供了一个专门用来定义工具的`defineTool`函数，使用它可用是工具定义稍微简单一点。比如上面这个`get_weather`工具就可用改用如下的方式利用`defineTool`函数来定义。

```typescript
import { Context } from '@deepseek-ai/cordis'
import {defineTool} from '@deepseek-ai/dsh-tools'

export const name = "tool_explor"
export async function apply(ctx:Context){
  const tool = defineTool( {
      name: 'get_weather',
      description: "Get the specified city's weather information.",
      parameters: {
        city: { type: 'string', description: 'The city to look up weather for.' },
      },
      output: {
        schema: { type: 'string' },
        render: (_args, value:string) => [{ type: 'text', text: value }],
      },
      async execute(args:any, _) {
        return `It is 20 °C raining in ${args.city} right now.`
      }
  })
  ctx.tools.register(tool)
}
```

## 3. 查看发送给LLM的工具信息

之所以需要利用`ToolDefinition`接口来规范工具定义，源于LLM对工具描述的要求。我们可用按照如下的方式通过监听`llm/stream`事件，看看我们注册的工具最终以何种形态发送给LLM。

```typescript
import { Context } from '@deepseek-ai/cordis'
import {defineTool} from '@deepseek-ai/dsh-tools'
import {GenerateOptions} from '@deepseek-ai/dsh-llm'

export const name = "tool_explor"
export async function apply(ctx:Context){  
  ...
  ctx.tools.register(tool)
  ctx.on("llm/stream", (options:GenerateOptions, next)=>{
    const tool = options.tools?.find(t=>t.name == "get_weather")
    if(tool){
      console.log(`'get_weather' tool in LLM (${options.provider}/${options.model}) request`)
      console.log(JSON.stringify(tool, null, 2))
    }
    return next()
  })
}
```

## 4. 利用约束控制工具的可见性

默认情况下所有注册的工具都会发送给LLM，但是我们知道发送太多与当前任务完全不相关的工具列表会造成负面的影响，此时我们可用在Agent的范围内（这里的范围指的就是[DeepSeek Harness深度拆解-09:基于Scope的隔离机制是如何实现的？](https://jaydenai.blog.csdn.net/article/details/166327421)介绍的Scope）调用`ToolRuntime`的`restrict`方法允许或者拒绝相应的工具。比如在如下的演示程序中，我们通过注册`agent/created`事件，得到当前执行的Agent，并在它提供的`Context`中以上述的方式禁用我们注册的`get_weather`工具。

```typescript
import { Context } from '@deepseek-ai/cordis'
import {defineTool} from '@deepseek-ai/dsh-tools'
import {GenerateOptions} from '@deepseek-ai/dsh-llm'
import '@deepseek-ai/dsh-agent'

export const name = "tool_explor"
export async function apply(ctx:Context){  
  ...
  ctx.on('agent/created', (payload) => {
      payload.agent.ctx.tools.restrict({deny: ["get_weather"]})
  })  
}
```

再次按照相同的方式启动DSH，注册的`get_weather`工具将不会发送给LLM。通过LLM的推理可用看出，它会启动一个`web search`任务访问[和风天气 · 苏州](https://www.qweather.com/weather/suzhou-101190401.html)得到真实的天气，并最终给出着装建议。

## 5. 工具执行前的最后一道关卡

`ToolRuntime`还提供了一个`guard`方法，我们将它视为执行工具的最后一道门卫。具体来说，我们可以利用这个方法注册一个回调，当Agent在执行工具函数之前会先调用此回调。如果此回调返回`undefined`，意味着**门卫放行**，继续完成目标工具的执行，否则返回的字符串将会作为本次工具调用的结果并反馈给LLM。以下面的演示程序为例，我们在`agent/created`事件的处理函数中改调`guard`方法，注册的回调会根据作为参数的`ToolExecution`得到工具名称，如果是`get_weather`，我们直接返回这段文字:`'get_weather' tool provides fake weather information only`.

```typescript
import { Context } from '@deepseek-ai/cordis'
import {defineTool} from '@deepseek-ai/dsh-tools'
import {GenerateOptions} from '@deepseek-ai/dsh-llm'
import '@deepseek-ai/dsh-agent'

export const name = "tool_explor"
export async function apply(ctx:Context){  
  ...
  ctx.on('agent/created', (payload) => {
      payload.agent.ctx.tools.guard(toolExecution=>{
        if(toolExecution.name == "get_weather"){
          return "'get_weather' tool provides fake weather information only."
        }
        return undefined
      })
  })  
}
```
