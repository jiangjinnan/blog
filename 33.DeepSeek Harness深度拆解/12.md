# [DeepSeek Harness深度拆解-12]揭秘工具完整的执行流程

到目前为止，我们都是站在开发者的角度来探讨工具如何定义和注册，接下来我们将站在`ToolRuntime`的视角，聊聊它如何处理我们提供的工具注册，并在Agent Loop中以怎样的形式执行由LLM生成的工具调用。由于作为定义的`ToolDefinition`、作为约束并最终决定工具可见性的`ToolRestriction`，以及在工具在执行前的进行防御性验证的`ToolGuard`都是基于Scope注册的。`ToolRuntime`提供的是一个基于Scope的分层注册表，按照[DeepSeek Harness深度拆解-08：如何实现基于自定义逻辑范围的隔离](https://blog.csdn.net/JaydenAI/article/details/166326962)对此的介绍，我们知道其中必然会使用到`ScopedLayers`对象，上述三个注册对象对应的条目会存储到某个实现了`ScopeLayer`接口的对象中，这个对象的类型为`ToolLayer`。

## 1. 基于Scope的单层注册表

由于Agent Loop中针对LLM的调用必然在某个确定的Scope中进行，所以在进行LLM调用的时候需要根据当前的Scope来选择注册的工具集。作为一个针对`ScopeLayer`接口的实现，`ToolLayer`提供了的工具注册表总是与具体的一个Scope绑定在一起。在最终为LLM调用收集工具的时候，我们只需要根据构建的全局Scope树，将从根到当前Scope对应的`ToolLayer`提取出来，并对注册在它们上面的工具进行合并，最终的结果就是与当前Scope匹配的工具集。

从如下所示的定了可以看出，`ScopeLayer`不仅仅利用`tools`字段对应的`NamedEntries<ToolDefinition>`提供了针对`ToolDefinition`的注册表，还通过`restrictions`和`guards`这两个`AnonymousEntries`对象提供了额外的注册表。`restrictions`对应的注册条目类型为`CompiledToolRestriction`，可以认为是`ToolRestriction`编译后的结果。`guards`存储就是我们提供的`ToolGuard`函数。

```typescript
class ToolLayer implements ScopeLayer {
  readonly tools: NamedEntries<ToolDefinition>
  readonly restrictions = new AnonymousEntries<CompiledToolRestriction>()
  readonly guards = new AnonymousEntries<ToolGuard>()
  mode: ToolPresentationMode | undefined
  isEmpty(): boolean {
    return this.tools.isEmpty() && this.restrictions.isEmpty() && this.guards.isEmpty()
      && this.mode === undefined
  }
  ...
}

export type ToolPresentationMode = 'native' | 'ptc' | 'both'

interface CompiledToolRestriction {
  readonly allow?: ReadonlySet<string>
  readonly deny?: ReadonlySet<string>
}
```

`mode`字段类型为`ToolPresentationMode | undefined`，表示该作用域的`agent`为自己声明的工具呈现方式，它具有下四个选项

- **native**：原生工具调用形式；
- **ptc**：PTC（Programmatic Tool Calling，DSH针对CodeAct的实现）形式;
- **both**：两种形式都呈现;
- **undefined**：未声明，沿用部署默认形式

`ToolLayer`利用注册的`CompiledToolRestriction`判断指定的工具是否应该被**承认**的判断逻辑体现它的`admits`方法上。针对任意一个`CompiledToolRestriction`，只要满足如下两个条件之一，就不会被承认：

- 对`allow`进行了设置，对应的**白名单**不包含当前的工具；
- 对`deny`进行了设置，对应的**黑名单**包含此工具。

```typescript
class ToolLayer implements ScopeLayer {
  admits(name: string): boolean {
    for (const filter of this.restrictions.values()) {
      if ((filter.allow !== undefined && !filter.allow.has(name))
        || (filter.deny !== undefined && filter.deny.has(name))) return false
    }
    return true
  }

  guardReason(exec: ToolExecution): string | undefined {
    for (const guard of this.guards.values()) {
      const reason = guard(exec)
      if (reason !== undefined) return reason
    }
    return undefined
  }
}
```

另一个`guardReason`方法则是针对指定的工具调用，利用注册的`ToolGuard`函数生成拒绝执行该工具的理由。逻辑很简单，它会遍历所有的`ToolGuard`并将指定的`ToolExecution`作为参数执行对应的函数，如果返回一个具体的字符串，则直接作为最终的拒绝执行理由。只有所有`ToolGuard`函数都返回`undefined`，`guardReason`方法才会返回`undefined`，工具执行才得以继续。

## 2. ToolRuntime针对工具注册的处理

`ToolRuntime`定义了如下这个`layers`字段，返回一个基于`ToolLayer`的`ScopedLayers`对象。注册的`ToolDefinition`、`ToolGuard`，以及`ToolRestriction`转换成的`CompiledToolRestriction`会直接添加到这个`ScopedLayers`对象，具体会落在某个`ToolLayer`上。

```typescript
export class ToolRuntime extends Service {
  private readonly layers = new ScopedLayers(
    scope => new ToolLayer(scope),
    () => { this.ctx.emit('tools/change') }
  )
  
  register(definition: ToolDefinition): () => void
  restrict(filter: ToolRestriction): () => void
  guard(guard: ToolGuard): () => void {
    return this.layers.effect(
      this.ctx,
      layer => layer.guards.append(guard),
      { label: 'tools.guard()', notify: false },
    )
  }
}
```

我们在上面列出了`guard`方法的定义，它会直接调用`layers`的`effect`方法，并将指定的`ToolGuard`对象添加到与指定`Context`匹配的那个`ToolLayer`对象的`guards`注册表中。由于`ToolRuntime`派生自基类`Service`，所以默认开启针对当前`Context`自动跟踪，即`this.ctx`总是动态绑定当前`Context`。也正是源于这个原因，注册的`ToolGuard`对象总是被添加到与当前`Context`绑定Scope对应的`ToolLayer`上。如果没有绑定，则添加全局`ToolLayer`上。`ToolRuntime`的`register`和`restrict`方法执行原理与`guard`方法本质上是一致的。只是`register`会对指定的`ToolDefinition`做一些必要的验证。`restrict`方法会复杂一些，具体逻辑如下：

- 由于工具约束不能全局注册，所以要求当前`Context`绑定的Scope必须存在，否则会抛出异常；
- 将指定的`ToolRestriction`转换成`CompiledToolRestriction`，并验证`allow`和`deny`中不能包含PTC工具`run_code`，因为这是被保留的、不允许被约束的工具；
- 验证每个工具名称的合法性，要求在工具注册在当前Scope的上级Scope对应的`Context`（包括未绑定Scope的`Context`）。如果你查阅API文档，上面会提到只有`global tools`才能被约束，其实这个表述会引起歧义；
- 按照`guard`方法类似的方式将`CompiledToolRestriction`添加到对应`ToolLayer`对象的`restrictions`注册表中。

## 3. 工具的执行流程

在Agent Loop中，LLM返回Assistant消息中携带的`ToolCall`将会用来创建作为工具执行输入的`ToolExecutionInput`对象，并调用`ToolRuntime`的`execute`方法完成对目标工具的执行。

```typescript
export class ToolRuntime extends Service {
  async execute(exec: ToolExecutionInput): Promise<ToolExecutionResult> 
}
```

`execute`方法返回的`ToolExecutionResult`是一个由`ToolExecutionSuccess`和`ToolExecutionFailure`组成的可辨识联合类型，用`isError`作为判别字段，分成成功与失败两支。

```typescript
export type ToolExecutionResult = ToolExecutionSuccess | ToolExecutionFailure

export interface ToolExecutionSuccess {
  readonly isError: false
  readonly value: JsonValue
  readonly content: ContentBlock[]
  readonly error?: never
  readonly meta?: JsonValue
  readonly additionalContexts?: UserMessage[]
  readonly concludesTurn?: true
}
export interface ToolExecutionFailure {
  readonly isError: true
  readonly error: ToolFailure
  readonly value?: never
  readonly content: ContentBlock[]
  readonly meta?: JsonValue
  readonly additionalContexts?: UserMessage[]
  readonly concludesTurn?: never
}
```

相关字段说明如下：

- **isError**：确定工具是成功执行还是抛出异常；
- **value**：工具函数执行的结果；
- **content**：执行结果转换成的ContentBlock列表；
- **error**：抛出的异常；
- **meta**: 额外的元数据；
- **additionalContexts**：调用ToolRunContext的deferContext方法提供的一组用户消息，它们将被置于对话历史当前工具结果的消息后，作为额外的上下文提供的给LLM；
- **concludesTurn**：表示本轮针对Agent的调用是否成功结束。

整条链路围绕一个分阶段调度展开，核心是把**工具执行预检 → 调度工具分发 → 工具执行后处理 → 结果生成与通知**拆成可被并行调度器驱动的步骤。但是并不是所有的工具执行都需要经历完整的阶段，如果出现取消调用、出现异常、引入人工审核并拒绝执行等情况，会跳过中间的步骤。当前阶段在完成执行后会创建这个`ScheduledToolPreparation`对象，并利用其kind字段决定接下来进入哪个阶段。

```typescript
export type ScheduledToolPreparation =
  | { kind: 'dispatch'; exec: ToolRunContext }
  | { kind: 'post-result'; exec: ToolRunContext; result: ToolExecutionResult }
  | { kind: 'final-result'; exec: ToolRunContext; result: ToolExecutionResult }
```

### 3.1 工具执行预检

在这个初始化阶段，传入的`ToolExecutionInput`将用来创建表示工具执行上下文的`ToolRunContext`，并将输入的参数全部冻结。如果采用`ptc`模式，意味着能够直接执行的只有`run_code`工具，此时会创建一个`ToolExecutionFailure`来表达当前工具不能被直接调用，并生成一个`kind`字段为`final-result`的`ScheduledToolPreparation`，意味着将直接进入**结果生成**阶段。如果此时利用`AbortSignal`接受到取消调用的信号，或者抛出异常，也会做出类似的应对，只是错误消息不同而已，而且类似操作会频繁出现在整个处理流程中。

在得到`ToolRunContext`上下文后，会将当前`ToolRuntime`和Agent作为`base`和`ScopeKey`调用`scopeTarget`方法创建一个在Agent范围内分发事件的对象，并以`waterfall`的形式触发`tools/pre-execute`事件，其目的在于收集当前工具是否希望被执行的决策。该事件对应处理函数的签名如下，当前执行上下文为`Scoped<ToolRuntime>`对象，可以利用输入得到描述当前工具执行的`ToolExecution`对象，`next`函数和事件流最终返回一个表示工具预决策的`PreToolDecision`对象。

```typescript
interface Events {
    'tools/pre-execute'(this: Scoped<ToolRuntime>, exec: ToolExecution, next: () => Promise<PreToolDecision>): Promise<PreToolDecision>
}
export type PreToolDecision =
  | { kind: 'allow' }
  | { kind: 'deny'; reason: string }
  | { kind: 'ask'; reason?: string }
```

`PreToolDecision`体现了针对当前工具的三种决策类型：

- **allow**：运行执行；
- **deny**：拒绝执行，并提供拒绝理由；
- **ask**：需要引入人工审批，并提供原因；

如果在此阶段有干预的需要，我们可以注册这个事件。如果没有对应的事件注册，整个事件流直接返回`{ kind: 'allow' }`。得到的`PreToolDecision`的类型为`ask`，会调用注册的`ApprovalService`服务引入人工审批，并最终得到审批结果的`ApprovalOutcome`对象，并进一步封装成`ToolAskResolution`对象。

```typescript
export type ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'

interface ToolAskResolution {
  readonly decision: Extract<PreToolDecision, { kind: 'allow' | 'deny' }>
  readonly approvalCancelled: boolean
}
```

我们注册的`ToolGuard`函数只有在`PreToolDecision`的`kind`为`allow`时才会执行，返回会的字符串将会作为拒绝执行当前工具原因。只有通过所有的**预检**，当前的工具执行才会继续，否则以如下三种方式提供的拒绝执行的理由。

- 注册`tools/pre-execute`事件，直接拒绝并给出理由；
- 注册`tools/pre-execute`事件要求引入人工审批，但是审批失败，并得到拒绝理由；
- 利用注册的`ToolGuard`函数返回拒绝理由。

拒绝理由将会作为工具执行的结果，被用来创建一个`ToolExecutionFailure`对象。接下来会创建一个`kind`为`post-result`的`ScheduledToolPreparation`对象，进入**工具执行后处理**阶段。

### 3.2 工具函数调用

在成功完成预检后，会创建`kind`为`dispatch`的`ScheduledToolPreparation`对象，进入对调度执行工具的分发阶段，工具函数就是在这个阶段执行的。该阶段的核心处理流程实现在如下这个`dispatchScheduledExecution`方法中。

```typescript
export class ToolRuntime extends Service {
  private async dispatchScheduledExecution(exec: ToolRunContext)
    : Promise<ScheduledToolDispatch> 
}
```

为了给我们一个对工具执行上下文进行最后定制的机会，`ToolRuntime`同样会采用上述的方式调用`scopeTarget`函数创建一个在当前Agent范围内分发事件的对象，并以`waterfail`触发具有如下签名的`tools/execute`事件。工具事件签名可以看出，当前`ToolRuntime`同样会作用事件处理函数的执行上下文，我们可以利用参数得到一个`ToolDispatchExecution`，其本质上就是一个`AbortSignal`被替换了的`ToolExecution`对象。

```typescript
interface Events {
    'tools/execute'(
      this: Scoped<ToolRuntime>, 
      exec: ToolDispatchExecution, 
      next: () => Promise<ToolExecutionResult>)
      : Promise<ToolExecutionResult>
}

export interface ToolDispatchExecution extends Omit<ToolExecution, 'signal'> {
  signal: AbortSignal
}
```

由于`next`函数和整个`waterfail`事件流返回作为工具执行结果的`ToolExecutionResult`，所有我们可以利用注册此事件的方式来对此结果进行任意的定制。只有在整个事件流没有被劫持并短路（注册的事件处理器没有调用`next`函数）情况下，才会调用作为注册工具定义的`ToolDefinition`对象的`execute`方法。`execute`方法执行是否成功，都会返回对应的`ToolExecutionResult`对象。在得到作为工具执行结果的`ToolExecutionResult`之后，会进行一些正常化的处理，然后附加上利用`ToolRunContext`的`deferContext`方法注入的User消息（如果有）。最终创建一个`kind`为`post-result`的`ScheduledToolPreparation`对象，进入**工具执行后处理**阶段。

### 3.3 工具执行后处理

在此阶段，我们已经拥有了作为工具执行结果的`ToolExecutionResult`对象，此阶段的核心任务就是对`ToolExecutionResult`实施再加工，其核心逻辑实现在如下这个`postExecute`方法上。

```typescript
export class ToolRuntime extends Service {
  private async postExecute(
    exec: ToolExecution, 
    result: ToolExecutionResult)
    : Promise<ToolExecutionResult> 
}
```

`postExecute`方法会按照之前触发`tools/pre-execute`和`tools/execute`的方式采用`waterfall`形式触发如下这个`tools/post-execute`事件。这是工具执行流水线里的后置策略钩子，在工具已经执行、结果已经产生之后介入，让我们有机会接受并改写或阻断这次结果。

```typescript
interface Events {
   'tools/post-execute'(
    this: Scoped<ToolRuntime>, 
    exec: ToolExecution, 
    result: Readonly<ToolExecutionResult>, 
    next: () => Promise<PostToolDecision>)
    : Promise<PostToolDecision>
}

export type PostToolDecision =
  | { kind: 'accept'; content?: ContentBlock[]; value?: never; additionalContexts?: UserMessage[] }
  | { kind: 'accept'; value: JsonValue; content?: never; additionalContexts?: UserMessage[] }
  | { kind: 'block'; feedback: ContentBlock[]; additionalContexts?: UserMessage[] }
```

`next`函数和整个`waterfall`事件流返回一个`PostToolDecision`对象，表示最终对执行结果的处理决策，具体的决策体现为如下三种形式：

- **accept + content**：接受结果，但替换掉`ToolExecutionResult`的`content`字段;
- **accept + value**：接受结果，但替换掉`ToolExecutionResult`的`value`字段。这会触发针对`value`的再校验，并重现生成`ContentBlock`列表；
- **block**：把结果翻转为错误，并根据`feedback`生成`ContentBlock`作为`ToolExecutionResult`的`content`字段，同时也作为`error`字段。

在整个事件流没有被劫持并短路（注册的事件处理器没有调用`next`函数）情况下，事件流返回一个`{kind: 'accept'}`对象，意味着直接使用现有的`ToolExecutionResult`结果。

### 3.4 结果生成与通知

它是整个执行流程的终点站，其核心操作实现在如下这个`finishScheduledExecution`方法中。它把前面各阶段产出的候选结果，经过**定稿 =>物化=>广播**，变成权威的、不可变的、已被观察者看到的最终结果。

```typescript
export class ToolRuntime extends Service {
  private finishScheduledExecution(
    exec: ToolRunContext, 
    result: ToolExecutionResult): ToolExecutionResult
}
```

作为最终执行结果的`ToolExecutionResult`以具有如下签名的`tools/result`事件对外通知。和之前的介绍的三个事件不同，这里仅仅是为了将结果通知到相关方，事件的发送形式不再是`waterfall`，就是单纯的`emit`。

```typescript
interface Events {
    'tools/result'(
      this: Scoped<ToolRuntime>, 
      exec: Readonly<ToolExecution>, 
      result: Readonly<ToolExecutionResult>)
      : undefined
}
```

从上面的介绍可以看出，整个工具的执行流程会涉及一系列事件，其中最核心的是前三个以`waterfall`形式触发的事件，充分利用这些事件可以实现对工具执行流程的干预，我们将在[下一篇](https://jaydenai.blog.csdn.net/article/details/166596696)专门讨论这个问题。
