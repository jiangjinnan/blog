# [DeepSeek Harness深度拆解-16]系统提示词的组装流程

[DeepSeek Harness深度拆解-15:体验系统提示词的构建](https://jaydenai.blog.csdn.net/article/details/166683509)从编程的角度利用提供的一系列实例演示如何使用`SystemPrompt`这个基础服务，这篇文章将会完整介绍该服务针对相关注册方法的处理和最终对系统提示词的组装流程。

## 1. 不仅仅提供单纯系统提示词文本

`SystemPrompt`并不是单纯地为我们生成调用LLM提供的系统提示词（对应`GenerateOptions`的`system`字段）。它最终构建的产物体现在其`assemble`方法构建的`PromptAssembly`对象上，只有`sections`部分的内容才会参与存储系统提示的渲染。`contexts`部分会转换成消息，并最终添加到`GenerateOptions`的`messages`列表中作为对话历史的一部分，而`tools`提供的工具Schema自然就对应`GenerateOptions`的同名字段。

```typescript
export class SystemPrompt extends Service {
  async assemble(context: AssembleContext = {}): Promise<PromptAssembly> 
}

export interface AssembleContext {
  scope?: ScopeKey
  signal?: AbortSignal
}

export interface PromptAssembly {
  sections: AssembledSection[]
  contexts: AssembledContext[]
  tools: ToolSchema[]
  variables: Record<string, string | undefined>
}
```

定义在`PromptAssembly`四个字段说明如下：

- **sections**：系统提示词的正文片段，已求值但未插值，按`order`排序，最终由 `renderPrompt` 插值、过滤、拼接成提示词字符串；
- **contexts**：动态运行时上下文快照，已求值但未插值，按`order`排序，最终渲染成用户消息插入模型历史；
- **tools**：面向模型的工具Schema列表，已结构化、已按 `toolOrder` 排序，不做文本渲染，直接作为LLM API的`tools` 参数传入；
- **variables**：变量名到值的扁平映射，已求值，仅作为`sections`和`contexts`插值时的查表来源。

DSH中的大部分资源都需要与具有某个Scope绑定,`SystemPrompt`提供的`PromptAssembly`自然也是如此，这一点从作为`assembly`方法的签名就可以看出来。该方法的参数`context`对应的`AssembleContext`接口定义了`ScopeKey`类型的`scope`字段，意味着可以针对指定的Scope动态提供对应的`PromptAssembly`对象。如果将Scope映射为Agent，那么就意味着可以针对性地为具体的Agent注册和提供系统提示词。

## 2. SystemPrompt插件配置

`SystemPrompt`既是服务也是插件，它以插件的方式将自己作为服务注册到`Context`上，作为插件的配置对应于如下这个`Config`接口。

```typescript
export interface Config {
  includeHarnessIdentity?: boolean
  includeRuntimeContext?: boolean
  personaPrefix?: string
  personaSuffix?: string
  toolOrder?: string[]
}
```

`Config`接口定义的配置选项包括：

- **includeHarnessIdentity**：是否注入Harness身份声明（默认`true`），即*You are an AI agent powered by DeepSeek Harness.*;
- **includeRuntimeContext**：是否包含`PromptContext`（默认`true`），如当前工作目录、可用工具等动态信息，每轮请求重新求;
- **personaPrefix**：作为persona的前缀，出现在第一个`PromptSection`之前，用于定义部署特有的角色描述，支持严格变量插值;
- **personaSuffix**：部署级人格后缀，出现在最后一个`PromptSection`之后，用于追加全局补充约束;
- **toolOrder**：显式指定工具呈现顺序。

## 3. 基于Scope的分层注册表

`SystemPrompt`采用标准的`Builder`模式来构建最终的`PromptAssembly`，它内部提供了一个基于Scope的分层注册表。我们针对`section`、`context`、`tools`和`variable`方法的调用都是在注册表中添加相应的条目，最终利用`assembly`方法根据指定的Scope提取匹配的注册条目进行合并，从而将返回的`PromptAssembly`对象创建出来。DSH中但凡涉及基于Scope的分层注册表概念，必然会使用`ScopedLayers`对象，并通过实现`ScopeLayer`接口提供某个Scope的单层注册表。如下这个`PromptLayer`类型就是`SystemPrompt`内部使用的单层注册表。

```typescript
class PromptLayer implements ScopeLayer {
  readonly sections: NamedEntries<PromptSection>
  readonly contexts: NamedEntries<PromptContext>
  readonly runtimeContextSuppressors = new AnonymousEntries<true>()
  readonly toolProviders = new AnonymousEntries<ToolProvider>()
  readonly variables: NamedEntries<VariableProvider>
 
  isEmpty(): boolean {
    return this.sections.isEmpty()
      && this.contexts.isEmpty()
      && this.runtimeContextSuppressors.isEmpty()
      && this.toolProviders.isEmpty()
      && this.variables.isEmpty()
  }
}

export interface PromptSection {
  readonly name: string
  readonly order: number
  readonly text: string | ((context: AssembleContext) => string)
  readonly complete?: boolean
}

export interface PromptContext {
  readonly name: string
  readonly order: number
  readonly text: string | ((context: AssembleContext) => string)
}

type ToolProvider = (context: AssembleContext) => ToolProviderResult

export interface ToolProviderResult {
  readonly schemas: readonly ToolSchema[]
  readonly knownNames?: readonly string[]
}

type VariableProvider = (context: AssembleContext) => string | undefined
```

如上面的代码所示，`PromptLayer`内部定义了五个字段来存储与某个Scope绑定或者全局系统提示词注册条目，其中包括三个类型为`NamedEntries<T>`的字段`sections`、`contexts`和`variables`用来存储注册的`PromptSection`、`PromptContext`和`VariableProvider`(用来提供模板渲染时替换占位符的变量值)。至于两个`AnonymousEntries<T>`类型的字段来说，`toolProviders`用来保存用于提供工具Schema的`ToolProvider`对象，`runtimeContextSuppressors`字段则用来存储当前Scope是否开启动态运行时上下文的开关。

## 4. 注册请求的处理
  
`SystemPrompt`定义了如下这个`ScopedLayers`类型的字段`layers`，它内部使用正是上面定义的这个`PromptLayer`。`PromptLayer`中定义的五个注册表分别通过五个对应的方法来维护。

```typescript
export class SystemPrompt extends Service {
  private readonly layers = new ScopedLayers(
    scope => new PromptLayer(scope),
    () => { this.ctx.emit('system-prompt/change') })

    section(section: PromptSection): () => void
    context(context: PromptContext): () => void 
    suppressRuntimeContext(): () => void 
    tools(provider: (context: AssembleContext) => ToolProviderResult): () => void 
    variable(name: string, provider: (context: AssembleContext) => string | undefined): () => void 
}
```

## 5. PromptAssembly的组装

在`assemble`方法中，会提取`AssembleContext`提供的Scope，然后利用它从`layers`字段表示的`ScopedLayers`对象中提取注册的条目，并生成最终的`PromptAssembly`对象。

```typescript
export class SystemPrompt extends Service {
    async assemble(context: AssembleContext = {}): Promise<PromptAssembly>
}
```

具体会按照如下的规则生成`PromptAssembly`的四个成员：

- **variables**：将Scope作为参数调用`layers`的`chainLayers`方法得到按照Scope路径排序的`PromptLayer`（不包含全局层），按照这个顺序提取变量进行合并（如果变量名称相同，与Scope越近的层具有更高遇优先级）；
- **sections** & **contexts**：将Scope作为参数调用`layers`的`merge`方法合并每个`PromptLayer`提供的`PromptSection`和`PromptContext`；
- **tools**: 将Scope作为参数调用`layers`的`chainLayers`方法得到按照Scope路径排序的`PromptLayer`，并使用全局层与之合并，然后按照此顺序提取每个`PromptLayer`的`ToolProvider`。将`AssembleContext`作为参数调用每个`ToolProvider`函数得到一组`ToolSchema`和工具名称列表，然后执行一系列验证和排序生成最终的`ToolSchema`列表。

在返回最终生成的`PromptAssembly`对象之前，`assemble`方法会以`waterfall`形式触发具有如下签名的`system-prompt/assemble`事件对外发送通知。当然，此事件肯定是以Scope绑定的范围进行分发的，本着事件向上传播的原则，只有当前以及上级Scope才会监听到此通知。整个事件流返回的`PromptAssembly`将会作为`assemble`方法的返回值，意味着我们还可以通过注册此事件的形式对`PromptAssembly`实施再加工。

```typescript
declare module '@deepseek-ai/cordis' {
  interface Events {
    'system-prompt/assemble'(
        this: Scoped<SystemPrompt>, 
        assembly: PromptAssembly, 
        context: AssembleContext, 
        next: () => Promise<PromptAssembly>): Promise<PromptAssembly>
  }
}
```

## 6. 提示词和上下文快照渲染

如下所示的是两个针对`PromptAssembly`进行文本渲染的`renderPrompt`和`renderContextSnapshot`方法的定义。它们分别从`PromptAssembly`提取`sections`和`contexts`，并将它们的内容作为模板调用`interpolate`函数使用`variables`提供的变量执行插值操作，生成最终的文本。

```typescript
export function renderPrompt(assembly: PromptAssembly): string {
  return assembly.sections
    .map(section => interpolate(section, assembly.variables, 'section'))
    .filter(text => text.length > 0)
    .join('\n\n')
}

export function renderContextSnapshot(assembly: PromptAssembly): string {
  return joinContextSections(renderContextSections(assembly))
}

export function renderContextSections(assembly: PromptAssembly): ContextSnapshotSection[] {
  return assembly.contexts
    .map(context => ({ name: context.name, text: interpolate(context, assembly.variables, 'context') }))
    .filter(section => section.text.length > 0)
}

export function joinContextSections(sections: readonly ContextSnapshotSection[]): string {
  const body = sections.map(section => section.text).join('\n\n')
  if (body.length === 0) return ''
  return `Current runtime context. This snapshot supersedes earlier runtime-context snapshots.\n\n${body}`
}

export interface ContextSnapshotSection {
  readonly name: string
  readonly text: string
}

function interpolate(
  input: AssembledSection | AssembledContext,
  variables: Record<string, string | undefined>,
  kind: 'section' | 'context',
): string
```

`renderContextSection`和`joinContextSections`函数作为`renderContextSnapshot`的辅助函数，同时可以直接导入使用。前者生成一个`ContextSnapshotSection`列表，后者将这个列表转换成字符串，并前置一段指示性文本。
