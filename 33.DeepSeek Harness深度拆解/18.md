# [DeepSeek Harness深度拆解-18]DSH配置服务设计详解

[DeepSeek Harness深度拆解-17:如何使用DSH的配置服务](https://jaydenai.blog.csdn.net/article/details/166774071)从编程的角度介绍了如何在自定义的插件中使用DSH提供的配置服务，接下我们将通过这篇以及后续的几篇文章详细介绍配置服务的完整设计和实现原理。配置服务最核心的部分实现在`SettingsProvider`这个抽象类中，学习它帮助我们深刻理解DSH原生提供的基于yaml和json文件的实现。如果希望提供其他数据源的配置，就必需对这个抽象类具有深刻的理解。

## 1. 抽象类SettingsProvider

`SettingsProvider`自身是一个派生自`Service`的Cordis服务。使用到此服务的插件总是从`Context`的`settings`字段提取此服务，这源于`SettingsProvider`构造函数中针对`super(ctx, 'settings')`的调用。

```typescript
export abstract class SettingsProvider extends Service {
  constructor(ctx: Context) {
    super(ctx, 'settings')
  }

  abstract readonly writable: boolean
  protected abstract load(): Promise<Record<string, unknown>>
  protected abstract persist(ns: SettingsNamespace, section: Record<string, unknown>): Promise<void>
}

export type SettingsNamespace = Branded<'SettingsNamespace'>
```

配置系统并未对配置内容的来源进行任何的假设和约束，所以作为抽象类的`SettingsProvider`将基于数据源的配置加载定义成抽象的`load`方法。`load`方法加载的配置体现为一个`Record<string, unknown>`对象，作为Key的字符串表示配置的命名空间，作为配置内容的Value并未作任何的约束。`SettingsProvider`自身并不要求提供针对配置更新的支持，具体的实现可用通过将抽象自读字段`writable`设置为`true`来支持此项功能，并将持久化实现在重写的`persist`方法中。

## 2. 维护状态的五个字段

`SettingsProvider`的整个状态通过如下所示的五个字段来维护：

```typescript
export abstract class SettingsProvider extends Service {
  private readonly registrations = new Map<SettingsNamespace, SettingsRegistration>()
  private document: Record<string, unknown> = {}
  private readonly writeQueues = new Map<SettingsNamespace, Promise<unknown>>()
  private readonly pendingTails = new Set<Promise<void>>()
  private stopped = false
}
```

这五个字段共同构成`SettingsProvider`的运行时状态骨架，可概括为三张表和一条标志：

- **registrations**：命名空间注册表，每个`SettingsRegistration`把该命名空间的解析规则、当前生效值、存储版本与更新监控收敛在一处；
- **document**：存储配置内容的原始用户文档。集中存放所有命名空间的用户层数据；
- **writeQueues**：针对不同命名空间对配置的写入操作构成的调用链；
- **pendingTails**：可用监控配置源的变更，并注册对应的回调函数，该字段提供的每个`Promise`表示注册到某个配置监控器上所有回调操作构成的调用链；
- **stopped**：停止服务标志。

`registrations`字段返回的`Map<SettingsNamespace, SettingsRegistration>`字典是整个配置系统最核心的部分。`SettingsRegistration`对应一个具体的命名空间，它把该命名空间的解析规则、当前生效值、存储版本与更新监控收敛在一处，是针对配置的注册、读取、写入、通知与销毁各环节共同操作的基本单元。它让每个配置域彼此隔离，又能独立演进、独立容错、独立进行并发控制。

```typescript
interface SettingsRegistration {
  ns: SettingsNamespace
  schema: z<unknown>
  base: unknown
  applies: SettingsApplies
  validate?: (value: unknown) => void
  resolved: unknown  
  revision: number
  watchers: Set<SettingsWatcher>
}
export type SettingsApplies = 'live' | 'restart'
```

各字段说明如下：

- **ns**：命名空间；
- **schema**：该命名空间的`schemastery schema`，是解析准入、界面输出与脱敏识别的类型真相来源；
- **base**：配置基准；
- **applies**：变更生效时机，具有如下两个选项：
  - live： 变更立即生效，运行时读到新值即用，无需重启；
  - restart：需要重启才能生。
- **validate**：配置验证函数；
- **resolved**：解析后的配置对象；
- **revision**：用来表达配置更新历史的版本；
- **watchers**：配置更新监控器集合。

配置服务采用了**三层合并**配置解析模型，也就是最终提供的配置是由**schema默认值 => composition base => 用户层**，从低到高叠加，高层覆盖低层:

- **schema默认值**：由schemastery schema提供，是类型的底线与兜底，保证任何字段都有合法初值;
- **配置基准**：插件/组合层内置的基准配置，表达**发布者推荐的默认**，用户未覆盖时生效，对应`SettingsRegistration`的`base`字段；
- **用户层**：用户实际持久化的原始数据，优先级最高，存在即覆盖下层。

上述针对针对配置对象的**三层合并**解析逻辑实现在如下所示的`resolve<T>`方法中，其中`mergeLayers`实现了后两层的合并，基于schemastery schema默认值的提供是通过调用`z<T>`函数完成的。

```typescript
export abstract class SettingsProvider extends Service {
  private resolve<T>(
    schema: z<T>,
    base: unknown,
    section: Record<string, unknown> | undefined,
    validate?: (value: T) => void,
  ): T {    
    const value = schema(mergeLayers(base, section) as never)
    validate?.(value)
    return value
  }
}

function mergeLayers(under: unknown, over: unknown): unknown {
  if (over === undefined) return under
  if (!isPlainObject(under) || !isPlainObject(over)) return over
  const merged: Record<string, unknown> = { ...under }
  for (const [key, value] of Object.entries(over)) {
    merged[key] = key in merged ? mergeLayers(merged[key], value) : value
  }
  return merged
}
```

注册到`SettingsRegistration`的`watchers`上的配置变更监控器通过如下这个`SettingsWatcher`接口表示，它的`active`字段决定了监控器的可用性，`callback`提供了回调函数。`SettingsWatcher`的`tail`字段返回的`Promise<void>`用来表示执行`callback`函数的调用链。它被初始化为`Promise.resolve()`，在检测到配置变更后，会将针对`callback`的调用通过`then`方法纳入到此调用链中，并生成一个新的`Promise<void>`并赋值给`tail`字段。与此同时，这个`Promise<void>`还会被添加到`SettingsProvider`的`pendingTails`字段返回的集合中。

```typescript
interface SettingsWatcher {
  callback: (next: never, prev: never) => void | Promise<void>
  tail: Promise<void>
  active: boolean
}
```

## 3. 配置服务的初始化

`SettingsProvider`中通过`Service.init`（`symbols.init`）方法会执行如下的初始化操作。它会调用`load`方法加载配置内容，然后将其作为参数调用`publish`进行发布。`publish`是`SettingsProvider`接收外部存储变更的入口。它的`source`参数（类型为`SettingsUpdateSource`）用来标记配置变更的来源：

- **provider**：表示变更由`SettingsProvider`初始化加载或者检测到外部变更重载导致；
- **update**: 表示变更由调用更新配置的API导致。

`yield`输出的函数会在卸载时执行，此时会将`stopped`状态设置为`true`，并保证未执行的配置写入和变更回调操作全部执行。

```typescript
export abstract class SettingsProvider extends Service {
  async* [Service.init](): AsyncGenerator<() => Promise<void> | void, void, void> {
    yield async () => {
      this.stopped = true
      await Promise.allSettled([...this.writeQueues.values(), ...this.pendingTails])
    }
    this.publish(await this.load())
  }
  protected publish(doc: Record<string, unknown>, source: SettingsUpdateSource = 'provider'): void {    
    const before = new Map<SettingsNamespace, unknown>()
    for (const registration of this.registrations.values()) {
      before.set(registration.ns, this.section(registration.ns))
    }
    this.document = doc
    for (const registration of this.registrations.values()) {
      let next: unknown
      next = deepFreeze(this.resolve(registration.schema, registration.base, this.section(registration.ns), registration.validate))
      this.bumpRevision(registration, before.get(registration.ns), this.section(registration.ns))
      this.commit(registration, next, source)
    }
  }
}
type SettingsUpdateSource = 'update' | 'provider'
```

初始化方法会采用默认的`source`（`provider`）调用`publish`方法，按照上面给出的简化版本，该方法大致的执行流程如下：

- 在使用`doc`参数覆盖当前`document`字段之前，会以`Map<SettingsNamespace, unknown>`的形式记录下原始的配置；
- 遍历每个命名空间对应的`SettingsRegistration`，依次执行如下操作：
  - 调用`resolve`函数利用`schemastery schema`（对应`SettingsRegistration`的`schema`字段）解析生成配置对象，并调用`deepFreeze`函数将其深度冻结；
  - 调用`bumpRevision`方法判断前后是否一致，并在不一致的情况下更细版本；
  - 调用如下这个`commit`方法将让新的配置生效并对外广播。

```typescript
export abstract class SettingsProvider extends Service {
  private commit(registration: SettingsRegistration, next: unknown, source: SettingsUpdateSource): void {
    const prev = registration.resolved    
    registration.resolved = next
    for (const watcher of [...registration.watchers]) {
      const segment = watcher.tail
        .then(() => {
          if (!watcher.active || this.isStopped()) return
          return watcher.callback(next as never, prev as never)
        })
        .then(() => undefined, (error: unknown) => {
          this.warnWatcherFailure(registration.ns, error)
        })
      watcher.tail = segment
      this.pendingTails.add(segment)
      void segment.then(() => this.pendingTails.delete(segment))
    }

    const args = ['settings/updated', registration.ns, next, prev, source]
    for (const listener of this.ctx.events.dispatch('emit', args) as Array<(...listenerArgs: unknown[]) => unknown>) {
      listener(registration.ns, next, prev, source)      
    }
  }
}
```

从如下给出的针对`commit`方法的简化版本可用看出对应的逻辑：

- 将解析出来的新配置对象赋值给`SettingsRegistration`的`resolved`字段是配置得以生效；
- 遍历注册到`SettingsRegistration`的每个`SettingsWatcher`对象，并将针对其`callback`的调用纳入`tail`字段体现的调用链中，并生成一个新的`Promise<void>`对象。该对象会覆盖`SettingsWatcher`对象的`tail`字段，并添加到`SettingsProvider`的`pendingTails`集合中；
- 以`emit`的形式触发`settings/updated`事件对外发送通知，此事件的监听器可以利用参数提取命名空间，变更前后的配置和更新来源（`SettingsUpdateSource`）。

## 4. 配置的注册

调用`register`方法注册配置的过程就是针对指定的命名空间创建对应的`SettingsRegistration`对象，并将其添加到`registrations`字典中，然后根据它创建`SettingsScope<T>`对象的过程。如代码所示，调用`register`方法需要指定命名空间、Schema和一个`SettingsRegisterOptions<T>`对象。

```typescript
export abstract class SettingsProvider extends Service {
  register<const Namespace extends string, T>(
    ns: Namespace & SettingsNamespaceInput<Namespace>,
    schema: z<T>,
    options?: SettingsRegisterOptions<T>): SettingsScope<T> {
    const parsedNs = ns as SettingsNamespace
    if (this.registrations.has(parsedNs)) {
      throw new Error(`settings namespace "${parsedNs}" is already registered`)
    }
    const registration: SettingsRegistration = {
      ns: parsedNs,
      schema: schema as z<unknown>,
      base: options?.base,
      applies: options?.applies ?? 'live',
      ...options?.validate === undefined
        ? {}
        : { validate: options.validate as (value: unknown) => void },
      resolved: deepFreeze(this.resolve(schema, options?.base, this.section(parsedNs), options?.validate)),
      revision: 0,
      watchers: new Set(),
    }
    this.ctx.effect(() => {
      this.registrations.set(parsedNs, registration)
      return () => this.registrations.delete(parsedNs)
    }, `settings.register(${JSON.stringify(String(parsedNs))})`)

    return {
      get: () => registration.resolved as T,
      watch: (callback) => {
        const watcher: SettingsWatcher = { callback: callback, tail: Promise.resolve(), active: true }
        registration.watchers.add(watcher)
        return () => {
          watcher.active = false
          registration.watchers.delete(watcher)
        }
      },
      update: patch => this.update(parsedNs, patch),
      replace: section => this.replace(parsedNs, section),
    }
  }
}

export interface SettingsRegisterOptions<T> {
  base?: Partial<T>
  applies?: SettingsApplies
  validate?: (value: T) => void
}

export interface SettingsScope<T> {
  get(): T
  watch(callback: (next: T, prev: T) => void | Promise<void>): () => void
  update(patch: object): Promise<void>
  replace(section: object): Promise<void>
}
```

作为参数的`SettingsRegisterOptions<T>`对象提供了配置基准（`base`）、更新配置生效的方式（`applies`）和配置验证函数。在创建对应`SettingsRegistration`的时候，它们连同其他两个参数将会作为对应字段（`ns`、`schema`、`base`、`applies`和`validate`）的值。至于`resolved`字段，则是调用上述的`resolve`方法实施**schema=>base=>user settings**三层合并的结果。初始化版本（`revision`）被设置为`0`，`watchers`被初始化为空集合。

返回的`SettingsScope<T>`对象直接根据`SettingsRegistration`对象创建而成，其四个成员进行如下的设置：

- **get**：对应的函数直接返回`SettingsRegistration`的`resolved`字段；
- **watch**：指定的回调函数被封装成`SettingsWatcher`（`tail`被初始化成一个空的Resolved的`Promise`，在应用配置更新的`commit`方法中，针对回调函数的调用会被纳入它该字段体现的调用链中），并被添加到`SettingsRegistration`的`watchers`集合中。返回的`Promise`将用来解除此`SettingsWatcher`的注册；
- **update** & **replace**：分别调用`update`和`replace`方法实现配置的增量合并和全量替换。

一切注册皆可撤销是Cordis一贯的设计，`register`方法也不例外。将创建的`SettingsRegistration`添加到`registrations`字典的操作是在调用当前`Context`的`effect`方法中进行的。执行的函数在完成配置注册后，还会返沪一个函数将添加的`SettingsRegistration`对象从`registrations`字典移除。

## 5. 配置的读取和更新

虽然`SettingsProvider`并没有提供根据指定命名空间直接返回`SettingsRegistration`对象的方式，但是提供了如下的`get`方法根据命名空间返回对应`SettingsRegistration`对象的`resolved`字段，我们可用通过它得到这个通过三层合并被冻结的配置对象。

```typescript
export abstract class SettingsProvider extends Service {
  get<const Namespace extends string>(ns: Namespace & SettingsNamespaceInput<Namespace>): unknown {
    return this.registrations.get(parseSettingsNamespace(ns))?.resolved
  }

  async update<const Namespace extends string>(
    ns: Namespace & SettingsNamespaceInput<Namespace>,
    patch: object,
    expectedRevision?: number): Promise<void> {
    return this.write(parseSettingsNamespace(ns), patch, 'merge', expectedRevision)
  }

  async replace<const Namespace extends string>(
    ns: Namespace & SettingsNamespaceInput<Namespace>,
    section: object,
    expectedRevision?: number): Promise<void> {
    return this.write(parseSettingsNamespace(ns), section, 'replace', expectedRevision)
  }

  async mutate<const Namespace extends string>(
    ns: Namespace & SettingsNamespaceInput<Namespace>,
    ops: readonly SettingsPathOp[],
    expectedRevision?: number): Promise<void> {
    const parsedNs = parseSettingsNamespace(ns)
    return this.write(parsedNs, ops, 'mutate', expectedRevision)
  }
}

export type SettingsPathOp =
  | { op: 'set'; path: readonly string[]; value: unknown }
  | { op: 'unset'; path: readonly string[] }
```

`register`方法返回的`SettingsScope<T>`对象提供了`update`和`replace`方法，它们最终会调用`SettingsProvider`的两个同名方法。除了增量合并和全量替换这两种更新方式之外，`SettingsProvider`还提供了`mutate`方法方法利用指定的指令（`set`和`unset`）针对指定的路径精准修改配置的第三种方式。考虑到并发更新，我们可以利用它们共同的参数`expectedRevision`指定当前更新针对的版本。如果同一版本的配置被并发更新，只有一个能够成功。从上面的代码可用看出，这三个方法最终调用的都是如下这个`write`方法。

```typescript
export abstract class SettingsProvider extends Service {
  private write(
    ns: SettingsNamespace,
    input: object,
    mode: 'merge' | 'replace' | 'mutate',
    expectedRevision?: number): Promise<void> {
    const verb = mode === 'merge' ? 'update' : mode === 'replace' ? 'replace' : 'mutate'
    const registration = this.registrations.get(ns)
    ...
    let payload: Record<string, unknown>
    if (mode === 'mutate') {
      payload = { ops: input }
    } else {
      payload = input
    }
    
    const snapshot = cloneJsonShaped(payload)
    const previous = this.writeQueues.get(ns) ?? Promise.resolve()    
    const run = previous.catch(() => undefined).then(async () => {    
      if (expectedRevision !== undefined && expectedRevision !== registration.revision) {
        throw new SettingsConflictError(ns, expectedRevision, registration.revision)
      }
      const current = this.section(ns) ?? {}
      const section = mode === 'merge'
        ? mergeLayers(current, snapshot) as Record<string, unknown>
        : mode === 'replace'
          ? snapshot
          : (snapshot['ops'] as SettingsPathOp[]).reduce(applyPathOp, current)
      const next = deepFreeze(this.resolve(registration.schema, registration.base, section, registration.validate))
      await this.persist(ns, section)     
      this.document[ns] = section
      if (this.registrations.get(ns) === registration && !this.isStopped()) {
        this.bumpRevision(registration, current, section)
        this.commit(registration, next, 'update')
      }
    })
    this.writeQueues.set(ns, run)
    return run
  }
}
```

上面是经过简化的版本，旨在提供基本的写入流程：

- 根据指定的命名空间提取对应的`SettingsRegistration`对象；
- 根据更新模式将提供的输入改造成适合后续更新操作的**形状**：
  - mutate：`{ ops: input }`
  - 其他：input
- 调用`cloneJsonShaped`函数以此形状生成快照；
- 从`writeQueues`字典中提取针对当前命名空间的写入操作调用量，然后将针对当前写入的操作纳入此调用链，并生成新的`Promise`，后者添加到`writeQueues`中作为当前命名空间的配置写入链。

至于具体的写入操作逻辑，依赖于具体的三种写入模式，具体流程为：

- 如果传入了`expectedRevision`，会进行版本验证，验证失败则抛出异常；
- 调用`section`方法根据命名空间从`document`字典中提取配置内容，根据写入模式对它实施更新并得到更新后的配置内容：
  - **merge**：调用`mergeLayers`方法针对上面创建的快照实施合并；
  - **replace**：直接上面创建的快照；
  - **mutate**：根据指定的指令、路径和更新值（针对`set`指令）实施修改。
- 调用`resolve`方法实施三层合并并深度冻结生成最终的配置对象；
- 调用`persist`方法对最新的配置实施持久化；
- 将新的配置对象保存到`document`字典中覆盖当前的内容；
- 比较先后内容，并在确定不一致的前提下提升版本；
- 调用`commit`方法让更新生效并对外发送通知，`source`参数此时被设置为`update`（加载时被设置为`provider`）

## 6. 以软依赖方式注册配置

[DeepSeek Harness插件内核-17：将针对服务的硬依赖转换成软依赖](https://blog.csdn.net/JaydenAI/article/details/166839098)中，我介绍了一种技能在插件中消费某个服务，自身的生命周期又不受依赖服务影响的编程模式。考虑到很多插件都会在统一的配置服务中注册属于自己的配置，但是又不希望自身的生命周期受到配置服务自身的可用状态改变的影响，此时就会使用到`installSection`方法。

```typescript
export abstract class SettingsProvider extends Service {
  installSection<const Namespace extends string, T>(
    owner: Context,
    ns: Namespace & SettingsNamespaceInput<Namespace>,
    schema: z<T>,
    entry: T,
    hooks: SettingsSectionHooks<T>): void {
        const scope = this.register<Namespace, T>(ns, schema, {
            base: entry,
            ...hooks.validate === undefined ? {} : { validate: hooks.validate },
        })
        hooks.setSource(() => scope.get())
        this.ctx.effect(() => () => {
            if (isUnloading(owner)) return
            hooks.setSource(() => entry)
            hooks.onChange()
        })
        hooks.onChange()
        scope.watch(() => {
            if (isUnloading(owner)) return
            hooks.onChange()
        })
  }
}
export interface SettingsSectionHooks<T> {
  setSource(current: () => T): void
  onChange(): void
  validate?: (value: T) => void
}
```

在大部分情况下，我们会采用[DeepSeek Harness插件内核-17：将针对服务的硬依赖转换成软依赖](https://blog.csdn.net/JaydenAI/article/details/166839098)介绍的方式插件中通过调用`inject`方法注册子插件的方式，并在子插件内调用这个`installSection`方法来安装属于插件自身的配置。我们以这个场景介绍该方法的几个参数：

- **owner**：配置拥有者，也就是主插件对应的`Context`，当前`Context`与子插件绑定在一起；
- **ns**：为注册的配置指定的命名空间；
- **schema**：作为schemastery schema的`z<T>`对象；
- **entry**：当配置服务不可用时的兜底配置；
- **hooks**：用来检测配置服务下线和配置更新的钩子，它具体提供了如下三个钩子方法：
  - **setSource**：用来像插件推送配置；
  - **onChange**：用来检测配置的更新；
  - **validate**：用来验证配置的有效性。

我们同样以上述的`installSection`方法调用场景来介绍它的执行流程：

- 将`entry`和`hooks`的`validate`函数作为基准配置和验证函数调用`register`方法完成配置的注册，并得到返回的`SettingsScope<T>`对象；
- 调用`SettingsScope<T>`的`get`方法得到当前配置，并调用`hooks`的`setSource`方法推送配置；
- 调用当前Context（针对子插件）的`effect`方法注册配置服务下线的回调（由于子插件仅仅设计针对`installSection`方法的调用，导致它下线的唯一因素就是作为唯一依赖的配置服务下线），回调函数会在确定主插件并未卸载的情况下，调用`hooks`的`setSource`方法推送entry参数设置的兜底配置，并同时调用`onChange`方法通知配置更新；
- 调用`SettingsScope<T>`对象的watch方法监控配置更新，通过调用`hooks`的`onChange`方法发送通知。
