# [DeepSeek Harness深度拆解-19]通过继承SettingsProvider构建自己的配置系统

[DeepSeek Harness深度拆解-18:DSH配置服务设计详解](https://blog.csdn.net/JaydenAI/article/details/166883464)围绕着`SettingsProvider`对DSH的配置系统的设计进行了系统的梳理，这是我们对配置系统进行定制的基础。在这篇文章中，我么将通过继承这个抽象的`SettingsProvider`，提供一个简单的将内存字典作为数据源的配置系统。

## 1. 基于内存的配置系统

如下这个`MemorySettingsProvider`派生于抽象类`SettingsProvider`，使用构造函数提供的`Record<string, unknown>`对象作为配置源，同时绑定到`config`字段上。本着怎么简单怎么来的原则，我们只定义了不得不重写的三个抽象成员。其中`writable`返回`true`以支持配置的写入，`load`方法将`config`字段作为加载的配置，`persist`方法则将指定的持久化配置写入`config`字段。

```typescript
import { Context } from '@deepseek-ai/cordis'
import {SettingsProvider,SettingsNamespace} from '@deepseek-ai/dsh-settings'
import z from '@deepseek-ai/schemastery'

class MemorySettingsProvider extends SettingsProvider{
    readonly writable: boolean
    constructor(ctx: Context,private config:Record<string, unknown> ) {
        super(ctx)  
        this.writable = true
    }
  protected  load(): Promise<Record<string, unknown>>{
    return Promise.resolve(this.config)
  }
  protected  persist(ns: SettingsNamespace, section: Record<string, unknown>): Promise<void>{
     this.config[ns] = section
     return Promise.resolve()
  }
}
```

## 2. 配置的注册和读取

`MemorySettingsProvider`虽然简单，但是该有的功能基本都有。接下来我们借助它来进一步演示DSH配置系统的基本编程模式。为了将原始的配置数据解析成对应类型的配置对象，我们需要为每个通过命名空间标识的配置节提供一个匹配的schemastery schema，这也是`register`方法的核心目标。简单起见，我们定义了如下所示的`Config`接口来表示配置的结构，`ConfigSchema`则是基于该接口的Schema对象。值得一提的是创建的Schema为四个字段都定义了默认值。

```typescript
import { Context } from '@deepseek-ai/cordis'
import {SettingsProvider,SettingsNamespace} from '@deepseek-ai/dsh-settings'
import z from '@deepseek-ai/schemastery'

...
interface Config{
    foobar:{foo: string, bar:string}
    baz:string
    qux:string
}

const FoobarScheama:z<{foo:string, bar:string}> = z.object({
    foo: z.string().default("schema_default_foo"),        
    bar: z.string().default("schema_default_bar"),
})
const ConfigSchema:z<Config> = z.object({
    foobar:FoobarScheama,
    baz: z.string().default("schema_default_baz"),        
    qux: z.string().default("schema_default_qux")
})

const ctx = new Context()
const source = {test:{qux:"user_qux"}}
ctx.plugin(MemorySettingsProvider, source)
ctx.inject(["settings"], ctx=> ctx.settings.register("test",ConfigSchema, {
    base: {baz:"base_baz", qux:"base_qux"},
    applies: 'live'
}))
ctx.inject(["settings"], ctx=>{
    console.log(JSON.stringify(ctx.settings.get("test"),null,2))
})
```

输出：

```json
{
  "foobar": {
    "foo": "schema_default_foo",
    "bar": "schema_default_bar"
  },
  "baz": "base_baz",
  "qux": "user_qux"
}
```

我们调用`plugin`方法将`MemorySettingsProvider`注册到创建的`Context`上，并将常量`source`作为其配置源，对应的值为`{test:{qux:"user_qux"}}`。在通过`inject`方法注册的插件中，我们调用`ctx.settings.register`方法完成了基于`ConfigSchema`的配置注册，指定的命名空间为`test`。我们同时利用`options`参数的`base`和`applies`字段指定了配置基准（`{baz:"base_baz", qux:"base_qux"}`）和生效的方式（`live`）。在另一个采用相同方式注册的插件中，我们调用`ctx.settings.get`方法将`test`命名空间对应的配置对象序列化成JSON并输出。从输出可以印证上一篇文章介绍的基于**schema默认值 => composition base => 用户层**的三层组合机制。

## 3. 配置的三种更新方式

`SettingsProvider`通过定义的`update`、`mutate`和`replace`三个方法提供了针对配置的三种更新模式，即增量合并、基于路径的`set`和`unset`以及全量替换。在如下的演示程序中，我们在调用`inject`方法注入`settings`服务注册的插件中依次调用了上述三个方法，并在每个更新之后调用`ctx.settings.get`方法提取配置对象，将以JSON的形式进行输出。

```typescript
import { Context } from '@deepseek-ai/cordis'
import {SettingsProvider,SettingsNamespace} from '@deepseek-ai/dsh-settings'
import z from '@deepseek-ai/schemastery'
...
const ctx = new Context()
const source = {test:{qux:"user_qux"}}
ctx.plugin(MemorySettingsProvider, source)
ctx.inject(["settings"], async ctx=>{
    ctx.settings.register("test",ConfigSchema, {
        base: {baz:"base_baz", qux:"base_qux"},
        applies: 'live'
    })

    await ctx.settings.update("test",{foobar:{foo: "111"}, bar: "111"})
    console.log(JSON.stringify(ctx.settings.get("test"),null, 2))

    await ctx.settings.mutate("test",[{op:"set", path:["foobar","bar"], value:"222"}])
    console.log(JSON.stringify(ctx.settings.get("test"),null, 2))

    await ctx.settings.replace("test", {foobar:{bar:"333"}, qux:"333"})
    console.log(JSON.stringify(ctx.settings.get("test"),null, 2))
})
```

输出的三段JSON格式的配置：

```json
{
  "foobar": {
    "foo": "111",
    "bar": "schema_default_bar"
  },
  "baz": "base_baz",
  "qux": "user_qux",
  "bar": "111"
}
```

```json
{
  "foobar": {
    "foo": "111",
    "bar": "222"
  },
  "baz": "base_baz",
  "qux": "user_qux",
  "bar": "111"
}
```

```json
{
  "foobar": {
    "foo": "schema_default_foo",
    "bar": "333"
  },
  "baz": "base_baz",
  "qux": "333"
}
```

由于配置的更新流程最终会涉及到用于持久化配置的`persist`方法的调用，所以按照如下的方式在更新后输出配置源对象，我们也可以看到类似的变化。由于持久化的内容并非当前配置的全量快照，而是根据当前加载内容进行更新的结果。具体来说，如果采用`replace`模式，持久化的就是指定的那个对象。对于其他两种模式，被用来持久化的是基于当前加载内容进行合并和修改（`set`和`unset`）后的结果。这一点充分体现在输出的JSON上。

```typescript
        base: {baz:"base_baz", qux:"base_qux"},
        applies: 'live'
    })

    await ctx.settings.update("test",{foobar:{foo: "111"}, bar: "111"})
    console.log(JSON.stringify(source,null, 2))

    await ctx.settings.mutate("test",[{op:"set", path:["foobar","bar"], value:"222"}])
    console.log(JSON.stringify(source,null, 2))

    await ctx.settings.replace("test", {foobar:{bar:"333"}, qux:"333"})
    console.log(JSON.stringify(source,null, 2))
})
```

输出的三段JSON格式的配置：

## 4. 监控配置的更新

如果在注册配置的是由将`options`的`applies`字段设置成`live`（默认值），针对配置的更新可以得到实时的应用。`register`方法返回的`SettingsScope<T>`提供了`watch`方法帮助我们实时监控配置的更新。至于更新的来源，可以是来自与绑定的配置源，也可以源自对上述三个方法的调用。

### 4.1 内部更新

如下的程序演示针对内部更新（在注册的插件中调用`ctx.settings.update`方法更新配置）的监控。具体来说，在调用`register`方法完成配置的注册并得到返回的`SettingsScope<T>`对象后，我们调用其`watch`方法注册了一个在配置更新时会自动调用的回调，并输出更新前后的配置。

```typescript
import { Context } from '@deepseek-ai/cordis'
import {SettingsProvider,SettingsNamespace} from '@deepseek-ai/dsh-settings'
import z from '@deepseek-ai/schemastery'

...
const ctx = new Context()
const source = {test:{qux:"user_qux"}}
ctx.plugin(MemorySettingsProvider, source)
ctx.inject(["settings"], async ctx=>{
    const scopedSettings = ctx.settings.register("test",ConfigSchema, {
        base: {baz:"base_baz", qux:"base_qux"},
        applies: 'live'
    })

    scopedSettings.watch((next, prev)=>{
        console.log(`
detect settings' change:
prev: 
${JSON.stringify(prev, null, 2)}
next: 
${JSON.stringify(next, null, 2)}`)
    }) 
})
ctx.inject(["settings"], async ctx=> ctx.settings.update("test",{foobar:{bar: "222"}}))
```

输出：

```markdown
detect settings' change:
prev: 
{
  "foobar": {
    "foo": "schema_default_foo",
    "bar": "schema_default_bar"
  },
  "baz": "base_baz",
  "qux": "user_qux"
}
next: 
{
  "foobar": {
    "foo": "schema_default_foo",
    "bar": "222"
  },
  "baz": "base_baz",
  "qux": "user_qux"
}
```

### 4.2 外部更新

对于我们自定义的`MemorySettingsProvider`来说，它的配置源来源于一个`Record<string, unknown>`对象。当我们从外部更新了此对象时，需要手工发送一个更新通知，所以我们为`MemorySettingsProvider`额外定义了一个`notifyChange`方法，该方法直接调用`publish`方法重新发布更新后的配置。对于`@deepseek-ai/dsh-settings-file`默认提供的基于文件的配置系统，这项功能可以通过检测文件的变更来实现。

```typescript
class MemorySettingsProvider extends SettingsProvider{    
  public notifyChange(){
    this.publish(this.config)
  }
}
```

我们将上面演示程序中配置的更新方式改成基于配置源的外部更新。具体来说，我们在最后注册的插件中直接修改了作为配置源的`source`，然后在调用上面定义的`notifyChange`方法。

```typescript
import { Context } from '@deepseek-ai/cordis'
import {SettingsProvider,SettingsNamespace} from '@deepseek-ai/dsh-settings'
import z from '@deepseek-ai/schemastery'

...
const ctx = new Context()

const source = {test:{qux:"user_qux"}}
ctx.plugin(MemorySettingsProvider, source)
ctx.inject(["settings"], async ctx=>{
    const scopedSettings = ctx.settings.register("test",ConfigSchema, {
        base: {baz:"base_baz", qux:"base_qux"},
        applies: 'live'
    })
    scopedSettings.watch((next, prev)=>{
        console.log(`
detect settings' change:
prev: 
${JSON.stringify(prev, null, 2)}
next: 
${JSON.stringify(next, null, 2)}`)
    }) 
})
ctx.inject(["settings"],  ctx=>{
    (source.test as any)["baz"] = "222";
    (ctx.settings as MemorySettingsProvider).notifyChange()
} )
```

输出：

```markdown
detect settings' change:
prev: 
{
  "foobar": {
    "foo": "schema_default_foo",
    "bar": "schema_default_bar"
  },
  "baz": "base_baz",
  "qux": "user_qux"
}
next: 
{
  "foobar": {
    "foo": "schema_default_foo",
    "bar": "222"
  },
  "baz": "base_baz",
  "qux": "user_qux"
}
```

### 4.3 注册settings/updated事件

对于每次配置的更新，除了执行监视器的钩子函数外，还会触发一个名为`settings/updated`的事件，我们也可以通过此事件得到配置变更的通知。作为事件的处理函数，我们不仅可以利用事件参数得到命名空间和更新前后的配置对象外，还可以得到用以区分内部和外部更新的`SettingsUpdateSource`（`provider`或者`update`）。和其他基于Scope的事件通知机制（事件只能向上传播）不同，该事件时面向全局的，没有Scope的限制。在如下的演示程序中，我们在一个独立注册的插件中注册了`settings/updated`事件，并利用指定的回调函数输出了配置的命名空间、更新来源和更新前后的值。在另一个注册的插件中，我们分别实施了内部和外部更新。

```typescript
import { Context } from '@deepseek-ai/cordis'
import {SettingsProvider,SettingsNamespace} from '@deepseek-ai/dsh-settings'
import z from '@deepseek-ai/schemastery'


const ctx = new Context()
const source = {test:{qux:"user_qux"}}
ctx.plugin(MemorySettingsProvider, source)

ctx.plugin(ctx=>ctx.on("settings/updated",(ns, next, prev, source)=>console.log(`
detect settings' change:
ns: ${ns}
source: ${source}
prev: 
${JSON.stringify(prev, null, 2)}
next: 
${JSON.stringify(next, null, 2)}`)))

ctx.inject(["settings"], ctx=> {
    ctx.settings.register("test",ConfigSchema, {
        base: {baz:"base_baz", qux:"base_qux"},
        applies: 'live'
    });
    (source.test as any)["baz"] = "222";
    (ctx.settings as MemorySettingsProvider).notifyChange()
    ctx.settings.update("test",{foobar:{foo:"333"}})
})
```
