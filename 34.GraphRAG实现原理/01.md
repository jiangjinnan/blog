# [GraphRAG实现原理-01]让LLM基于构建的知识图谱回答问题

GraphRAG是一种结构化的、分层的检索增强生成 (RAG) 方法，它不同于使用纯文本片段的简单语义搜索方法。GraphRAG的流程包括：从原始文本中提取知识图谱，构建社群层级结构，为这些社群生成摘要，然后在执行基于 RAG 的任务时利用这些结构。

## 1. GraphRAG V.S Baseline RAG

RAG是一种利用真实世界信息改进逻辑逻辑模型（LLM）输出的技术。该技术是大多数基于LLM的工具的重要组成部分，大多数RAG方法都使用向量相似度作为搜索技术，我们称之为基线Baseline RAG。GraphRAG利用知识图谱，在推理复杂信息时显著提升问答性能。RAG技术在帮助逻辑学习模型 (LLM) 处理私有数据集方面展现出潜力，这里的私有数据集是指LLM未接受过训练且从未见过的数据，例如企业的专有研究、业务文档或通信记录。基线 RAG 的创建旨在帮助解决这个问题，但我们观察到Baseline RAG在某些情况下表现非常糟糕：

- Baseline RAG难以将各个信息点联系起来。这种情况发生在回答问题需要梳理分散的信息，并分析它们之间的共同属性，从而得出新的综合见解时；
- 当被要求全面理解大型数据集甚至单个大型文档中的概括语义概念时，Baseline RAG的表现很差。

为了解决这个问题，技术界正在努力开发扩展和增强RAG的方法。微软研究院的新方法GraphRAG 基于输入语料库创建知识图谱。该图谱与社区摘要和图机器学习输出一起，用于在查询时增强提示信息。GraphRAG 在回答上述两类问题方面表现出显著的改进，展现出超越以往方法的智能或精湛技术。

这个系列我们将介绍GraphRAG的基本编程模式以及背后的实现原理，以及如何对它进行扩展。并通过一个简单的示例来演示如何使用GraphRAG来构建知识图谱并进行问答。

## 1. 安装和初始化GraphRAG

我们先来安装GraphRAG并初始化一个新的项目，请确保你已经安装了Python 3.8或更高版本。如下的脚本在激活的Python虚拟环境中在执行`python -m pip install graphrag`命令后，执行`graphrag init`对GraphRAG进行了初始化。出现提示时，请指定您希望在配置中使用的默认聊天和嵌入模型，以及API-KEY。

```bash
mkdir graphrag_explor
cd graphrag_quickstart
python -m venv .venv
.venv\Scripts\activate
python -m pip install graphrag
graphrag init
```

GraphRAG舒适化的过程会在指定的目录下创建如下的目录结构。其中prompts中会包含一系列预定义的提示词模板，他们服务于GraphRAG的知识图谱构建（这个过程被成为索引）和在此基础上的查询。`.env`文件作为环境变量文件中会包含你在初始化时输入的API-KEY，`settings.yaml`是GraphRAG的配置文件，它会提供默认的配置。

```markdown
graphrag_explor
  ├── prompts
  ├── .env
  └── settings.yaml
```

## 2. 修改配置文件

`settings.yaml`提供的配置非常丰富，我们将在后续文章中对每个配置进行介绍，这里我从中摘出如下几个配置节。

```yaml
## LLM settings
completion_models:
  default_completion_model:
    model_provider: openai
    api_base: https://eap2410.openai.azure.com/openai/v1
    model: gpt-5.4-mini
    auth_method: api_key # or azure_managed_identity
    api_key: ${GRAPHRAG_API_KEY} # set this in the generated .env file, or remove if managed identity
    retry:
      type: exponential_backoff
    api_version: 2024-02-15-preview 
embedding_models:
  default_embedding_model:
    model_provider: openai
    model: text-embedding-3-small
    api_base: https://eap2410.openai.azure.com/openai/v1
    auth_method: api_key
    api_key: ${GRAPHRAG_API_KEY}
    retry:
      type: exponential_backoff
    api_version: 2024-02-15-preview 

## Storage settings
input_storage:
  type: file # [file, blob, cosmosdb]
  base_dir: "input"
output_storage:
  type: file # [file, blob, cosmosdb]
  base_dir: "output"

## Document processing settings
input:
  type: csv # [csv, text, json, jsonl]
chunking:
  type: tokens
  size: 1200
  overlap: 100
  encoding_model: o200k_base

## Caching settings
cache:
  type: json # [json, memory, sqlite, none]
  storage:
    type: file # [file, blob, cosmosdb]
    base_dir: "cache"

## Vector store settings
vector_store:
  type: lancedb
  db_uri: output\lancedb
  vector_size: 1536

extract_claims:
  enabled: true
  completion_model_id: default_completion_model
  prompt: "prompts/extract_claims.txt"
  description: "Any claims or facts that could be relevant to information discovery."
  max_gleanings: 1
```

上述的配置主要划分为如下几类：

- **LLM**：这里设置了两类LLM，一种是服务于知识图谱构建和最终用来查询的LLM（completion_models），另一种用来将文本转换成嵌入向量并存入销量数据库（embedding_models）。这里我指定的分别是`gpt-5.4-mini`和`text-embedding-3-small`（默认为`text-embedding-3-normal`）；
- **存储**：`input_storage`和`output_storage`是对输入和输出存储的配置，输入存储提供构建知识图谱的原始内容，构建的支持图谱体现为一系列的表（Table）和向量数据库，它们保证在输出存储中。GraphRAG默认提供了`file`, `blob`和`CosmosDB`三种存储，这里我选择的是基于文件系统的`file`，并设置了对应的目录（`input`和`ouput`）；
- **文档处理**：`input`利用`type`提供了输入文件的格式，这里我使用了`csv`（默认为text）。`chunking`用来设置如何将大文档切割成利于处理的切片（chunk），具体包括长度计量方式（tokens）、切片长度、重叠部分长度和编码方式；
- **cache**：由于用来构建知识图谱的索引过程会频繁调用LLM，一般会通过缓存LLM响应内容节约成本（Token）和提高效率，`cache`设置了缓存内容的格式和存储；
- **vector_store**：GraphRAG并没有放弃向量数据库，但是向量数据库在GraphRAG和Baseline RAG中的使用方式完全不同。GraphRAG主要利用它来实现针对实体相似度的检索。这里使用的是lancedb，由于使用的嵌入模式为`text-embedding-3-small`，所里这里设置的维度（1536）需要与之匹配。我们利用db_uri的设置将lancedb输出到output目录下；
- **extract_claims**：知识图谱除了会提取实体和关系这些静态规则外，还会以声明（Claim）的方式提取发生在某个实体上的离散事件。这个开关默认是关闭的，我们通过这个配置节将其打开。

## 3. 构建知识图谱

所谓的知识图谱构建的构建，就是利用预定义的执行管道读取提供的原始数据，然后将其转换成标准文本，并重中提取实体（Entity）、关系（Relationship）、声明（Claim），并最终构建基于层级社区（Community）结构的知识图谱的过程。上面将输入存储设置为目录为input的文件系统，所以我们将承载原始数据的data.csv文件中。

```markdown
graphrag_explor
  └── input  
      └── data.csv
```

data.csv文件内容如下，相当于一个4*3的表格，它从四个维度（选址、产品、营销和供应链）描述了李明如何经营他的咖啡馆。我们将基于这个内容来构建一个简单的知识图谱，并在此基础上实时基于自然语言的查询。


管道的执行并不是单纯地将前序任务的执行结构直接交给后序任务进行处理，而且会对每项索引任务的输出进行持久化。对于我们的例子来说，所有的索引结果都会保存在`output`目录下。

```markdown
graphrag_explor 
  └── output
        ├── lancedb
        ├── documents.parquet
        ├── entities.parquet
        ├── relationships.parquet        
        ├── text_units.parquet
        ├── covariates.parquet.parquet        
        ├── community.parquet        
        ├── community_reports.parquet 
        ├── stats.json
        └── context.json
```

根据上图所示的目录结构，我们会发现输出的内容由如下四部分组成：

- **.parquet文件**： 生成的标准化文档（`documents.parquet`）、切片/文本单元（`text_units.parquet`）、实体（`entities.parquet`）、关系（`relationships.parquet` ）、声明（`covariates.parquet`）、社区（`community.parquet`）和社区报告（`community_reports.parquet`）相关的Table，它们对应采用列式存储的`.parquet`文件；
- **lancedb**：向量数据库，这里默认使用的是l`ancedb`；
- **stats.json**：每一项索引任务针对耗时、内存使用和处理数据量的统计信息
- **context.json**：索引流水线的上下文/状态信息

## 4. 查询知识图谱

索引工作完成之后，我们就可以执行graphrag query命令根据指定的指令针对构建的知识图谱进行查询了。这是针对查询*李明在经营咖啡店过程中遇到了哪些风险，分别采取了什么应对措施？*查询结果。文中出现的类似`[Data: Reports (1, 3, 0)]`的内容是GraphRAG生成答案时自动附加的结论溯源标记，表示这句话的结论来源于索引中编号为 1、3、0 的社区报告（对应于community_reports.parquet文件对应的Table）

```bash
(.venv) E:\graphrag\graphrag_explor>graphrag query "李明在经营咖啡店过程中遇到了哪些风险，分别采取了什么应对措施？"
## 李明经营咖啡店面临的风险与应对措施

李明在经营咖啡店过程中，主要遇到了**供应链中断风险、选址带来的经营不确定性、以及开业初期获客与流量获取风险**。他针对这些风险分别采取了相应措施，以提升门店的稳定性、客流确定性和经营连续性 [Data: Reports (1, 3, 0)]。

首先，**供应链风险**较为直接。2024年7月，由于雨季运输延误，门店曾出现**两天缺货**，估计造成约**四千元损失**。为避免再次发生断供问题，李明随后**增加了第二家供应商作为备份**，以降低对单一供应渠道的依赖，增强供货稳定性 [Data: Reports (1)]。这一做法也说明他原先对本地乳企供奶存在依赖，而天气和运输变化会放大断货风险，因此备用供应商对维持经营连续性很重要 [Data: Reports (1)]。

其次，李明在**门店选址**上也面临经营风险。他在**学校附近、写字楼商圈和老城区街角**之间权衡时，需要同时考虑客流、租金和客户结构。学校附近虽然客流高，但租金也高；老城区街角租金低，但年轻客群较少。最终，他选择了**写字楼商圈**，看重的是相对稳定的工作日客流和较为可控的租金，这样可以降低经营不确定性 [Data: Reports (3, 0)]。

第三，李明在**获客初期**还面临流量获取不足的风险。为此，他主要借助**小红书和抖音**进行引流，争取开业初期的曝光和潜在客户。同时，他在**2024年6月建立会员体系**，并通过**充值赠送**等活动促进会员增长和复购，减少对一次性流量的依赖 [Data: Reports (0)]。此外，他还通过与**周边书店、健身房**开展合作互推来分散获客压力、降低获客成本，借助本地商户联动补充自有流量不足并扩大客户来源 [Data: Reports (0)]。

总体来看，李明的应对思路是围绕“**降低单点依赖、增强稳定性、分散风险**”展开：在供应上增加备用渠道，在选址上平衡客流与租金，在获客上同时使用内容平台、会员机制和本地合作来提升流量韧性 [Data: Reports (1, 3, 0)]。
```

原始内容涉及三个人李明、王芳和张伟，我们问它三个人是什么关系，得到的答案是准确的。

```bash

## 关系判断

从现有数据看，**李明、王芳和张伟并没有形成一个完整的三人直接关系链**。三人都与李明经营的咖啡店有关，但证据只支持以下两组关系：

- **李明与王芳**：存在明确的门店经营协作关系。王芳是店长，并就会员折扣和复购率提升向李明提出建议，说明她在门店运营中承担辅助管理角色，而李明负责整体经营决策 [Data: Reports (0)]。
- **李明与张伟**：存在供应链关系。张伟是来自云南普洱的咖啡豆供应商，按月向门店供货，说明他是李明咖啡店的上游供应端之一 [Data: Reports (2)]。

## 结论

目前**没有证据表明王芳与张伟之间存在直接关系**，也**没有证据表明张伟直接与王芳发生业务往来**。因此，能确认的是：
**李明分别与王芳、张伟存在业务联系，但王芳和张伟之间的关系未被数据明确支持** [Data: Reports (0, 2)]。
```
