# [GraphRAG实现原理-04]构建知识图谱的索引管道

[GraphRAG实现原理-02:基于社区（Community）的知识图谱](https://jaydenai.blog.csdn.net/article/details/168962194)介绍了组成整个知识图谱的5张表，它们连同向量数据库都是调用`graphrag index`命令实时索引（Indexing）的产物。整个索引是一个预先编排好的Sequential类型的工作流，但是这里不能叫工作流，叫管道（Pipeline），工作流（Workflow）是对组成管道的单个处理步骤的称呼。如果你了解LangChain，可以将Pipeline和Workflow分别视为Chain和`Runnable`，而`Runable`可大可小，Agent就是一个`Runnable`对象，本质上也是一个Workflow。

## 1. Pipeline

`Pipeline`类型的定义非常简单。如代码所示，一个`Pipelin`对象本质上就是一组Workflow对象的有序组合。`Workflow`则是一个基于`[str, WorkflowFunction]`二元组，前者返回`Workflow`的名称，后者利用`WorkflowFunction`对象承载具体的操作。`run`方法仅仅利用`yield from`的形式以生成器的方式依次返回组成管道的`[str, WorkflowFunction]`二元组。`names`方法返回组成当前管道的`Workflow`名称列表，`remove`方法则用来将指定的`Workflow`从管道中移除。

```python
class Pipeline:
    def __init__(self, workflows: list[Workflow]):
        self.workflows = workflows

    def run(self) -> Generator[Workflow]:
        yield from self.workflows

    def names(self) -> list[str]:
        return [name for name, _ in self.workflows]

    def remove(self, name: str) -> None:
        self.workflows = [w for w in self.workflows if w[0] != name]

Workflow = tuple[str, WorkflowFunction]
```

## 2. WorkflowFunction

承载`Workflow`操作的`WorkflowFunction`是一个异步函数。它具有两个参数，`GraphRagConfig`表示GraphRAG完整的配置，`PipelineRunContext`则表示管道执行上下文。执行后的输出被封装在`WorkflowFunctionOutput`对象中。

```python
WorkflowFunction = Callable[
    [GraphRagConfig, PipelineRunContext],
    Awaitable[WorkflowFunctionOutput],
]

class WorkflowFunctionOutput:
    result: Any | None
    stop: bool = False
```

作为执行后输出内容的`WorkflowFunctionOutput`只有两个字段：

- **result**：工作流函数的结果。这可以是任何内容，我们仅将其用于下游**日志记录**，并期望每个工作流函数将正式输出写入提供的存储空间。
- **stop**： 此标志用于指示工作流是否应在此函数执行后停止。仅当继续执行可能导致不稳定故障时才应使用此标志。

由于`GraphRagConfig`承载的配置太多，我不打算在这里介绍这个类型，而是选择在使用到具体配置的时候作针对性介绍。我们下来看看作为管道执行上下文的`PipelineRunContext`类型的定义。

```python
@dataclass
class PipelineRunContext:
    stats: PipelineRunStats
    input_storage: Storage
    output_storage: Storage
    output_table_provider: TableProvider
    previous_table_provider: TableProvider | None
    cache: Cache
    callbacks: WorkflowCallbacks
    state: PipelineState

PipelineState = dict[Any, Any]
```

各个上下文字段说明如下：

- **stats**：当前管道运行的统计信息（`PipelineRunStats`），用于记录运行指标。
- **input_storage**：用于读取输入文档的存储实例。
- **output_storage**：pipeline 各步骤使用的长期输出存储，写入的内容会落到存储提供者中。
- **output_table_provider**：用于读写输出表的`TableProvider`。
- **previous_table_provider**：`update`模式（代表对知识图谱的增量更新，与之相对的基于全量的初始化）下用于读取上一轮管道运行结果的`TableProvider`，可为`None`。
- **cache**：用于读取此前LLM响应的缓存实例。
- **callbacks**：管道运行期间调用的工作流回调。
- **state**：任意属性的运行时状态包，用于持久化预计算结果或实验性功能。

[GraphRAG实现原理-03：针对Table和Storage的抽象](https://jaydenai.blog.csdn.net/article/details/169133473)提供了针对Table、TableProvider和Storage的详细介绍。

### 2.1 管道运行统计

`PipelineRunStats`用于记录一次管道运行的统计指标，包括总运行时长、文档数量、输入加载耗时，以及各工作流的执行指标。各字段均提供默认值，便于在运行过程中逐步累加填充。

```python
@dataclass
class PipelineRunStats:
    total_runtime: float = field(default=0)
    num_documents: int = field(default=0)
    update_documents: int = field(default=0)
    input_load_time: float = field(default=0)
    workflows: dict[str, WorkflowMetrics] = field(default_factory=dict)
```

各个统计字段说明如下：

- **total_runtime**：总运行时长，浮点数，默认0。
- **num_documents**：文档数量，整数，默认0。
- **update_documents**：更新文档数量，整数，默认0。
- **input_load_time**：输入加载耗时，浮点数，默认0。
- **workflows**：各工作流执行指标的字典，键为工作流名称、值为`WorkflowMetrics`，默认空字典。

`WorkflowMetrics`用于记录单个工作流一次执行的性能指标，包括实际耗时和基于**tracemalloc**的内存统计。它作为`PipelineRunStats.workflows`字典的值，帮助分析各工作流的耗时与内存开销。

```python
@dataclass
class WorkflowMetrics:
    overall: float
    peak_memory_bytes: int
    memory_delta_bytes: int
    tracemalloc_overhead_bytes: int
```

### 2.2 LLM响应缓存

索引过程中需要频繁调用LLM，为了加速索引的速度和节省Token，针对LLM响应结果的缓存是必要的。具体的缓存操作定义在如下这个Cache抽象类中，它定义了一套异步的键值缓存操作契约，涵盖读取、批量读取、写入、存在性判断、删除、清空，以及派生命名子缓存等能力。`get_many`方法提供了基于`get`的默认批量实现，其余方法均为抽象方法，由具体子类实现底层存储细节。

```python
class Cache(ABC):
    @abstractmethod
    def __init__(self, *, storage: Storage | None, **kwargs: Any) -> None

    @abstractmethod
    async def get(self, key: str) -> Any

    async def get_many(self, keys: Sequence[str]) -> dict[str, Any]

    @abstractmethod
    async def set(self, key: str, value: Any, debug_data: dict | None = None) -> None

    @abstractmethod
    async def has(self, key: str) -> bool

    @abstractmethod
    async def delete(self, key: str) -> None

    @abstractmethod
    async def clear(self) -> None

    @abstractmethod
    def child(self, name: str) -> Cache
```

如下这个`CacheType`枚举提供了四种缓存选项，它们分别对应JSON文件、内存和Sqlite作为存储的实现。而Noop选项，自然代表不对LLM响应实施缓存。下面给出了四种对应`Cache`类型的`__init__`方法的声明。

```python
class CacheType(StrEnum):
    Json = "json"
    Memory = "memory"
    Noop = "none"
    Sqlite = "sqlite"

class MemoryCache(Cache):
    def __init__(self, **kwargs: Any) -> None

class JsonCache(Cache):
    def __init__(
        self,
        storage: Storage | dict[str, Any] | None = None,
        **kwargs: Any,
    ) -> None

class SQLiteCache(Cache):
    def __init__(
        self,
        storage: Storage | dict[str, Any] | None = None,
        database_name: str = "cache.db",
        *,
        namespace: str = "",
        **_: Any,
    ) -> None

class NoopCache(Cache):
    def __init__(self, **kwargs: Any) -> None
```

`GraphRagConfig`定义了针对缓存的配置节，具体的类型为`CacheConfig`。我们通过`type`字段设置对应的类型，并利用`storage`和`database_name`为`Json`和`Sqlite`选项设置对应的存储的数据库名称。[GraphRAG实现原理-01:让LLM基于构建的知识图谱回答问题](https://blog.csdn.net/JaydenAI/article/details/168961798)演示了如果执行`graphrag index`命令实施索引，索引结束后会在`output/cache`目录下为涉及LLM调用的Workflow生成响应的缓存文件。

```python
class CacheConfig(BaseModel):
    model_config = ConfigDict(extra="allow")
    type: str = Field(
        description="The cache type to use. Builtin types include 'Json', 'Memory', 'Noop', and 'Sqlite'.",
        default=CacheType.Json,
    )
    storage: StorageConfig | None = Field(
        description="The storage configuration to use for storage-backed caches such as 'Json' and 'Sqlite'.",
        default_factory=lambda: StorageConfig(type=StorageType.File, base_dir="cache"),
    )
    database_name: str = Field(
        description="The SQLite database name within the configured file storage. Used only when type is 'Sqlite'.",
        default="cache.db",
    )
```

GraphRAG还定义了如下这个用来生成缓存键的`CacheKeyCreator`协议，以及用来根据指定输入参数生成缓存键的`create_cache_key`函数。从实现可以看出，`create_cache_key`采用对输入参数进行**hash**的方式生成缓存键。

```python
@runtime_checkable
class CacheKeyCreator(Protocol):
    def __call__(
        self,
        input_args: dict[str, Any],
    ) -> str

def create_cache_key(input_args: dict[str, Any]) -> str:"
    return hash_data(input_args)
```

### 2.3 管道执行回调

`PipelineRunContext`的`callbacks`返回一个`WorkflowCallbacks`对象。`WorkflowCallbacks`是一个Protocol，定义了一组用于监控工作流执行的回调接口，覆盖整个管道的启动与结束、单个工作流的启动与结束、进度更新，以及错误发生等关键事件。它作为一个"noop"基类契约，客户端只需实现自己关心的方法即可，无需实现全部回调。

```python
class WorkflowCallbacks(Protocol):
    def pipeline_start(self, names: list[str]) -> None:
        ...
    def pipeline_end(self, results: list[PipelineRunResult]) -> None:
        ...
    def workflow_start(self, name: str, instance: object) -> None:
        ...
    def workflow_end(self, name: str, instance: object) -> None:
        ...
    def progress(self, progress: Progress) -> None:
        ...
    def pipeline_error(self, error: BaseException) -> None:
        ...
```

各个回调方法说明如下：

- **pipeline_start**：整个管道开始时触发的回调，接收本次运行涉及的工作流名称列表。
- **pipeline_end**：整个管道结束时触发的回调，接收各 pipeline 运行结果列表。
- **workflow_start**：单个工作流开始时触发的回调，接收工作流名称和实例对象。
- **workflow_end**：单个工作流结束时触发的回调，接收工作流名称和实例对象。
- **progress**：进度更新时触发的回调，接收进度信息对象。
- **pipeline_error**：管道中发生错误时触发的回调，接收异常对象。

## 3. PipelineFactory

代表GraphRAG索引管道的`Pipeline`最终由作为管道工厂的`PipelineFactory`来创建。如代码所示，`PipelineFactory`提供了`workflows`和`pipelines`这两个字典类型的类字段作为全局`Workflow`和`Pipeline`的注册表，字典的Key为注册名称。`register`、`register_all`和`register_pipeline`三个方法则用来完成具体的注册工作。

```python
class PipelineFactory:
    workflows: ClassVar[dict[str, WorkflowFunction]] = {}
    pipelines: ClassVar[dict[str, list[str]]] = {}

    @classmethod
    def register(cls, name: str, workflow: WorkflowFunction):
        cls.workflows[name] = workflow

    @classmethod
    def register_all(cls, workflows: dict[str, WorkflowFunction]):
        for name, workflow in workflows.items():
            cls.register(name, workflow)

    @classmethod
    def register_pipeline(cls, name: str, workflows: list[str]):
        cls.pipelines[name] = workflows

    @classmethod
    def create_pipeline(
        cls,
        config: GraphRagConfig,
        method: IndexingMethod | str = IndexingMethod.Standard,
    ) -> Pipeline:
        workflows = config.workflows or cls.pipelines.get(method, [])
        return Pipeline([(name, cls.workflows[name]) for name in workflows])
```

我们可以调用`create_pipeline`方法根据指定的`config`和`method`来创建`Pipeline`对象。该方法的实现非常简单：如果指定的`GraphRagConfig`提供了Workflow列表，则使用它，否则就利用指定的`method`参数从`pipelines`注册表中提取所有的`Workflow`列表，然后基于此列表创建返回的`Pipeline`对象。

### 3.1 四种索引方法

我们在调用`PipelineFactory`的`create_pipeline`方法创建`Pipeline`对象的时候，可以利用`method`参数指定管道的注册名称，也可以指定如下这个`IndexingMethod`枚举。`IndexingMethod`用于指定GraphRAG建索引时采用的方法。它区分标准/快速两种建图策略，并分别提供全量与增量更新两种模式，共四个取值。

```python
class IndexingMethod(str, Enum):
    Standard = "standard"
    Fast = "fast"
    StandardUpdate = "standard-update"
    FastUpdate = "fast-update"
```

四种索引方法说明如下：

- **Standard**：值为`standard`，传统GraphRAG索引方式，图构建与摘要全部由语言模型完成。
- **Fast**：值为`fast`，快速索引方式，使用NLP进行图构建、语言模型仅负责摘要。
- **StandardUpdate**：值为`standard-update`，基于标准索引的增量更新模式。
- **FastUpdate**：值为`fast-update`，基于快速索引的增量更新模式。

四种索引方法最终体现在索引管道的结构上面。说得更具体一下，体现在对应索引管道由哪些`Workflow`组成，它们采用怎样得顺序。GraphRAG初始化的时候会以如下的方式完整四个管道的注册。
