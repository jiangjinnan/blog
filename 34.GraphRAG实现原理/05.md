# [GraphRAG实现原理-05]知识图谱索引管道的完整执行流程

[GraphRAG实现原理-04:构建知识图谱的索引管道](https://jaydenai.blog.csdn.net/article/details/169133995)详细介绍了用来构建知识图谱的索引管道以及创建方式，在本篇文章中我们将重点介绍这个管道的执行原理。通过这篇文章，我们将会对执行`graphrag index`和`graphrag update`命令提取并执行管道的流程有一个清晰的认识。

## 1. 调用run方法对Workflow进行迭代

通过前文对`Pipeline`类型的介绍我们知道，它的`run`方法仅仅利用返回的生成器实现对组成管道的所有`Workflow`迭代而已。由于`Workflow`仅仅是一个`[str, WorkflowFunction]`二元组，所以每次迭代我们会得到Workflow的注册名称和承载其功能操作的`WorkflowFunction`对象。如果需要真正执行指定的管道，我们还得去执行迭代生成的`WorkflowFunction`对象。

```python
class Pipeline:
    def __init__(self, workflows: list[Workflow]):
        self.workflows = workflows
    def run(self) -> Generator[Workflow]:
        yield from self.workflows

Workflow = tuple[str, WorkflowFunction]
```

按照上述的原理，我们编写了如下这个演示程序。我们定义了`build_workflow`函数根据指定的名称创建对应的`Workflow`。`Workflow`的`WorkflowFunction`函数执行的唯一操作就是属性一段指示性的文字用来确定当前`Workflow`是否被调用。在main函数中，我们调用此函数创建了三个分别命名为foo、bar和baz的三个`Workflow`，并利用它们构建了一个Pipeline。接下来我们调用其run方法，对返回的`Workflow`进行迭代，并利用创建的`GraphRagConfig`和`PipelineRunContext`作为参数调用`WorkflowFunction`函数。

```python
import asyncio
from graphrag.index.typing.workflow import Workflow,WorkflowFunctionOutput
from graphrag.index.typing.pipeline import Pipeline
from graphrag.config.models.graph_rag_config import GraphRagConfig
from graphrag.index.typing.context import PipelineRunContext
from graphrag.index.run.utils import create_run_context

def build_workflow(name:str)-> Workflow:
    async def invoke(config:GraphRagConfig, context: PipelineRunContext):
        print(f"Workflow {name} is executed.")
        return WorkflowFunctionOutput(f"reuslt_of_{name}")
    return (name, invoke)
async def main():   
    pipeline = Pipeline(workflows=[build_workflow(name) for name in ("foo","bar","baz")])
    for (_, func) in pipeline.run():
        await func(GraphRagConfig(), create_run_context())

asyncio.run(main())
```

输出：

```text
Workflow foo is executed.
Workflow bar is executed.
Workflow baz is executed.
```

## 2. 创建PipelineRunContext上下文

从上面的演示程序可以看出，我们执行`WorkflowFunction`函数指定的`PipelineRunContext`是利用如下这个`create_run_context`函数创建的。

```python
def create_run_context(
    input_storage: Storage | None = None,
    output_storage: Storage | None = None,
    output_table_provider: TableProvider | None = None,
    previous_table_provider: TableProvider | None = None,
    cache: Cache | None = None,
    callbacks: WorkflowCallbacks | None = None,
    stats: PipelineRunStats | None = None,
    state: PipelineState | None = None,
) -> PipelineRunContext:
    input_storage = input_storage or MemoryStorage()
    output_storage = output_storage or MemoryStorage()
    return PipelineRunContext(
        input_storage=input_storage,
        output_storage=output_storage,
        output_table_provider=output_table_provider
        or ParquetTableProvider(storage=output_storage),
        previous_table_provider=previous_table_provider,
        cache=cache or MemoryCache(),
        callbacks=callbacks or NoopWorkflowCallbacks(),
        stats=stats or PipelineRunStats(),
        state=state or {},
    )
```

从定义可以看出，`create_run_context`函数为创建的`PipelineRunContext`很多上下文成员进行了兜底：

- **input_storage/output_storage**：MemoryStorage()；
- **output_table_provider**：ParquetTableProvider(storage=output_storage);
- **cache**:MemoryCache();
- **callbacks**:NoopWorkflowCallbacks();
- **stats**: PipelineRunStats;
- **state**: {}

## 3. Pipeline完整执行流程

如下这个`_run_pipeline`函数体现了GraphRAG基于指定`PipelineRunContext`上下文的执行流程

```python
async def _run_pipeline(
    pipeline: Pipeline,
    config: GraphRagConfig,
    context: PipelineRunContext,
) -> AsyncIterable[PipelineRunResult]:
    start_time = time.time()
    last_workflow = "<startup>"
    try:
        await _dump_stats_json(context)
        await _dump_context_json(context)

        logger.info("Executing pipeline...")
        for name, workflow_function in pipeline.run():
            last_workflow = name
            context.callbacks.workflow_start(name, None)

            with WorkflowProfiler() as profiler:
                result = await workflow_function(config, context)

            context.callbacks.workflow_end(name, result)
            yield PipelineRunResult(
                workflow=name, result=result.result, state=context.state, error=None
            )
            context.stats.workflows[name] = profiler.metrics
            await _dump_stats_json(context)
            if result.stop:
                logger.info("Halting pipeline at workflow request")
                break

        context.stats.total_runtime = time.time() - start_time
        logger.info("Indexing pipeline complete.")
        await _dump_stats_json(context)
        await _dump_context_json(context)

    except Exception as e:
        logger.exception("error running workflow %s", last_workflow)
        yield PipelineRunResult(
            workflow=last_workflow, result=None, state=context.state, error=e
        )
```

我们简单说说整个函数的正常的执行流程：

- 调用`_dump_stats_json`函数输出`PipelineRunContext`的`stats`字段上的统计数据（默认输出到`./output/stats.json`）；
- 调用`_dump_context_json`函数输出`PipelineRunContext`的`state`字段上的状态（默认输出到`./output/context.json`）；
- 遍历调用`Pipeline`的`run`方法返回的每个`Workflow`：
  - 执行`WorkflowCallbacks`的`workflow_start`回调；
  - 将创建的`WorkflowProfiler`作为上下文调用Workflow的`WorkflowFunction`函数，其目的在于利用这个上下文记录`WorkflowMetrics`指标；
  - 执行`WorkflowCallbacks`的`workflow_end`回调；
  - 创建`PipelineRunResult`对象来封装`Workflow`执行的结果和状态，利用`yield`语句输出；
  - 将`WorkflowProfiler`收集的`WorkflowMetrics`指标存储到`PipelineRunContext`的`stats`字段的`workflows`字典中（针对`Workflow`的指标）中；
  - 调用`_dump_stats_json`函数输出`PipelineRunContext`的`stats`字段上的统计数据;
  - 如果返回`WorkflowFunctionOutput`的`stop`字段为`True`，表明希望中止管道后续部分的执行，此时直接中止循环。
- 将管道执行耗时写入`PipelineRunContext`的`stats`字段；
调用`_dump_stats_json`函数输出`PipelineRunContext`的`stats`字段上的统计数据;
- 调用`_dump_context_json`函数输出`PipelineRunContext`的`state`字段上的状态。

`_run_pipeline`函数返回一个`AsyncIterable[PipelineRunResult]`对象，`PipelineRunResult`用于记录单个工作流一次执行的结果，包括工作流名称、函数返回值、运行期间的管道状态以及可能发生的错误。它作为`WorkflowCallbacks.pipeline_end`等处的输入，便于在运行结束后汇总和检查各工作流的执行情况。

```python
@dataclass
class PipelineRunResult:
    workflow: str
    result: Any | None
    state: PipelineState
    error: BaseException | None
```

## 4. Pipeline两种执行模式

索引管道具有两种执行模式。一种是基于全量的初始化模式，另一种基于增量更新模式。它们的执行逻辑是不一样的，具体体现在如下这个`run_pipeline`函数中，`is_update_run`参数用来区分这两种执行模式。从代码可以看出，在开启基于执行模式的分支之前，会根据提供的配置创建作为输入输出存储的`Storage`（`input_storage`和`output_storage`），用来读写数据表的`TableProvider`（`output_table_provider`）和用来缓存LLM响应结果的`Cache`（`cache`）。还会从输出存储中提取上下文状态（`state`），如果利用`additional_context`参数提供了额外上下文，会将它们存储到此状态中。

```python
async def run_pipeline(
    pipeline: Pipeline,
    config: GraphRagConfig,
    callbacks: WorkflowCallbacks,
    is_update_run: bool = False,
    additional_context: dict[str, Any] | None = None,
    input_documents: pd.DataFrame | None = None,
) -> AsyncIterable[PipelineRunResult]:

    input_storage = create_storage(config.input_storage)
    output_storage = create_storage(config.output_storage)
    output_table_provider = create_table_provider(config.table_provider, output_storage)
    cache = create_cache(config.cache)
    state_json = await output_storage.get("context.json")
    state = json.loads(state_json) if state_json else {}

    if additional_context:
        state.setdefault("additional_context", {}).update(additional_context)

    if is_update_run:
        logger.info("Running incremental indexing.")

        update_storage = create_storage(config.update_output_storage)
        update_timestamp = time.strftime("%Y%m%d-%H%M%S")
        timestamped_storage = update_storage.child(update_timestamp)
        delta_storage = timestamped_storage.child("delta")
        update_base_provider = create_table_provider(
            config.table_provider, update_storage
        )
        update_table_provider = update_base_provider.child(update_timestamp)
        delta_table_provider = update_table_provider.child("delta")
        previous_table_provider = update_table_provider.child("previous")

        await _copy_previous_output(output_table_provider, previous_table_provider)
        state["update_timestamp"] = update_timestamp

        if input_documents is not None:
            await delta_table_provider.write_dataframe("documents", input_documents)
            pipeline.remove("load_update_documents")

        context = create_run_context(
            input_storage=input_storage,
            output_storage=delta_storage,
            output_table_provider=delta_table_provider,
            previous_table_provider=previous_table_provider,
            cache=cache,
            callbacks=callbacks,
            state=state,
        )

    else:
        logger.info("Running standard indexing.")
        if input_documents is not None:
            await output_table_provider.write_dataframe("documents", input_documents)
            pipeline.remove("load_input_documents")

        context = create_run_context(
            input_storage=input_storage,
            output_storage=output_storage,
            output_table_provider=output_table_provider,
            cache=cache,
            callbacks=callbacks,
            state=state,
        )

    async for table in _run_pipeline(
        pipeline=pipeline,
        config=config,
        context=context,
    ):
        yield table
```

对于基于全量的初始化，处理逻辑很简单：

- 如果利用`input_documents`参数以`DataFrame`形式提供了输入文档，意味着无需执行`load_input_documents`这个用来加载输入文档的Workflow；
- 调用上面介绍的`create_run_context`函数创建`PipelineRunContext`上下文；
- 调用上面介绍的`_run_pipeline`函数基于指定的`PipelineRunContext`上下文执行管道，并实时返回输出的`PipelineRunResult`对象。

对于基于增量更新，处理逻辑会复杂一些，两种的不同之处主要体现在`PipelineRunContext`上下文的`output_storage`、`output_table_provider`和`previous_table_provider`字段上。针对着三个字段的提供方法如下：

- **output_storage**：
  - 从配置的`update_output_storage`字段提取用于更新的存储配置，并调用`create_storage`函数创建对应的`Storage`；
  - 调用`Storage`的`child`方法基于当前时间戳创建一个子存储；
  - 返回调用子存储的`child`方法创建一个命名为`delta`的子存储。
- **output_table_provider**：  
  - 从配置的`update_output_storage`字段提取用于更新的存储配置，并调用`create_table_provider`函数创建一个基准`TableProvider`；
  - 调用`TableProvider`的`child`方法基于当前时间戳创建一个子`TableProvider`；
  - 返回调用子`TableProvider`的`child`方法创建一个命名为`delta`的子`TableProvider`。
- **previous_table_provider**：
  - 得到上面根据当前时间戳创建一个子`TableProvider`，调用其child方法创建一个名为`previous`的子`TableProvider`；
  - 调用`_copy_previous_output`函数将`output_table_provider`中的Table悉数拷贝到这个子`TableProvider`上。

`run_pipeline`函数基于两种模式执行指定`Pipeline`涉及到定义在`GraphRagConfig`中的如下这些配置选项：输入、输出和更新的存储配置（`input_storage`、`output_storage`和`update_output_storage`）、用来读写数据表的`TableProvider`配置（`table_provider`）和LLM响应缓存配置(`cache`)。

```python
class GraphRagConfig(BaseModel):
    input_storage: StorageConfig = Field(
        description="The input storage configuration.",
        default=StorageConfig(
            base_dir=graphrag_config_defaults.input_storage.base_dir,
        ),
    )
    output_storage: StorageConfig = Field(
        description="The output configuration.",
        default=StorageConfig(
            base_dir=graphrag_config_defaults.output_storage.base_dir,
        ),
    )
    update_output_storage: StorageConfig = Field(
        description="The output configuration for the updated index.",
        default=StorageConfig(
            base_dir=graphrag_config_defaults.update_output_storage.base_dir,
        ),
    )
    table_provider: TableProviderConfig = Field(
        description="The table provider configuration.", default=TableProviderConfig()
    )
    cache: CacheConfig = Field(
        description="The cache configuration.",
        default=CacheConfig(**asdict(graphrag_config_defaults.cache)),
    )
```

## 5. 索引的构建

上面这个`run_pipeline`函数最终会在如下这个`build_index`函数中被调用。顾名思义，这个函数用来最终构建知识图谱的索引。该函数会利用`method`指定的索引方法来创建作为管道的`Pipeline`对象，并交给`run_pipeline`函数执行。

```python
async def build_index(
    config: GraphRagConfig,
    method: IndexingMethod | str = IndexingMethod.Standard,
    is_update_run: bool = False,
    callbacks: list[WorkflowCallbacks] | None = None,
    additional_context: dict[str, Any] | None = None,
    verbose: bool = False,
    input_documents: pd.DataFrame | None = None,
) -> list[PipelineRunResult]:   
    init_loggers(config=config, verbose=verbose)
    workflow_callbacks = (
        create_callback_chain(callbacks) if callbacks else NoopWorkflowCallbacks()
    )
    outputs: list[PipelineRunResult] = []
    logger.info("Initializing indexing pipeline...")
    method = _get_method(method, is_update_run)
    pipeline = PipelineFactory.create_pipeline(config, method)

    workflow_callbacks.pipeline_start(pipeline.names())

    async for output in run_pipeline(
        pipeline,
        config,
        callbacks=workflow_callbacks,
        is_update_run=is_update_run,
        additional_context=additional_context,
        input_documents=input_documents,
    ):
        outputs.append(output)
        if output.error is not None:
            logger.error("Workflow %s completed with errors", output.workflow)
            workflow_callbacks.pipeline_error(output.error)
        else:
            logger.info("Workflow %s completed successfully", output.workflow)
        logger.debug(str(output.result))

    workflow_callbacks.pipeline_end(outputs)
    return outputs
```

`build_index`函数构建所以的流程如下：
- 调用`create_callback_chain`函数将指定的`WorkflowCallbacks`列表串联成链（最终体现为一个`WorkflowCallbacksManager`对象）。如果没有提供任何的`WorkflowCallbacks`，则使用`NoopWorkflowCallbacks`兜底；
- 调用`_get_method`个根据指定的索引方法（`method`）和执行模式（`is_update_run`）确定管道注册的名称：
  - **is_update_run == False**：索引方法即为管道注册的名称；
  - **is_update_run == True**：索引方法加上`-update`后缀即为管道注册的名称。
- 调用`PipelineFactory.create_pipeline`方法根据配置和管道注册名称创建对应的`Pipeline`；
- 执行`WorkflowCallbacks`的`pipeline_start`回调；
- 调用`run_pipeline`函数执行指定创建的管道，并收集每个`Workflow`返回的`PipelineRunResult`；
- 执行`WorkflowCallbacks`的`pipeline_end`回调。

单纯来看`_get_method`方法的逻辑是有问题的，因为`IndexingMethod`枚举提供的四种索引方法已经包含了两种基于增量更新管道名称（`standard-update`和`fast-update`），不过命令行在执行的时候会对此参数进行验证。

```python
def _get_method(method: IndexingMethod | str, is_update_run: bool) -> str:
    m = method.value if isinstance(method, IndexingMethod) else method
    return f"{m}-update" if is_update_run else m

class IndexingMethod(str, Enum):
    Standard = "standard"
    Fast = "fast"
    StandardUpdate = "standard-update"
    FastUpdate = "fast-update"
```

## 6. graphrag index/update命令行

全量初始化索引和增量更新索引最终通过执行`graphrag index`和`graphrag update`命令，它们分别具有如下所示的命令行参数：

- graphrag index

| 选项 | 说明 |
| --- | --- |
| `-r, --root <directory>` | 项目根目录。[默认值：`/home/runner/work/graphrag/graphrag`] |
| `-m, --method <standard\|fast\|standard-update\|fast-update>` | 要使用的索引方法。[默认值：`standard`] |
| `-v, --verbose` | 以详细日志模式运行索引流水线。 |
| `--dry-run` | 在不执行任何步骤的情况下运行索引流水线，用于检查和验证配置。 |
| `--cache / --no-cache` | 是否使用LLM缓存。[默认值：`cache`] |
| `--skip-validation` | 跳过任何预检验证。当运行不涉及LLM的步骤时很有用。 |

- graphrag update

| 选项 | 说明 |
| --- | --- |
| `-r, --root <directory>` | 项目根目录。[默认值：`/home/runner/work/graphrag/graphrag`] |
| `-m, --method <standard\|fast\|standard-update\|fast-update>` | 要使用的索引方法。[默认值：`standard`] |
| `-v, --verbose` | 以详细日志模式运行索引流水线。 |
| `--cache / --no-cache` | 是否使用LLM 缓存。[默认值：`cache`] |
| `--skip-validation` | 跳过任何预检验证。当运行不涉及LLM的步骤时很有用。 |

如果没有将`--dry-run`参数设置为true，上述两个命令的执行最终都会调用上述的`build_index`函数，它们的区别体现在传入的`is_update_run`参数上。配置文件`settings.yaml`被加载生成`GraphRagConfig`对象。根据上面对`build_index`函数的分析，我们会发现说明上面针对`--method`参数的说明不对。该参数只有两个选项`standard`和`fast`，`build_index`函数会根据`is_update_run`参数将其转换成对应管道的注册名称。所以针`graphrag index standard-update`和`graphrag update  standard-update`命令行的执行都会出错。
