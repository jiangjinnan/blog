# [GraphRAG实现原理-09]调用LLM提取实体关系图

GraphRAG的Graph本质上是从输入文档中提取出来的实体关系图。这张图以抽取的实体作为节点，实体之间的关系作为边的五向图。实体关系图的提取是整个索引管道最核心的部分，此功能是通过`standard`管道中命名为`extract_graph`的`Workflow`完成。

## 1. 我们现在在哪里？

这是`standard`管道系列的第四篇文章，`extract_graph`也是我们介绍的四个`Workflow`。经过前面的三道工序，我们已经拥有了`documents`和`text_units`两个表，前者存储完整的文档，后者存储分割文档生成的切片，两者之间通过`text_unit_ids`和`document_id`保持双向溯源。

```markdown
load_input_documents
    └── create_base_text_units
            └── create_final_documents
                    └── **extract_graph**
                            └── finalize_graph
                                    └── extract_covariates
                                            └── create_communities
                                                    └── create_final_text_units
                                                            └──create_community_reports
                                                                    └── generate_text_embeddings
```

## 2. LLMCompletion

实体类关系图的提取需要解决LLM的利用，`LLMCompletion`是`graphrag-llm`包中针对文本补齐的**Completion模型**的抽象基类，定义了所有补全提供者必须遵循的统一契约。它并不直接实现具体的模型调用，而是通过抽象方法约束子类完成实际的文本生成工作。

```python
class LLMCompletion(ABC):
    @abstractmethod
    def __init__(
        self,
        *,
        model_id: str,
        model_config: "ModelConfig",
        tokenizer: "Tokenizer",
        metrics_store: "MetricsStore",
        metrics_processor: "MetricsProcessor | None" = None,
        rate_limiter: "RateLimiter | None" = None,
        retrier: "Retry | None" = None,
        cache: "Cache | None" = None,
        cache_key_creator: "CacheKeyCreator",
        **kwargs: Any,
    )

    @abstractmethod
    def completion(
        self,
        /,
        **kwargs: Unpack["LLMCompletionArgs[ResponseFormat]"],
    ) -> "LLMCompletionResponse[ResponseFormat] | Iterator[LLMCompletionChunk]"

    @abstractmethod
    async def completion_async(
        self,
        /,
        **kwargs: Unpack["LLMCompletionArgs[ResponseFormat]"],
    ) -> "LLMCompletionResponse[ResponseFormat] | AsyncIterator[LLMCompletionChunk]"
       

    @contextmanager
    def completion_thread_pool(
        self,
        *,
        response_handler: "ThreadedLLMCompletionResponseHandler",
        concurrency: int,
        queue_limit: int = 0,
    ) -> "Iterator[ThreadedLLMCompletionFunction]"        

    def completion_batch(
        self,
        completion_requests: list["LLMCompletionArgs[ResponseFormat]"],
        *,
        concurrency: int,
        queue_limit: int = 0,
    ) -> list["LLMCompletionResponse[ResponseFormat] | Iterator[LLMCompletionChunk] | Exception"]       

    @property
    @abstractmethod
    def metrics_store(self) -> "MetricsStore"

    @property
    @abstractmethod
    def tokenizer(self) -> "Tokenizer"
```

初始化一个`LLMCompletion`对象需要提供如下的参数：

- **model_id**: 模型标识符，用于指定要调用的语言模型，例如`"openai/gpt-4o"`。它是工厂创建补全实例和路由到对应提供者的关键依据。
- **model_config**: 语言模型的配置对象，承载模型相关的参数设置。它为补全实例提供初始化所需的模型级配置信息。
- **tokenizer**: 使用的分词器实例，负责Token计数与编解码。它在补全流程中支撑提示词Token统计和上下文窗口控制。
- **metrics_store**: 指标存储实例，用于记录补全调用的运行指标。它为成本追踪、性能监控等横切能力提供数据落点。
- **metrics_processor**: 指标处理器，可选，默认`None`。它在指标写入前对数据进行加工或转换，未配置时跳过该处理环节。
- **rate_limiter**: 限流器，可选，用于控制补全请求的发送速率。它帮助避免超出厂商配额或保护下游服务不被突发流量压垮。
- **retrier**: 重试策略，可选，定义失败请求的重试行为。它在遇到瞬时错误时自动重试，提升补全调用的可靠性。
- **cache**: 嵌入缓存，可选，用于缓存补全结果。命中缓存时可跳过实际模型调用，降低延迟与成本。
- **cache_key_creator**: 缓存键生成函数，可选，负责将请求参数映射为缓存键。它决定缓存命中与复用的粒度，未配置时可能使用默认键策略。
- **kwargs**: 额外关键字参数，用于传递扩展配置。它为子类实现或自定义行为留出灵活的注入空间。

`LLMCompletion`定义了如下这些方法和属性：

- **completion**: 抽象同步补全方法，接收消息、结构化响应格式、流式开关及采样参数等。它返回补全响应或流式块迭代器，是同步调用路径的统一入口。
- **completion_async**: 抽象异步补全方法，参数与同步版保持一致，返回响应或异步流式迭代器。它为高并发场景提供非阻塞的补全调用能力。
- **completion_thread_pool**: 上下文管理器方法，启动补全线程池并按并发数与队列上限调度请求。它产出可提交请求的函数，并通过回调处理每个响应，支持背压控制。
- **completion_batch**: 批量补全方法，使用线程池并行处理多个请求。它按请求原始顺序返回响应或异常，便于调用方批量获取结果。
- **metrics_store**: 抽象属性，返回指标存储实例。它对外暴露补全调用的指标落点，供监控与成本追踪读取。
- **tokenizer**: 抽象属性，返回所使用的分词器实例。它对外暴露分词能力，供Token计数与上下文控制使用。

### 2.1 两种预定义LLMCompletion类型

GraphRAG提供了两种预定`LLMCompletion`类型，它们分别对应如下这个`LLMProviderType`枚举的两个选项。`LiteLLMCompletion`是GraphRAG基于LiteLLM的默认补全实现，负责调用各类大模型完成文本生成。它以中间件管道方式集成缓存、指标采集、限流与重试，并提供同步与异步两种补全入口，支持结构化输出解析。

`MockLLMCompletion`是用于测试和离线开发的模拟补全实现，从配置中读取预置响应字符串并循环返回，不发起真实模型调用。它不支持流式输出，但会按需解析结构化响应，便于在无API环境下验证GraphRAG流程。

```python
class LLMProviderType(StrEnum):
    LiteLLM = "litellm"
    MockLLM = "mock"

class LiteLLMCompletion(LLMCompletion):
    def __init__(
        self,
        *,
        model_id: str,
        model_config: "ModelConfig",
        tokenizer: "Tokenizer",
        metrics_store: "MetricsStore",
        metrics_processor: "MetricsProcessor | None" = None,
        rate_limiter: "RateLimiter | None" = None,
        retrier: "Retry | None" = None,
        cache: "Cache | None" = None,
        cache_key_creator: "CacheKeyCreator",
        azure_cognitive_services_audience: str = "https://cognitiveservices.azure.com/.default",
        drop_unsupported_params: bool = True,
        **kwargs: Any,
    ) -> None

class MockLLMCompletion(LLMCompletion):
    def __init__(
        self,
        *,
        model_config: "ModelConfig",
        tokenizer: "Tokenizer",
        metrics_store: "MetricsStore",
        **kwargs: Any,
    ) -> None
```

### 2.3 LLMCompletion的创建

GraphRAG同样采用一贯的工厂模式来创建`LLMCompletion`对象。具体来说，它定义了派生自`Factory[LLMCompletion]`的`CompletionFactory`类型，并利用`register_completion`函数将`LLMCompletion`初始化函数基于指定的类型注册到全局`CompletionFactory`对象上。GraphRAG最终调用`create_completion`函数来提供所需的`LLMCompletion`对象。

```python
class CompletionFactory(Factory["LLMCompletion"])

completion_factory = CompletionFactory()

def register_completion(
    completion_type: str,
    completion_initializer: Callable[..., "LLMCompletion"],
    scope: "ServiceScope" = "transient",
) -> None

def create_completion(
    model_config: "ModelConfig",
    *,
    cache: "Cache | None" = None,
    cache_key_creator: "CacheKeyCreator | None" = None,
    tokenizer: "Tokenizer | None" = None,
) -> "LLMCompletion"
```

`create_completion`函数会自动调用`register_completion`完成注册工作。对于`LLMProviderType.LiteLLM`类型，会采用单例的形式进行注册，意味着多次提取的`LiteLLMCompletion`其实是同一个对象。此函数最终自然是调用全局`CompletionFactory`对象的`create`方法来提供返回的`LLMCompletion`对象。

### 3.2 实体关系图提取配置 

这个实体关系图的提取涉及两种目的的LLM调用，一种是单纯地提取实体和关系，另一种则是生成描述实体的摘要信息。`GraphRagConfig`利用`extract_graph`。`GraphRagConfig`的`extract_graph`字段返回一个`ExtractGraphConfig`对象，用于控制从文本单元中抽取实体与关系的核心行为，其字段直接决定抽取阶段使用哪个模型、抽取哪些类型的实体、以及追问补抽的轮数等关键参数。

```python
class GraphRagConfig(BaseModel):
    extract_graph: ExtractGraphConfig = Field(
        description="The entity extraction configuration to use.",
        default=ExtractGraphConfig(),
    )
    summarize_descriptions: SummarizeDescriptionsConfig = Field(
        description="The description summarization configuration to use.",
        default=SummarizeDescriptionsConfig(),
    )

class ExtractGraphConfig(BaseModel):
    completion_model_id: str = Field(
        description="The model ID to use for text embeddings.",
        default=graphrag_config_defaults.extract_graph.completion_model_id,
    )
    model_instance_name: str = Field(
        description="The model singleton instance name. This primarily affects the cache storage partitioning.",
        default=graphrag_config_defaults.extract_graph.model_instance_name,
    )
    prompt: str | None = Field(
        description="The entity extraction prompt to use.",
        default=graphrag_config_defaults.extract_graph.prompt,
    )
    entity_types: list[str] = Field(
        description="The entity extraction entity types to use.",
        default=graphrag_config_defaults.extract_graph.entity_types,
    )
    max_gleanings: int = Field(
        description="The maximum number of entity gleanings to use.",
        default=graphrag_config_defaults.extract_graph.max_gleanings,
    )
    def resolved_prompts(self) -> ExtractGraphPrompts
```

各配置选项说明如下：

- **completion_model_id**: 指定抽取阶段使用的补全模型 ID，决定调用哪个已配置的模型实例执行实体抽取任务。默认值为`default_completion_model`。
- **model_instance_name**: 模型单例实例名称，主要影响缓存存储的分区，有助于提升缓存命中率与隔离性。默认值为`extract_graph`。
- **prompt**: 自定义实体抽取提示词的文件路径，为`None`时回退到内置的 `GRAPH_EXTRACTION_PROMPT`。
- **entity_types**: 允许抽取的实体类型白名单，约束LLM只识别指定类别的实体，避免输出无关类型。默认值为`["organization", "person", "geo", "event"]`
- **max_gleanings**: 追问补抽的最大轮数，轮数越多召回率越高但成本也越大。默认值为`1`。
- **resolved_prompts**: 运行时解析最终使用的抽取提示词，配置了路径则读取文件内容，否则使用内置提示词常量。

这是我们实例演示程序的`settings.yaml`提供的`extract_graph`配置节的定义，它利用`completion_model_id`(`default_completion_model`)引用了定义在`completion_models`节点中的Completion模型。

```yaml
extract_graph:
  completion_model_id: default_completion_model
  prompt: "prompts/extract_graph.txt"
  entity_types: [organization,person,geo,event]
  max_gleanings: 1
```

### 3.3 汇总描述摘要配置

由于实体关系图的提取是针对单个TextUnit进行的，单个实体和关系会重复出现。独立生成的实体和关系的描述都是片面的，所以最终还需要针对单一实体和关系的一组描述听给LLM，并由其生成一条完整的摘要描述。`SummarizeDescriptionsConfig`用来提供与摘要描述生成相关的配置，`GraphRagConfig`的`summarize_descriptions`字段返回的正是这个对象。`SummarizeDescriptionsConfig`和`ExtractGraphConfig`涉及一些共享的配置选项，而`max_length`和`max_input_tokens`则用来控制输入的Token数量和输出的文本长度。

```python
class GraphRagConfig(BaseModel):
    summarize_descriptions: SummarizeDescriptionsConfig = Field(
        description="The description summarization configuration to use.",
        default=SummarizeDescriptionsConfig(),
    )

class SummarizeDescriptionsConfig(BaseModel):
    completion_model_id: str = Field(
        description="The model ID to use for summarization.",
        default=graphrag_config_defaults.summarize_descriptions.completion_model_id,
    )
    model_instance_name: str = Field(
        description="The model singleton instance name. This primarily affects the cache storage partitioning.",
        default=graphrag_config_defaults.summarize_descriptions.model_instance_name,
    )
    prompt: str | None = Field(
        description="The description summarization prompt to use.",
        default=graphrag_config_defaults.summarize_descriptions.prompt,
    )
    max_length: int = Field(
        description="The description summarization maximum length.",
        default=graphrag_config_defaults.summarize_descriptions.max_length,
    )
    max_input_tokens: int = Field(
        description="Maximum tokens to submit from the input entity descriptions.",
        default=graphrag_config_defaults.summarize_descriptions.max_input_tokens,
    )
```

## 5. Workflow的实现

`extract_graph`这个`Workflow`的`WorkflowFunction`对应如下这个`run_workflow`函数（所在模块目录为`graphrag/workflows/extract_graph`）。

```python
async def run_workflow(
    config: GraphRagConfig,
    context: PipelineRunContext,
) -> WorkflowFunctionOutput:
    reader = DataReader(context.output_table_provider)
    text_units = await reader.text_units()
    extraction_model_config = config.get_completion_model_config(
        config.extract_graph.completion_model_id
    )
    extraction_prompts = config.extract_graph.resolved_prompts()
    extraction_model = create_completion(
        extraction_model_config,
        cache=context.cache.child(config.extract_graph.model_instance_name),
        cache_key_creator=cache_key_creator,
    )

    summarization_model_config = config.get_completion_model_config(
        config.summarize_descriptions.completion_model_id
    )
    summarization_prompts = config.summarize_descriptions.resolved_prompts()
    summarization_model = create_completion(
        summarization_model_config,
        cache=context.cache.child(config.summarize_descriptions.model_instance_name),
        cache_key_creator=cache_key_creator,
    )

    entities, relationships, raw_entities, raw_relationships = await extract_graph(
        text_units=text_units,
        callbacks=context.callbacks,
        extraction_model=extraction_model,
        extraction_prompt=extraction_prompts.extraction_prompt,
        entity_types=config.extract_graph.entity_types,
        max_gleanings=config.extract_graph.max_gleanings,
        extraction_num_threads=config.concurrent_requests,
        extraction_async_type=config.async_mode,
        summarization_model=summarization_model,
        max_summary_length=config.summarize_descriptions.max_length,
        max_input_tokens=config.summarize_descriptions.max_input_tokens,
        summarization_prompt=summarization_prompts.summarize_prompt,
        summarization_num_threads=config.concurrent_requests,
    )

    await context.output_table_provider.write_dataframe("entities", entities)
    await context.output_table_provider.write_dataframe("relationships", relationships)

    if config.snapshots.raw_graph:
        await context.output_table_provider.write_dataframe(
            "raw_entities", raw_entities
        )
        await context.output_table_provider.write_dataframe(
            "raw_relationships", raw_relationships
        )
    return WorkflowFunctionOutput(
        result={
            "entities": entities,
            "relationships": relationships,
        }
    )
```

我们总结一下`Workflow`的执行流程：

- 利用`PipelineRunContext`上下文提供的`TableProvider`读取`text_units`表并转换成`DataFrame`（`text_units`）；
- 从`GraphRagConfig`的提取`ExtractGraphConfig`和`SummarizeDescriptionsConfig`配置，并进一步提取两个提示词模板；
- 利用`ExtractGraphConfig`和`SummarizeDescriptionsConfig`提供的LLM配置调用`create_completion`函数生成对应的`LLMCompletion`对象；
- 将`LLMCompletion`对象、提示词模板以及相关配置提交给`extract_graph`函数完成最终的提取工作，该函数返回如下的四元组，每个部分都是一个`DataFrame`对象：
  - **entities**：合并去重后实体列表
  - **relationships**：合并去重后关系列表
  - **raw_entities**: 合并去重前实体列表
  - **raw_relationships**：合并去重前关系列表
- 调用`TableProvider`的`write_dataframe`方法将`entities`和`relationships`写入对用的表；
- 如果`GraphRagConfig.snapshots`的配置要求保存实例和关系快照，则调用`TableProvider`的`write_dataframe`方法将`raw_entities`和`raw_relationships`写入快照。
- 以字典形式返回前5条被写入的实体和关系记录。

`extract_graph`函数的涉及代码很多，但是逻辑很清晰：

- 按照配置给定的异步模式和并发量针对每一条`TextUnit`调用LLM生成实体和关系。如果配置选项`max_gleanings > 1`，将会涉及多轮调用（通过累积消息实现Session的效果）；
- 将提取的实体和关系汇总，此时会分别为实体和关系计算`frequency`（实体出现的次数）和`weight`（所有关系`weight`之和） 调用LLM生成完整的摘要。
