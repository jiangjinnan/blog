# [GraphRAG实现原理-15]将实体、切片和社区写入向量数据库

很多人觉得GraphRAG不会像Baseline RAG那样继续使用向量数据库，其实不然。GraphRAG支持四种Query模式，Global Search主要使用`create_community_reports`这个`Workflow`构建的社区报告进行查询，但是Local Search会先用向量检索定位相关实体，再沿知识图谱扩展出关联的关系、社区报告和原始文本块，组装成上下文交给LLM。DRIFT Search在Prmier阶段会从向量数据库中检索社区报告，Follow-up节点本质上就是基于Local search的迭代。Basic Search就更不用说了，自身就是针对Baseline RAG的实现。综上所述，`standard`管道进行索引使还是需要涉及到向量数据库。

## 1. 管道的最后一个Workflow

`standard`索引管道一共包括10个`Workflow`，前面的系列文章已经介绍了9个，我们通过本篇文章介绍最后一个名为`generate_text_embeddings`的`Workflow`。这个`Workflow`会为每个`Entity`、`TextUnit`和`Community`创建一个向量。如果没有对向量数据库类型进行设置，默认会使用`lancedb`，并将数据库文件保存在`./output/lancedb`目录下。

## 2. 查看三个向量表

我们在前面演示实例的基础上编写了如下的代码来查看上述三个向量表的结构。如代码片段所示，我们创建了由`generate_text_embeddings`这个`Workflow`（对应`WorkflowFunction`函数指向`graphrag.index.workflows.generate_text_embeddings.run_workflow`）组成的`Pipeline`。在完成该管道执行后，我们链接路径`./output/lancedb`创建了一个`lancedb.db`对象，并输出每个数据表的结构。

```python
import asyncio

from graphrag.index.typing.pipeline import Pipeline
from graphrag.config.load_config import load_config
from graphrag.index.run.run_pipeline import run_pipeline
from graphrag.callbacks.noop_workflow_callbacks import NoopWorkflowCallbacks
import lancedb

async def main():   
    config = load_config(root_dir="./")
    pipeline = Pipeline(workflows=[
        ("generate_text_embeddings", generate_text_embeddings.run_workflow)
    ])
    async for _ in  run_pipeline(
        pipeline = pipeline,
        config = config,
        callbacks= NoopWorkflowCallbacks(),
    ):
        pass

    db = await lancedb.connect_async("./output/lancedb")
    table_names = await db.table_names()
    for name in table_names:
        table = await db.open_table(name)
        print(f"---------- {name} ----------")
        print(await table.schema())
        print()           
   
asyncio.run(main())
```

## 3. 向量存储

`VectorStore`是GraphRAG中所有向量存储后端的抽象基类，它定义了一套统一的文档存取与检索接口让上层查询逻辑无需关心底层究竟采用何种存储方式。

```python
class VectorStore(ABC):
    def __init__(
        self,
        index_name: str = "vector_index",
        id_field: str = "id",
        vector_field: str = "vector",
        create_date_field: str = "create_date",
        update_date_field: str = "update_date",
        vector_size: int = 3072,
        fields: dict[str, str] | None = None,
        timestamp_exploder: TimestampExploder = explode_timestamp,
        **kwargs: Any,
    )

    @abstractmethod
    def connect(self) -> None

    @abstractmethod
    def create_index(self) -> None:

    @abstractmethod
    def load_documents(self, documents: list[VectorStoreDocument]) -> None

    def insert(self, document: VectorStoreDocument) -> None

    @abstractmethod
    def similarity_search_by_vector(
        self,
        query_embedding: list[float],
        k: int = 10,
        select: list[str] | None = None,
        filters: FilterExpr | None = None,
        include_vectors: bool = True,
    ) -> list[VectorStoreSearchResult]

    def similarity_search_by_text(
        self,
        text: str,
        text_embedder: TextEmbedder,
        k: int = 10,
        select: list[str] | None = None,
        filters: FilterExpr | None = None,
        include_vectors: bool = True,
    ) -> list[VectorStoreSearchResult]

    @abstractmethod
    def search_by_id(
        self,
        id: str,
        select: list[str] | None = None,
        include_vectors: bool = True,
    ) -> VectorStoreDocument

    @abstractmethod
    def count(self) -> int

    @abstractmethod
    def remove(self, ids: list[str]) -> None

    @abstractmethod
    def update(self, document: VectorStoreDocument) -> None
```

`VectorStore`提供了如下的方法：

- **connect**：建立与向量存储的连接。
- **create_index**：创建向量索引。
- **load_documents**：批量将文档写入向量存储。
- **insert**：插入单条文档，内部委托给`load_documents`。
- **similarity_search_by_vector**：基于嵌入向量的相似度检索。
- **similarity_search_by_text**：基于文本的相似度检索。
- **search_by_id**：按ID精确取回单个文档。
- **count**：返回存储中的文档总数。
- **remove**：按 ID 列表删除文档。
- **update**：更新存储中的单个文档。

初始化一个`VectorStore`对象时需要提供如下参数：

- **index_name**：向量索引名称，默认`vector_index`。
- **id_field**：文档ID字段名，默认`id`。
- **vector_field**：向量字段名，默认`vector`。
- **create_date_field**：创建时间字段名，默认`create_date`。
- **update_date_field**：更新时间字段名，默认`update_date`。
- **vector_size**：向量维度，默认`3072`。
- **fields**：自定义字段名到类型的映射；其中`date` 类型字段会被转为字符串并自动注册时间分量字段。
- **timestamp_exploder**：时间展开函数，用于把日期字符串展开为年、月、日等分量字段，默认`explode_timestamp`。
- **kwargs**：额外关键字参数，供子类实现使用。

### 3.1 向量存储文档

`VectorStoreDocument`是GraphRAG 向量存储的统一文档模型，承载唯一 ID、可选向量、附加数据字典及创建/更新时间戳，用于在不同向量后端间统一交换数据。

```python
@dataclass
class VectorStoreDocument:
    id: str | int
    vector: list[float] | None
    data: dict[str, Any] = field(default_factory=dict)
    create_date: str | None = None
    update_date: str | None = None
```

各字段说明如下：

- **id**：文档的唯一标识符。
- **vector**：文档的向量嵌入。
- **data**：与文档关联的附加数据字典，默认空字典。
- **create_date**：文档创建时间的可选 ISO-8601时间戳。
- **update_date**：文档最后更新时间的可选ISO-8601时间戳。

### 3.2 检索结果

`VectorStoreSearchResult`是向量检索的结果封装类型，是**文档 + 相似度分数**的组合。`document`字段持有检索到的完整`VectorStoreDocument`，`score`是取值范围在-1到1之间的相似度分数，越高表示越相似。它使不同向量后端的检索返回值具有统一结构，上层可直接按分数排序或过滤。

```python
@dataclass
class VectorStoreSearchResult:
    document: VectorStoreDocument
    score: float
```

### 3.3 三种预定义向量存储

GraphRAG默认支持三种类型的向量存储，分别对应如下这个`VectorStoreType`枚举的三个选项：

```python
class VectorStoreType(StrEnum):

    AzureAISearch = "azure_ai_search"
    CosmosDB = "cosmosdb"
```

三种类型的向量存储说明如下：

- **LanceDB**：本地嵌入式向量存储，无需外部服务，数据随项目目录管理，适合开发调试与单机离线检索；

### 3.5 向量存储的创建

GraphRAG依然采用其一贯的工厂模式来创建向量存储。如代码所示，对应的工厂类型`VectorStoreFactory`派生自`Factory[VectorStore]`。`register_vector_store`函数根据指定的`ServiceScope`（`singleton`或者`transient`，默认采用后者）将`VectorStore`初始化函数注册到全局的`VectorStoreFactory`对象上，注册名称为向量存储的类型。GraphRAG最终会调用`create_vector_store`函数来创建所需的`VectorStore`。此函数最终调用`VectorStoreFactory`对象的`create`方法完成`VectorStore`的创建，并会采用Lazy Loading的方式完成注册工作。

```python
class VectorStoreFactory(Factory[VectorStore]):
vector_store_factory = VectorStoreFactory()

def register_vector_store(
    vector_store_type: str,
    vector_store_initializer: Callable[..., VectorStore],
    scope: ServiceScope = "transient",
) -> None:
    vector_store_factory.register(vector_store_type, vector_store_initializer, scope)

def create_vector_store(
    config: VectorStoreConfig, index_schema: IndexSchema
) -> VectorStore:
    strategy = config.type
    if strategy not in vector_store_factory:
        match strategy:
            case VectorStoreType.LanceDB:
                from graphrag_vectors.lancedb import LanceDBVectorStore
                register_vector_store(VectorStoreType.LanceDB, LanceDBVectorStore)
            case VectorStoreType.AzureAISearch:
                from graphrag_vectors.azure_ai_search import AzureAISearchVectorStore
                register_vector_store(
                    VectorStoreType.AzureAISearch, AzureAISearchVectorStore
                )
            case VectorStoreType.CosmosDB:
                from graphrag_vectors.cosmosdb import CosmosDBVectorStore
                register_vector_store(VectorStoreType.CosmosDB, CosmosDBVectorStore)
            case _:
                msg = f"Vector store type '{strategy}' is not registered in the VectorStoreFactory. Registered types: {', '.join(vector_store_factory.keys())}."
                raise ValueError(msg)
    config_model = config.model_dump()
    index_model = index_schema.model_dump()
    return vector_store_factory.create(
        strategy, init_args={**config_model, **index_model}
    )
```

## 4. 嵌入模型

`VectorStore`解决了嵌入向量的存储问题，嵌入向量的生成则需要对应的嵌入模型。`LLMEmbedding`是GraphRAG中对嵌入模型的抽象，这个抽象类定义了一套统一的嵌入生成接口，并内建了批处理、线程池、指标、限流、重试与缓存等横切能力的契约。

```python
class LLMEmbedding(ABC):
    @abstractmethod
    def __init__(
        self,
        *,
        model_id: str,
        model_config: "ModelConfig",
        tokenizer: "Tokenizer",
        metrics_store: "MetricsStore",
        metrics_processor: "MetricsProcessor | None" = None,
        rate_limiter: "RateLimiter | None" = None,
        retrier: "Retry | None" = None,
        cache: "Cache | None" = None,
        cache_key_creator: "CacheKeyCreator",
        **kwargs: Any,
    )

    @abstractmethod
    def embedding(
        self, /, **kwargs: Unpack["LLMEmbeddingArgs"]
    ) -> "LLMEmbeddingResponse"

    @abstractmethod
    async def embedding_async(
        self, /, **kwargs: Unpack["LLMEmbeddingArgs"]
    ) -> "LLMEmbeddingResponse"

    @contextmanager
    def embedding_thread_pool(
        self,
        *,
        response_handler: "ThreadedLLMEmbeddingResponseHandler",
        concurrency: int,
        queue_limit: int = 0,
    ) -> "Iterator[ThreadedLLMEmbeddingFunction]"

    def embedding_batch(
        self,
        embedding_requests: list["LLMEmbeddingArgs"],
        *,
        concurrency: int,
        queue_limit: int = 0,
    ) -> list["LLMEmbeddingResponse | Exception"]

    @property
    @abstractmethod
    def metrics_store(self) -> "MetricsStore"

    @property
    @abstractmethod
    def tokenizer(self) -> "Tokenizer"
```

对应方法说明：

- **embedding**：抽象同步嵌入方法，接收嵌入参数并返回嵌入响应。
- **embedding_async**：抽象异步嵌入方法，接收嵌入参数并返回嵌入响应。
- **embedding_thread_pool**：上下文管理器，创建受并发数限制、可选队列背压的嵌入线程池，产出可提交请求的函数，并通过回调处理响应。
- **embedding_batch**：基于线程池批量处理嵌入请求，按请求序号把响应或异常回填到结果列表对应位置。
- **metrics_store**：抽象属性，返回指标存储。
- **tokenizer**：抽象属性，返回分词器。

初始化一个`LLMEmbedding`需要提供如下参数：

- **model_id**：嵌入模型ID，例如`"openai/gpt-4o"`。
- **model_config**：嵌入模型的配置对象。
- **tokenizer**：使用的分词器。
- **metrics_store**：使用的指标存储。
- **metrics_processor**：可选的指标处理器。
- **rate_limiter**：可选的限流器。
- **retrier**：可选的重试策略。
- **cache**：可选的嵌入缓存。
- **cache_key_creator**：可选的缓存键创建函数，输入参数字典返回字符串键。
- **kwargs**：额外的关键字参数。

### 4.2 LLMEmbedding的创建

`LLMEmbedding`依然采用一贯的工厂模式来创建，对应的工厂类型为派生自`Factory["LLMEmbedding"]`的`EmbeddingFactory`。`register_embedding`函数将指定的`LLMEmbedding`初始化函数注册到全局`EmbeddingFactory`对象上，注册名称为指定的类型。`create_embedding`函数最终调用全局`EmbeddingFactory`对象的`create`方法来创建`LLMEmbedding`，并以Lazy loading的形式完成上述两种`LLMEmbedding`类型的注册。

```python
class EmbeddingFactory(Factory["LLMEmbedding"])

embedding_factory = EmbeddingFactory()

def register_embedding(
    embedding_type: str,
    embedding_initializer: Callable[..., "LLMEmbedding"],
    scope: "ServiceScope" = "transient",
) -> None:
    embedding_factory.register(embedding_type, embedding_initializer, scope)

def create_embedding(
    model_config: "ModelConfig",
    *,
    cache: "Cache | None" = None,
    cache_key_creator: "CacheKeyCreator | None" = None,
    tokenizer: "Tokenizer | None" = None,
) -> "LLMEmbedding"
```

`EmbedTextConfig`提供的配置选项说明如下：

- **embedding_model_id**：用于文本嵌入的模型ID。
- **model_instance_name**：模型单例实例名，主要影响缓存存储分区。
- **batch_size**：嵌入处理的批大小。
- **batch_max_tokens**：每批允许的最大token数。
- **names**：指定要执行的嵌入项名称列表。

## 6. 生成并保存嵌入向量

`generate_text_embeddings`这个`Workflow`的`WorkflowFunction`对应如下这个`run_workflow`函数（所在模块目录为`graphrag/workflows/generate_text_embeddings`）。该函数会从`GraphRagConfig`配置中提供嵌入模型的配置，并调用上面介绍的`create_embedding`函数根据配置创建对应的`LLMEmbedding`对象。这个`LLMEmbedding`对象连同其他相关对象作为参数传入`generate_text_embeddings`函数完成最终的嵌入向量的生成和保存。

```python
async def run_workflow(
    config: GraphRagConfig,
    context: PipelineRunContext,
) -> WorkflowFunctionOutput:
    model_config = config.get_embedding_model_config(
        config.embed_text.embedding_model_id
    )
    model = create_embedding(
        model_config,
        cache=context.cache.child(config.embed_text.model_instance_name),
        cache_key_creator=cache_key_creator,
    )
    tokenizer = model.tokenizer

    await generate_text_embeddings(
        config=config,
        table_provider=context.output_table_provider,
        callbacks=context.callbacks,
        model=model,
        tokenizer=tokenizer,
    )
    return WorkflowFunctionOutput(result=None)
```

`generate_text_embeddings`函数执行流程如下：

- 调用`create_vector_store`函数根据配置创建作为向量存储的`VectorStore`对象；
- 利用`PipelineRunContext`上下文提供的`TableProvider`依次打开`text_units`、`entities`和`community_reports`三个表，并分别读取它们的`text`、`title_description`和`full_content`字段。利用`embedding_async`方法生成嵌入向量并保存到`VectorStore`对应的而向量表中。
