# [GraphRAG实现原理-18]四种查询方式之三：DRIFT Search

[GraphRAG实现原理-17:四种查询方式之二：Local Search](https://jaydenai.blog.csdn.net/article/details/169919728)介绍了Local Search查询模式的涉及和实现原理。RIFT Search在Local Search之上增加了一层社区级别的全局引导。普通Local Search直接从查询映射到实体，起点完全依赖实体相似度。DRIFT则先用社区报告做一轮宽泛的语义铺开，由社区报告**教会**系统应该追问什么，再将追问下放到实体层面执行。这使得DRIFT能触及比单次Local Search更广泛的事实集合。

## 1. RIFT Search针对Local Search的改进

DRIFT Search（Dynamic Reasoning and Inference with Flexible Traversal）的核心设计思路是**先全局铺开、再局部深挖**：以社区报告作为宽泛的起点生成初步答案和后续查询，再通过多轮局部搜索逐层细化，最终汇总为综合回答。整个流程总体划分为如下三个阶段：

- **Primer**: 从索引表`community_reports`中提取`top k`个社区报告，并基于报告的内容调用LLM生成一个初始答案和置信度评分，和一批为了完成最终的任务需要继续追问的查询文本；
- **Follow-Up**: 采用并发的方式采用Local Search模式对每个查询文本实时搜索并生成新的中间答案和追问查询，然后以相同当时迭代处理这些追问查询，直至满足退出的条件；
- **Reduce**: 将生成的中间答案提交给LLM进行汇总并生成最终的答案。

个配置选项说明如下：

- **prompt**：Primer阶段使用的提示词模板，用于生成假设答案、中间答案与后续查询。
- **reduce_prompt**：Reduce阶段的提示词模板，用于把各分支中间答案融合为最终响应。
- **completion_model_id**：Completion模型ID。
- **embedding_model_id**：嵌入模型ID。
- **data_max_tokens**：数据侧LLM的最大token数，控制送入LLM的上下文数据量。
- **reduce_max_tokens**/**reduce_max_completion_tokens**：Reduce阶段LLM响应可产生的最大token数。
- **reduce_temperature**：Reduce阶段调用LLM的温度参数，控制输出随机性。
- **concurrency**：并发请求数量，控制Follow-up阶段进行搜索采用的最大并发度。
- **drift_k_followups**：每轮生成的后续追问（follow-up）数量上限，即从全局结果中取`top-k`作为追问。
- **primer_folds**：对提取的社区表格进行分组的数量。
- **primer_llm_max_tokens**：Primer阶段LLM的最大token数。
- **n_depth**：Follow-up阶段进行搜索迭代的深度（步数）。

Follow-up阶段采用Local search模式，`DRIFTSearchConfig`提供了如下的配置选项：

- **local_search_text_unit_prop**：分配给文本单元的上下文预算比例。
- **local_search_community_prop**：分配给社区报告的上下文预算比例。
- **local_search_top_k_mapped_entities**：在实体映射阶段召回的实体数量上限。
- **local_search_top_k_relationships**：保留的关系数量上限。
- **local_search_max_data_tokens**：上下文数据的最大token数。
- **local_search_temperature**：的token生成温度。
- **local_search_top_p**：的`top-p`采样参数。
- **local_search_n**：生成的补全条数。
- **local_search_llm_max_gen_tokens**/**local_search_llm_max_gen_completion_tokens**：的LLM最大生成token数。


## 3. 利用QueryState维护迭代状态

`QueryState`状态的核心是一个通过`networkx.MultiDiGraph`对象的维护的多重有向图，即两个节点之间可以包含多条边。`MultiDiGraph`在`QueryState`中的节点绑定为一个`DriftAction`对象，该对象可以视为一个最小推理单元。`DriftAction`是一个有状态的对象，它维护了如下的状态：

- **query**：推理的查询文本。
- **answer**：推理生成的中间答案，`None`表示尚未完成。如果此答案存在，表示推理操作是否以完成的`is_complete`字段返回True；
- **score**：置信度评分，`None`表示未评分；`-inf`表示**评不出分/失败**，用于排序时沉底。
- **follow_ups**：后续追问查询文本列表。
- **metadata**：元数据字典
  - **llm_calls**：推理触发的LLM调用次数
  - **prompt_tokens**：推理消耗的提示token数
  - **output_tokens**：推理消耗的输出token数
  - **context_data**: 本次搜索返回的上下文数据

```python
class DriftAction:
    def __init__(
        self,
        query: str,
        answer: str | None = None,
        follow_ups: list["DriftAction"] | None = None,
    ):        
        self.query = query
        self.answer: str | None = answer  # Corresponds to an 'intermediate_answer'
        self.score: float | None = None
        self.follow_ups: list[DriftAction] = (
            follow_ups if follow_ups is not None else []
        )
        self.metadata: dict[str, Any] = {
            "llm_calls": 0,
            "prompt_tokens": 0,
            "output_tokens": 0,
        }

    @property
    def is_complete(self) -> bool:
        return self.answer is not None

    async def search(
        self,
        search_engine: Any,
        global_query: str,
        k_followups: int,
        scorer: Any = None,
    ):        
        if self.is_complete:
            return self

        search_result = await search_engine.search(
            query=self.query,
            drift_query=global_query,
            k_followups=k_followups,
        )

        _, response = try_parse_json_object(search_result.response, verbose=False)

        self.answer = response.pop("response", None)
        self.score = float(response.pop("score", "-inf"))
        self.metadata.update({"context_data": search_result.context_data})

        self.metadata["llm_calls"] += 1
        self.metadata["prompt_tokens"] += search_result.prompt_tokens
        self.metadata["output_tokens"] += search_result.output_tokens

        self.follow_ups = response.pop("follow_up_queries", [])
        if scorer:
            self.compute_score(scorer)

        return self

    def compute_score(self, scorer: Any):
        score = scorer.compute_score(self.query, self.answer)
        self.score = (
            score if score is not None else float("-inf")
        ) 

def try_parse_json_object(input: str, verbose: bool = True) -> tuple[str, dict]
```

`DriftAction`承载的推理体现在它的`search`方法上，它接受如下的三个参数：

- **search_engine**：搜索引擎实例，负责实际执行当前动作的查询并返回答案、评分、上下文及追问。由于Follow-up阶段采用Local search，所以这里是要给`LocalSearch`对象。
- **global_query**：原始查询文本。
- **k_followups**：期望生成的追问查询上限。
- **scorer**：评分器对象，其`compute_score`方法用来评分。

`DriftAction`对象的`search`方法按照如下的流程执行搜索：

- 将当前查询文本、原始查询文本和`k_followups`作为参数调用`search_engine`的`search`方法，并得到表示搜索结果的`search_result`对象；
- 调用`try_parse_json_object`一个JSON形式将格式化响应内容解析成`response`表示的字段。
- 根据`search_result`和`response`修改当前状态：
  - **answer**: response.pop("response", None);
  - **score**: float(response.pop("score", "-inf"));
  - **follow_ups**: response.pop("follow_up_queries", [])
  - **metadata**:
    - **context_data**：search_result.context_data
    - **llm_calls**: +1;
    - **prompt_tokens**: += search_result.prompt_tokens
    - **output_tokens**: += search_result.output_tokens

`DriftAction`还提供了如下这个`serialize`方法将它的状态（query、answer、score、metadata和follow_ups）序列化成字典。

```python
class DriftAction:
    def serialize(self, include_follow_ups: bool = True) -> dict[str, Any]:
        data = {
            "query": self.query,
            "query": self.answer,
            "score": self.score,
            "metadata": self.metadata,
        }
        if include_follow_ups:
            data["follow_ups"] = [action.serialize() for action in self.follow_ups]
        return data
```

`QueryState`本质上就是对一个`MultiDiGraph`对象的封装，并提供了`add_action`和`relate_actions`方法来添加作为节点的`DriftAction`对象和父子节点之间的有向边。当一轮推理完成后，LLM会为当前`DriftAction`生成一组继续追问的查询文本，后者将被转换对应的子`DriftAction`通过调用`add_all_follow_ups`方法添加到图中。`add_all_follow_ups`方法最终会调用`add_action`和`relate_actions`方法完成节点和边的添加。

```python
class QueryState:
    def __init__(self):
        self.graph = nx.MultiDiGraph()

    def add_action(self, action: DriftAction, metadata: dict[str, Any] | None = None):
        self.graph.add_node(action, **(metadata or {}))

    def relate_actions(self, parent: DriftAction, child: DriftAction, weight: float = 1.0):
        self.graph.add_edge(parent, child, weight=weight)

    def add_all_follow_ups(
        self,
        action: DriftAction,
        follow_ups: list[DriftAction] | list[str],
        weight: float = 1.0,
    ):
        for follow_up in follow_ups:
            if isinstance(follow_up, str):
                follow_up = DriftAction(query=follow_up)
            self.add_action(follow_up)
            self.relate_actions(action, follow_up, weight)
```

`QueryState`还定义其他的方法：

- **find_incomplete_actions**：找出尚未完成的（没有生成答案）的`DriftAction`节点。
- **rank_incomplete_actions**：根据指定的`scorer`对未完成的`DriftAction`节点进行排序（从高到低）。如果没有指定`scorer`，则调用`random.shuffle`方法重新**洗牌**。
- **action_token_ct**：合计所有`DriftAction`节点的LLM调用和token统计。
- **serialize**：对状态实施序列化，最终的输出取决于include_context参数
  - **True**： 返回一个三元组，分别是由节点和边组成的字典（`{"nodes": nodes, "edges": edges}`），每个节点上名为`context_data`的元数据元数据字典（以节点的查询文本作为Key）和该字点的字符串表示；
  - **False**：只返回由节点和边组成的字典（`{"nodes": nodes, "edges": edges}`）

```python
class QueryState:
    def find_incomplete_actions(self) -> list[DriftAction]:
        return [node for node in self.graph.nodes if not node.is_complete]

    def rank_incomplete_actions(
        self, scorer: Callable[[DriftAction], float] | None = None
    ) -> list[DriftAction]:
        unanswered = self.find_incomplete_actions()
        if scorer:
            for node in unanswered:
                node.compute_score(scorer)
            return sorted(
                unanswered,
                key=lambda node: (
                    node.score if node.score is not None else float("-inf")
                ),
                reverse=True,
            )
        random.shuffle(unanswered)
        return list(unanswered)    

    def action_token_ct(self) -> dict[str, int]:
        llm_calls, prompt_tokens, output_tokens = 0, 0, 0
        for action in self.graph.nodes:
            llm_calls += action.metadata["llm_calls"]
            prompt_tokens += action.metadata["prompt_tokens"]
            output_tokens += action.metadata["output_tokens"]
        return {
            "llm_calls": llm_calls,
            "prompt_tokens": prompt_tokens,
            "output_tokens": output_tokens,
        }
    
    def serialize(self, include_context: bool = True
    ) -> dict[str, Any] | tuple[dict[str, Any], dict[str, Any], str]:
        nodes: list[dict[str, Any]] = [
            {
                **node.serialize(include_follow_ups=False),
                "id": node_to_id[node],
                **self.graph.nodes[node],
            }
            for node in self.graph.nodes()
        ]
        edges: list[dict[str, Any]] = [
            {
                "source": node_to_id[u],
                "target": node_to_id[v],
                "weight": edge_data.get("weight", 1.0),
            }
            for u, v, edge_data in self.graph.edges(data=True)
        ]
        if include_context:
            context_data = {
                node["query"]: node["metadata"]["context_data"]
                for node in nodes
                if node["metadata"].get("context_data") and node.get("query")
            }

            context_text = str(context_data)
            return {"nodes": nodes, "edges": edges}, context_data, context_text

        return {"nodes": nodes, "edges": edges}
```

## 4. Primer阶段

作为搜索引擎的`DRIFTSearch`会在Primer阶段从索引表`community_reports`中提取与查询文本相似度最高的`top k`（通过`GraphRagConfig`的`drift_k_followups`字段配置）个社区报告，并基于报告的内容调用LLM生成一个初始答案和置信度评分，和一批为了完成最终的任务需要继续追问的查询文本。

### 4.1 采用HyDE生成更利于社区报告检索的查询文本

为了更加精准地找到与原始查询匹配的社区报告，`DRIFTSearch`采用了典型的**假设文档嵌入（HyDE：Hypothetical Document Embeddings）**的方式。HyDE核心思路是：如果向量数据库存储的嵌入向量对应的文本具有某种固有的模式（比如它们都是LLM针对类似的提示词生成），那么比直接使用原始查询文本进行检索更好的方式是：让LLM生成一份与原始查询文本具有相同语义又符合此模式的文本来实时检索，因为新的查询文本与向量存储的嵌入空间对得更齐。`DRIFTSearch`会利用一个类型为`PrimerQueryProcessor`的可执行对象采用HyDE的方式为原始的查询文本生成更契合`community_reports`嵌入空间的新查询文本，并将其转换成嵌入向量。

```python
class PrimerQueryProcessor:
    def __init__(
        self,
        chat_model: "LLMCompletion",
        text_embedder: "LLMEmbedding",
        reports: list[CommunityReport],
        tokenizer: Tokenizer | None = None,
    ):        
        self.chat_model = chat_model
        self.text_embedder = text_embedder
        self.tokenizer = tokenizer or chat_model.tokenizer
        self.reports = reports

    async def expand_query(self, query: str) -> tuple[str, dict[str, int]]:        
        template = secrets.choice(self.reports).full_content  # nosec S311
        prompt = (
            textwrap.dedent(f"""\
                Create a hypothetical answer to the following query: {query}

                Format it to follow the structure of the template below:

                """)
            + template
            + textwrap.dedent("""

                Ensure that the hypothetical answer does not reference new named entities that are not present in the original query.""")
        )

        model_response: LLMCompletionResponse = await self.chat_model.completion_async(
            messages=prompt
        )  # type: ignore
        text = model_response.content

        prompt_tokens = len(self.tokenizer.encode(prompt))
        output_tokens = len(self.tokenizer.encode(text))
        token_ct = {
            "llm_calls": 1,
            "prompt_tokens": prompt_tokens,
            "output_tokens": output_tokens,
        }
        if text == "":
            return query, token_ct
        return text, token_ct

    async def __call__(self, query: str) -> tuple[list[float], dict[str, int]]:
        hyde_query, token_ct = await self.expand_query(query)
        return self.text_embedder.embedding(
            input=[hyde_query]
        ).first_embedding, token_ct
```

当传入初始查询文本调用`__call__`方法时，内部会调用`expand_query`方法，后者会执行如下的操作：

- 从列表中随机提取一个`CommunityReport`对象，然后根据原始的查询文本定义一条提示词，该提示词旨在指导LLM生成一条与该社区报告内容描述（对应`CommunityReport`对象的`full_content`字段）模式匹配的新查询文本;
- 执行`LLMCompletion`的`completion_async`方法调用LLM并得到响应内容和token统计；
- 返回`[str, dict[str, int]]`二元组：
  - 更利于社区报告检索的查询文本
  - LLM调用次数和token统计字典

`__call__`方法进一步调用`LLMEmbedding`的`embedding`方法将生成的新查询文本转换成嵌入向量，并与LLM调用次数和token统计字典组成返回的二元组。

### 4.2 检索社区报告和生成搜索上下文

`PrimerQueryProcessor`采用HyDE生成的查询文本对应的向量最终被`DRIFTSearchContextBuilder`用来检索社区报告，并进一步生成调用LLM的上下文。`DRIFTSearchContextBuilder`就是`DRIFTSearch`专属的ContextBuilder，如下这个`DRIFTContextBuilder`是它的基类。抽象方法返回一个`[pd.DataFrame, dict[str, int]]`二元组，前者表示用来承载检索社区报告的`DataFrame`，后者就是上述的LLM调用次数和token统计字典。

```python
class DRIFTContextBuilder(ABC):
    @abstractmethod
    async def build_context(
        self,
        query: str,
        **kwargs,
    ) -> tuple[pd.DataFrame, dict[str, int]]
```

`DRIFTSearchContextBuilder`不仅仅实现了为了Primer搜索提供上下文的`build_context`方法，还定义了`init_local_context_builder`方法为Follow-up阶段的Local search创建`LocalSearchMixedContext`。构造函数的很多参数都用在了这个方法上。

```python
class DRIFTSearchContextBuilder(DRIFTContextBuilder):
    def __init__(
        self,
        model: "LLMCompletion",
        config: DRIFTSearchConfig,
        text_embedder: "LLMEmbedding",
        entities: list[Entity],
        entity_text_embeddings: VectorStore,
        text_units: list[TextUnit] | None = None,
        reports: list[CommunityReport] | None = None,
        relationships: list[Relationship] | None = None,
        covariates: dict[str, list[Covariate]] | None = None,
        tokenizer: Tokenizer | None = None,
        embedding_vectorstore_key: str = EntityVectorStoreKey.ID,
        local_system_prompt: str | None = None,
        local_mixed_context: LocalSearchMixedContext | None = None,
        reduce_system_prompt: str | None = None,
        response_type: str | None = None,
    )

    def init_local_context_builder(self) -> LocalSearchMixedContext:
        return LocalSearchMixedContext(
            community_reports=self.reports,
            text_units=self.text_units,
            entities=self.entities,
            relationships=self.relationships,
            covariates=self.covariates,
            entity_text_embeddings=self.entity_text_embeddings,
            embedding_vectorstore_key=self.embedding_vectorstore_key,
            text_embedder=self.text_embedder,
            tokenizer=self.tokenizer,
        )
```

`DRIFTSearchContextBuilder`的`build_context`方法采用如下的方式为Primer搜索创建上下文：

- 调用创建的`PrimerQueryProcessor`对象针对原始查询文本生成服务HyDE策略的新查询文本，并返回其嵌入向量和LLM调用和token统计；
- 对查询向量进行归一化后，采用计算点积的方法提取出相似度最高的`k`个（由`DRIFTSearchConfig`配置的`drift_k_followups`字段配置）社区报告；
- 将提取出来的社区报告转换成`DataFrame`（保留`short_id`, `community_id`和`full_content`三个字段）；
- 返回上述`DataFrame`和LLM调用和token统计字典构成的二元组。

```python
class DRIFTSearchContextBuilder(DRIFTContextBuilder):
    async def build_context(
        self, query: str, **kwargs
    ) -> tuple[pd.DataFrame, dict[str, int]]:   
        query_processor = PrimerQueryProcessor(
            chat_model=self.model,
            text_embedder=self.text_embedder,
            tokenizer=self.tokenizer,
            reports=self.reports,
        )
        query_embedding, token_ct = await query_processor(query)
        report_df = self.convert_reports_to_df(self.reports)
        query_norm = np.linalg.norm(query_embedding)
        document_norms = np.linalg.norm(report_df["full_content_embedding"].to_list(), axis=1)
        dot_products = np.dot(np.vstack(report_df["full_content_embedding"].to_list()), query_embedding)
        report_df["similarity"] = dot_products / (document_norms * query_norm)
        top_k = report_df.nlargest(self.config.drift_k_followups, "similarity")
        return top_k.loc[:, ["short_id", "community_id", "full_content"]], token_ct
```

### 4.3 首轮搜索

`DRIFTSearchContextBuilder`利用`build_context`方法创建的上下文最终会被`DRIFTPrimer`使用，后者完成了Primer阶段的搜索工作。`DRIFTPrimer`在初始时需要指定作为配置的`DRIFTSearchConfig`对象、作为Completion模型的`LLMCompletion`对象和用来计算token数的`Tokenizer`。

```python
class DRIFTPrimer:
    def __init__(
        self,
        config: DRIFTSearchConfig,
        chat_model: "LLMCompletion",
        tokenizer: Tokenizer | None = None,
    ):
        self.chat_model = chat_model
        self.config = config
        self.tokenizer = tokenizer or chat_model.tokenizer

    async def decompose_query(
        self, query: str, reports: pd.DataFrame
    ) -> tuple[dict, dict[str, int]]:
        community_reports = "\n\n".join(reports["full_content"].tolist())
        prompt = DRIFT_PRIMER_PROMPT.format(
            query=query, community_reports=community_reports
        )
        model_response: LLMCompletionResponse[
            PrimerResponse
        ] = await self.chat_model.completion_async(
            messages=prompt, response_format=PrimerResponse
        )  # type: ignore

        parsed_response = model_response.formatted_response.model_dump()  # type: ignore

        token_ct = {
            "llm_calls": 1,
            "prompt_tokens": len(self.tokenizer.encode(prompt)),
            "output_tokens": len(self.tokenizer.encode(model_response.content)),
        }

        return parsed_response, token_ct

    async def search(
        self,
        query: str,
        top_k_reports: pd.DataFrame,
    ) -> SearchResult:
        start_time = time.perf_counter()
        report_folds = self.split_reports(top_k_reports)
        tasks = [self.decompose_query(query, fold) for fold in report_folds]
        results_with_tokens = await tqdm_asyncio.gather(*tasks, leave=False)
        completion_time = time.perf_counter() - start_time

        return SearchResult(
            response=[response for response, _ in results_with_tokens],
            context_data={"top_k_reports": top_k_reports},
            context_text=top_k_reports.to_json() or "",
            completion_time=completion_time,
            llm_calls=len(results_with_tokens),
            prompt_tokens=sum(ct["prompt_tokens"] for _, ct in results_with_tokens),
            output_tokens=sum(ct["output_tokens"] for _, ct in results_with_tokens),
        )

    def split_reports(self, reports: pd.DataFrame) -> list[pd.DataFrame]:
        primer_folds = self.config.primer_folds or 1  
        if primer_folds == 1:
            return [reports]
        return [
            reports.iloc[indices]
            for indices in np.array_split(np.arange(len(reports)), primer_folds)
        ]
```

由`DRIFTPrimer`完成搜索工作实现在它的`search`方法中，方法的`top_k_reports`参数对应的`DataFrame`就是检索得到的社区报告。整个执行流程如下所示：

- 根据`GraphRagConfig`配置的`primer_folds`字段对社区报告列表包括进行分割，并将它们分批存入不同的`DataFrame`中；
- 并行处理每一批社区报告，具体的处理流程如下：
  - 提取默认的提示词模板；
  - 使用query参数表示的原始查询文本替换模板的`{query}`占位符
  - 将每一份社区报告的`full_content`字段提取出来，并使用`\n\n`分隔符合并生成的字符串来替换模板的`{community_reports}`占位符；
  - 执行`LLMCompletion`对象的`completion_async`方法调用LLM，除了传入完整的提示词外，还基于响应类型`PrimerResponse`实现结构化响应；
  - 从返回的`LLMCompletionResponse`对象的`formatted_response`字段直接提取结构化的响应内容，并返回它与LLM调用/token统计组成的二元组。
- 汇总所有任务的执行结果，并返回生成的`SearchResult`对象。

- **follow_up_queries**：后面继续追问的查询文本列表。

## 5. 完整的流程

DRIFT Search对应的搜索引擎类型为`DRIFTSearch`，接下来我们就来看看实现在它上面的完整流程。如代码所示，`DRIFTSearch`派生自`BaseSearch[DRIFTSearchContextBuilder]`，并将上面介绍的`DRIFTSearchContextBuilder`作为上下文构建器类型。

我们在初始化`DRIFTSearch`对象时需要指定作为Completion模型的`LLMCompletion`对象和`DRIFTSearchContextBuilder`对象，后者提供完整的`DRIFTSearchConfig`配置。如果没有指定`tokenizer`参数，将会使用`LLMCompletion`对象提供的`Tokenizer`。如果没有指定`QueryState`，会创建一个空的`QueryState`对象作为驱动整个流程执行的状态。除此之外，初始化时还会创建`DRIFTPrimer`和`LocalSearch`。上述的三个阶段的执行流程就体现在它的`DRIFTSearch`的`search`方法中。

```python
class DRIFTSearch(BaseSearch[DRIFTSearchContextBuilder]):
    async def search(
        self,
        query: str,
        conversation_history: Any = None,
        reduce: bool = True,
        **kwargs,
    ) -> SearchResult:
        llm_calls, prompt_tokens, output_tokens = {}, {}, {}
        start_time = time.perf_counter()
        
        # Primer
        if not self.query_state.graph:
            primer_context, token_ct = await self.context_builder.build_context(query)
            llm_calls["build_context"] = token_ct["llm_calls"]
            prompt_tokens["build_context"] = token_ct["prompt_tokens"]
            output_tokens["build_context"] = token_ct["output_tokens"]

            primer_response = await self.primer.search(
                query=query, top_k_reports=primer_context
            )
            llm_calls["primer"] = primer_response.llm_calls
            prompt_tokens["primer"] = primer_response.prompt_tokens
            output_tokens["primer"] = primer_response.output_tokens

            init_action = self._process_primer_results(query, primer_response)
            self.query_state.add_action(init_action)
            self.query_state.add_all_follow_ups(init_action, init_action.follow_ups)

        # Follow-up
        epochs = 0
        while epochs < self.context_builder.config.n_depth:
            actions = self.query_state.rank_incomplete_actions()
            if len(actions) == 0:
                logger.debug("No more actions to take. Exiting DRIFT loop.")
                break
            actions = actions[: self.context_builder.config.drift_k_followups]           
            results = await self._search_step(
                global_query=query,
                k_followups=self.context_builder.config.drift_k_followups,
                search_engine=self.local_search,
                actions=actions,
            )
            for action in results:
                self.query_state.add_action(action)
                self.query_state.add_all_follow_ups(action, action.follow_ups)
            epochs += 1

        t_elapsed = time.perf_counter() - start_time
        token_ct = self.query_state.action_token_ct()
        llm_calls["action"] = token_ct["llm_calls"]
        prompt_tokens["action"] = token_ct["prompt_tokens"]
        output_tokens["action"] = token_ct["output_tokens"]
        response_state, context_data, context_text = self.query_state.serialize(
            include_context=True
        )
        reduced_response = response_state

        # Reduce
        if reduce:           
            for callback in self.callbacks:
                callback.on_reduce_response_start(response_state)
            model_params = {
                "temperature": self.context_builder.config.reduce_temperature,
                "max_completion_tokens": self.context_builder.config.reduce_max_completion_tokens,
            }
            reduced_response = await self._reduce_response(
                responses=response_state,
                query=query,
                llm_calls=llm_calls,
                prompt_tokens=prompt_tokens,
                output_tokens=output_tokens,
                model_params=model_params,
            )

            for callback in self.callbacks:
                callback.on_reduce_response_end(reduced_response)

        return SearchResult(
            response=reduced_response,
            context_data=context_data,
            context_text=context_text,
            completion_time=t_elapsed,
            llm_calls=sum(llm_calls.values()),
            prompt_tokens=sum(prompt_tokens.values()),
            output_tokens=sum(output_tokens.values()),
            llm_calls_categories=llm_calls,
            prompt_tokens_categories=prompt_tokens,
            output_tokens_categories=output_tokens,
        )
```

我们根据search方法定义简单说说三个阶段的执行流程：

### 5.1 Primer阶段

- 调用`DRIFTSearchContextBuilder`的`build_context`方法根据查询文本构建上下文，并从中得到`top k`个与查询文本具有最高相似度的社区报告（被封装在一个`DataFrame`中）和LLM调用和token统计；
- 将查询文本和承载社区报告列表的`DataFrame`作为参数调用`DRIFTPrimer`对象`的search`方法发起首轮搜索，得到的结构化响应包含初始的中间答案、后续追问查询文本列表和置信度得分；
- 基于响应结果调用`_process_primer_results`函数创建一个`DriftAction`，并调用`QueryState`对象的`add_action`方法将它作为初始节点添加到用来描述整个推理流程的图中；

### 5.2 Follow-up阶段
- 开启一个循环，并将`GraphRagConfig.n_depth`的设置作为迭代次数的上限。每轮迭代执行流程如下：
  - 调用`QueryState`对象的`rank_incomplete_actions`方法提取得分最高的未完成`DriftAction`列表，如果列表为空，退出迭代；
  - 将`GraphRagConfig.drift_k_followups`作为限额对`DriftAction`列表作进一步过滤；
  - 将构造函数中创建的`LocalSearch`对象作为参数调用`_search_step`方法，后者会并发调用每个`DriftAction`的`search`方法;
  - 调用`QueryState`对象的`add_action`方法添加``DriftAction`，这里出现了重复添加，不过`add_action`方法的幂等性确保不会出错；
  - 调用`QueryState`对象的`add_all_follow_ups`方法为生成的追问查询创建对应的`DriftAction`，并作为子`DriftAction`的方式添加到推理图中。
- 调用`QueryState`对象的`action_token_ct`方法，并对结果提供的LLM调用、输入和输出Token进行统计。
- 调用`QueryState`对象的`serialize`方法状态进行序列化（`include_context=True`），如果不进行后续的Reduce，那么作为序列化结果的第一部分（包含推理图节点和边）将最为返回的`SearchResult`的响应内容。

上面提到的在每个跌断中并发执行Local search的`_search_step`方法定义如下

```python
class DRIFTSearch(BaseSearch[DRIFTSearchContextBuilder]):
    async def _search_step(
        self,
        global_query: str,
        k_followups: int,
        search_engine: LocalSearch,
        actions: list[DriftAction],
    ) -> list[DriftAction]:
        tasks = [
            action.search(
                search_engine=search_engine,
                global_query=global_query,
                k_followups=k_followups,
            )
            for action in actions
        ]
        return await tqdm_asyncio.gather(*tasks, leave=False)
```

### 5.3 Reduce阶段

最终的Reduct节点的执行流程主要体现在如下这个`_reduce_response`方法上，具体流程如下：

- 从`QueryState`对象的序列化结果中提取每个节点（`DriftAction`对象）携带的中间答案；
- 从`DRIFTSearchContextBuilder`的`reduce_system_prompt`字段提取配置或者默认的系统提示词模板，并将上面获取的中间答案列表和`response_type`字段返回的响应类型（由命令行参数指定）作为参数进行格式化生成完整的提示词；
- 利用`CompletionMessagesBuilder`将系统提示词和查询文本转换成角色分别为system和user的两条消息；
- 将消息列表作为参数调用`LLMCompletion`对象的`completion_async`方法对LLM发起调用，并调用`gather_completion_response_async`函数解析响应结果，该结果将作为最终生成的`SearchResult`对象的响应结果。

```python
class DRIFTSearch(BaseSearch[DRIFTSearchContextBuilder]):
    async def _reduce_response(
        self,
        responses: str | dict[str, Any],
        query: str,
        llm_calls: dict[str, int],
        prompt_tokens: dict[str, int],
        output_tokens: dict[str, int],
        **llm_kwargs,
    ) -> str:
        reduce_responses = []
        if isinstance(responses, str):
            reduce_responses = [responses]
        else:
            reduce_responses = [
                response["answer"]
                for response in responses.get("nodes", [])
                if response.get("answer")
            ]

        search_prompt = self.context_builder.reduce_system_prompt.format(
            context_data=reduce_responses,
            response_type=self.context_builder.response_type,
        )

        messages_builder = (
            CompletionMessagesBuilder()
            .add_system_message(search_prompt)
            .add_user_message(query)
        )

        model_response = await self.model.completion_async(
            messages=messages_builder.build(),
            **llm_kwargs.get("model_params", {}),
        )

        reduced_response = await gather_completion_response_async(model_response)

        llm_calls["reduce"] = 1
        prompt_tokens["reduce"] = len(self.tokenizer.encode(search_prompt)) + len(
            self.tokenizer.encode(query)
        )
        output_tokens["reduce"] = len(self.tokenizer.encode(reduced_response))
        return reduced_response
```

## 6. 流式调用

DRIFTSearch定义`search`这个阻塞式调用的方法返回最终的结果之前，它还定义了如下这个基于流式调用的`stream_search`方法。该方法的实现很清晰：

- 将指定的查询文本和对话历史作为参数调用`search`方法，由于`reduce=False`，所以得到的结果仅仅是Follow-up阶段结束后的状态。说得具体一点，得到的结果是`QueryState`序列化的结果，包含推理图的所有结果和边的状态（`{"nodes": nodes, "edges": edges}`）。
- 调用`_reduce_response_streaming`方法以流形式完成Reduce阶段的工作，并实时输出生成的结果。

```python
class DRIFTSearch(BaseSearch[DRIFTSearchContextBuilder]):
    async def stream_search(
        self, query: str, conversation_history: ConversationHistory | None = None
    ) -> AsyncGenerator[str, None]:
        result = await self.search(query=query, conversation_history=conversation_history, reduce=False)

        if isinstance(result.response, list):
            result.response = result.response[0]

        for callback in self.callbacks:
            callback.on_reduce_response_start(result.response)

        model_params = {
            "temperature": self.context_builder.config.reduce_temperature,
            "max_completion_tokens": self.context_builder.config.reduce_max_completion_tokens,
        }

        full_response = ""
        async for resp in self._reduce_response_streaming(
            responses=result.response,
            query=query,
            model_params=model_params,
        ):
            full_response += resp
            yield resp

        for callback in self.callbacks:
            callback.on_reduce_response_end(full_response)
```

除了在调用`LLMCompletion`的`completion_async`方法时将`stream`参数设置为`True`之外，整个流程与实现在`search`中的Reduce逻辑完全一样。

```python
class DRIFTSearch(BaseSearch[DRIFTSearchContextBuilder]):
    async def _reduce_response_streaming(
        self,
        responses: str | dict[str, Any],
        query: str,
        model_params: dict[str, Any],
    ) -> AsyncGenerator[str, None]:
        
        reduce_responses = []

        if isinstance(responses, str):
            reduce_responses = [responses]
        else:
            reduce_responses = [
                response["answer"]
                for response in responses.get("nodes", [])
                if response.get("answer")
            ]

        search_prompt = self.context_builder.reduce_system_prompt.format(
            context_data=reduce_responses,
            response_type=self.context_builder.response_type,
        )

        messages_builder = (
            CompletionMessagesBuilder()
            .add_system_message(search_prompt)
            .add_user_message(query)
        )

        response_search: AsyncIterator[LLMCompletionChunk] = await self.model.completion_async(
            messages=messages_builder.build(), stream=True, **model_params
        ) 

        async for chunk in response_search:
            response_text = chunk.choices[0].delta.content or ""
            for callback in self.callbacks:
                callback.on_llm_new_token(response_text)
            yield response_text
```
