# [GraphRAG实现原理-19]DRIFT Search可能花光了Token，还无法提供正确答案

[上篇](https://jaydenai.blog.csdn.net/article/details/169920210)对作为DRIFT Search搜索引擎的`DRIFTSearch`进行了深入的介绍，从而了解了该模式完整的执行流程。这篇文章我主要想通过一个简单的实例演示这种查询方式特有的不断追问的推理风格。而且这个实例并不是为了说明DRIFT Search有多强大，正好相反，而是反映了这个种查询模式在一些场景中不但效果不好，而且还极其昂贵。在这之前，我们来补充一些必要的内容。

## 1. 搜索引擎的创建

GraphRAG在进行DRIFT Search的时候会调用如下这个`get_drift_search_engine`函数来创建作为搜索引擎的`DRIFTSearch`对象。提供的参数包括：

- 表示整体配置的`GraphRagConfig`对象；
- 从索引表`community_reports`、`text_units`、`entities`和`relationships`提取的`CommunityReport`、`TextUnit`、`Entity`和`Relationship`列表；
- 作为向量存储的`VectorStore`对象；
- 响应格式；
- Follow-up和Reduce阶段调用LLM的提示词模板。

```python
def get_drift_search_engine(
    config: GraphRagConfig,
    reports: list[CommunityReport],
    text_units: list[TextUnit],
    entities: list[Entity],
    relationships: list[Relationship],
    description_embedding_store: VectorStore,
    response_type: str,
    local_system_prompt: str | None = None,
    reduce_system_prompt: str | None = None,
    callbacks: list[QueryCallbacks] | None = None,
) -> DRIFTSearch:
    chat_model_settings = config.get_completion_model_config(
        config.drift_search.completion_model_id
    )
    chat_model = create_completion(chat_model_settings)
    embedding_model_settings = config.get_embedding_model_config(
        config.drift_search.embedding_model_id
    )
    embedding_model = create_embedding(embedding_model_settings)
    tokenizer = chat_model.tokenizer
    return DRIFTSearch(
        model=chat_model,
        context_builder=DRIFTSearchContextBuilder(
            model=chat_model,
            text_embedder=embedding_model,
            entities=entities,
            relationships=relationships,
            reports=reports,
            entity_text_embeddings=description_embedding_store,
            text_units=text_units,
            local_system_prompt=local_system_prompt,
            reduce_system_prompt=reduce_system_prompt,
            config=config.drift_search,
            response_type=response_type,
        ),
        tokenizer=tokenizer,
        callbacks=callbacks,
    )
```

`get_drift_search_engine`函数采用如下的流程来创建`DRIFTSearch`对象:

- 根据提供的模型配置将代表Completion模型和嵌入模型的`LLMCompletion`和`LLMEmbedding`对象创建出来；
- 根据`LLMCompletion`和`LLMEmbedding`对象、`VectorStore`对象、四个索引对象列表、两个提示词模板、从`GraphRagConfig`中提取的`DRIFTSearchConfig`配置创建用来构建上下文的`DRIFTSearchContextBuilder`对象；
- 根据创建的`LLMCompletion`、`DRIFTSearchContextBuilder`和前者提取的`Tokenizer`创建返回的`DRIFTSearch`对象。

## 2. 阻塞式调用和流式调用

当我们执行命令行`graphrag query --method drift`命令时，最终会根据`--streaming`参数选择调用`drift_search`或者`drift_search_streaming`函数。如下所示的代码是经过简化的`drift_search_streaming`函数的定义。

```python
def drift_search_streaming(
    config: GraphRagConfig,
    entities: pd.DataFrame,
    communities: pd.DataFrame,
    community_reports: pd.DataFrame,
    text_units: pd.DataFrame,
    relationships: pd.DataFrame,
    community_level: int,
    response_type: str,
    query: str,
    callbacks: list[QueryCallbacks] | None = None,
    verbose: bool = False,
) -> AsyncGenerator:
    description_embedding_store = get_embedding_store(
        config=config.vector_store,
        embedding_name=entity_description_embedding,
    )
    full_content_embedding_store = get_embedding_store(
        config=config.vector_store,
        embedding_name=community_full_content_embedding,
    )
    entities_ = read_indexer_entities(entities, communities, community_level)
    reports = read_indexer_reports(community_reports, communities, community_level)
    read_indexer_report_embeddings(reports, full_content_embedding_store)
    prompt = load_search_prompt(config.drift_search.prompt)
    reduce_prompt = load_search_prompt(config.drift_search.reduce_prompt)

    search_engine = get_drift_search_engine(
        config=config,
        reports=reports,
        text_units=read_indexer_text_units(text_units),
        entities=entities_,
        relationships=read_indexer_relationships(relationships),
        description_embedding_store=description_embedding_store,
        local_system_prompt=prompt,
        reduce_system_prompt=reduce_prompt,
        response_type=response_type,
        callbacks=callbacks,
    )
    return search_engine.stream_search(query=query)
```

`drift_search_streaming`函数接受如下的参数：

- **config**：全局配置，提供向量存储设置以及DRIFT搜索两阶段的提示词配置，驱动整个搜索流程。
- **entities**：实体数据，作为图节点参与检索。
- **communities**：社区数据，描述实体所属社区及层级结构，用于按层级筛选实体与报告。
- **community_reports**：社区报告数据，提供各社区的摘要内容，是 DRIFT 搜索汇总阶段的重要上下文来源。
- **text_units**：文本单元数据，原始文档的片段，用于最终引用与上下文补充。
- **relationships**：关系数据，实体之间的连接及描述，用于扩展检索上下文。
- **community_level**：指定使用的社区层级，层级越粗粒度越大。
- **response_type**：期望的回答类型或格式，影响提示词与输出风格。
- **query**：用户的查询问题，即要检索并回答的自然语言输入。
- **callbacks**：可选回调，用于在搜索过程中插入日志、调用追踪、进度监控等钩子。
- **verbose**：是否输出详细日志或调试信息；当前函数体中未实际使用，可能用于上游日志控制或预留。

`drift_search_streaming`函数采用如下的执行流程：

- 根据配置调用`get_embedding_store`函数创建针对实体描述和社区报告内容的`VectorStore`对象；
- 从提供的五个DataFrame中提取实体、关系、切片、社区和社区报告；
- 调用`load_search_prompt`函数根据配置提取Follow-up和Reduce阶段使用的提示词模板；
- 将上面创建的对象作为参数调用`get_drift_search_engine`函数将`DRIFTSearch`对象创建出来，传入查询文本调用其`stream_search`方法，并以迭代器的方式流式输出实时生成的内容。

基于阻塞式调用的`drift_search`函数内部会调用上面这个`drift_search_streaming`，并将利用异步迭代收集并拼接响应内容，最终进行统一输出。

```python
async def drift_search(
    config: GraphRagConfig,
    entities: pd.DataFrame,
    communities: pd.DataFrame,
    community_reports: pd.DataFrame,
    text_units: pd.DataFrame,
    relationships: pd.DataFrame,
    community_level: int,
    response_type: str,
    query: str,
    callbacks: list[QueryCallbacks] | None = None,
    verbose: bool = False,
) -> tuple[
    str | dict[str, Any] | list[dict[str, Any]],
    str | list[pd.DataFrame] | dict[str, pd.DataFrame],
]:
    callbacks = callbacks or []
    full_response = ""
    context_data = {}

    def on_context(context: Any) -> None:
        nonlocal context_data
        context_data = context

    local_callbacks = NoopQueryCallbacks()
    local_callbacks.on_context = on_context
    callbacks.append(local_callbacks)
    async for chunk in drift_search_streaming(
        config=config,
        entities=entities,
        communities=communities,
        community_reports=community_reports,
        text_units=text_units,
        relationships=relationships,
        community_level=community_level,
        response_type=response_type,
        query=query,
        callbacks=callbacks,
    ):
        full_response += chunk
    return full_response, context_data
```

## 3. 感受一下DRIFT Search不断追问的推理风格

[上篇](https://jaydenai.blog.csdn.net/article/details/169920210)介绍了DRIFT Search完整的执行流程，由于第二任阶段（Follow-up）会经历多轮迭代，每一次迭代都会并发调用LLM（次数取决于上一次生成的追问查询的数量和提供的配置）。我们通过一个简单的例子感受一下：对于一个简单的问题，这种查询方式如何采用不断追问的推理方式得到最终的答案。这个演示依然建立在前面构建的索引上，我们回顾一下提供的作为原始文档的`.svc`文件：

在如下的演示程序中，我们基于当前构建的索引表和配置调用`get_drift_search_engine`函数将作为搜索引擎的`DRIFTSearch`对象创建出来。我们调用其`search`方法，并指定一个只需要阅读`doc2 + doc4`就能回答的问题：*李明、张伟和王芳三人是什么关系*。在这之后，我们将承载查询状态的`QueryState`对象提取出来，此时它的`graph`字段返回的推理图本质上是一棵树，每个节点对应一个`DriftAction`对象。我们从作为根节点的`DriftAction`对象开始，以递归的形式输出它们的查询文本（同时也是父节点生成追问文本之一）。

```python
import asyncio
from typing import cast
from graphrag.config.load_config import load_config
from graphrag.callbacks.noop_query_callbacks import NoopQueryCallbacks
from graphrag.query.structured_search.drift_search.action import DriftAction
import pandas as pd
from graphrag.config.models.graph_rag_config import GraphRagConfig
from graphrag.query.indexer_adapters import (
    read_indexer_entities,
    read_indexer_relationships,
    read_indexer_report_embeddings,
    read_indexer_reports,
    read_indexer_text_units)

from graphrag.utils.api import (
    get_embedding_store,
    load_search_prompt,
)
from graphrag.query.factory import (
    get_drift_search_engine,
)

async def main():   
    config: GraphRagConfig = load_config(root_dir="./")
    entities = pd.read_parquet('./output/entities.parquet')
    communities = pd.read_parquet('./output/communities.parquet')
    community_reports = pd.read_parquet('./output/community_reports.parquet')
    entities = pd.read_parquet('./output/entities.parquet')
    description_embedding_store = get_embedding_store(
            config=config.vector_store,
            embedding_name="entity_description",
        )    
    full_content_embedding_store = get_embedding_store(
        config=config.vector_store,
        embedding_name="community_full_content",
    )    
    entity_list = read_indexer_entities(
        entities= entities, 
        communities= communities,
        community_level= 2)
    report_list = read_indexer_reports(        
        final_community_reports = community_reports, 
        final_communities= communities,
        community_level=  2)
    read_indexer_report_embeddings(report_list, full_content_embedding_store)
    prompt = load_search_prompt(config.drift_search.prompt)
    reduce_prompt = load_search_prompt(config.drift_search.reduce_prompt)
    
    search_engine = get_drift_search_engine(
        config=config,
        reports=report_list,
        text_units=read_indexer_text_units(pd.read_parquet('./output/text_units.parquet')),
        entities=entity_list,
        relationships=read_indexer_relationships(pd.read_parquet('./output/relationships.parquet')),
        description_embedding_store=description_embedding_store,
        local_system_prompt=prompt,
        reduce_system_prompt=reduce_prompt,
        response_type="Single Sentence",
        callbacks=[NoopQueryCallbacks()],
    )
    await search_engine.search(query="李明、张伟和王芳三人是什么关系")
    graph = search_engine.query_state.graph
    root = cast(DriftAction,[n for n in graph.nodes if graph.in_degree(n) == 0][0])
    actions = [cast(DriftAction,n)  for n in graph.nodes]

    def walk(node: DriftAction, level: int):
      print(f"{'    '*level}{node.query}")
      for follow_up in node.follow_ups:
         sub_nodes = [action for action in actions if action.query == follow_up]
         if(len(sub_nodes)):
            walk(sub_nodes[0], level + 1)
    walk(root, 0)
asyncio.run(main())
```

## 4. 为什么会膨胀成这样？

Drift Search的设计假设是大规模、异构、跨主题的语料库（成千上万文档、多个社区），此时：

- 单一向量检索容易**只见树木不见森林**；
- 需要先在Primer阶段建立全局底稿，再让LLM决定*往哪个方向深挖*；
- Follow-up阶段递归是为了覆盖问题的多个侧面。

在我们的场景里，这个假设不成立：

- 语料极小（4篇），信息密度低，几乎不存在**检索不到**的问题；
- 三人的关系在doc2/doc4里一句话就说清了（张伟=咖啡豆供应商，王芳=店长，李明=老板）；
- LLM生成的follow-up大量是同义重复或无关展开（输出里*李明为什么没选学校附近*，*桂花拿铁占比三成*反复出现几十次），说明follow-up生成没有收敛机制。

Drift缺少**够了就停**的判据。它默认每个节点都值得继续展开，于是小语料上就出现了**问题树爆炸**。但Drift不是没用，而是有适用边界：

- 语料大（数千文档以上）、跨多个社区/主题；
- 问题本身是开放式的、需要多跳、需要发现"没预料到的关联"（例如"这三人的关系对门店经营风险有何系统性影响"）；
- 有预算、且能接受较高延迟。

其实导致问题树爆炸还有一个原因，那就是调用`DRIFTSearch`对象的search方法时将响应类型设置成了`Single Sentence`，导致生成的中间答案承载的信息量缩水。
