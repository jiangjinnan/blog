## 1. OKF概述

Open Knowledge Format（OKF）是Google Cloud于2026年6月发布的一种开放规范，旨在将企业知识组织为 AI 智能体与人类都能直接读取的**Living Wiki**（相对于传统静态文档而言的一个概念，核心在于文档能够持续自我更新、自我维护，而非一次写就后便逐渐过时）式文件结构。它的核心是一个由Markdown文件与YAML元数据（Frontmatter）组成的目录树，无需专有数据库或运行时环境。

OKF采用一种开放的、对人和智能体都友好的知识表示格式：它包含了围绕数据和系统的元数据、上下文以及经过精心整理的洞察。OKF的设计理念是：由人编写，由智能体生成，跨组织交换，并被两者共同使用。该格式刻意保持极简：一个包含带有YAML元数据（Frontmatter）的Markdown文件目录。它没有模式注册表、没有中央权威机构，也不需要任何工具。只要你会使用`cat`命令，就能阅读 OKF 文件；只要你会使用`git clone`命令，就能创建OKF文件。

Agent的知识表示领域正在快速发展，许多互不兼容的约定正在涌现。OKF认为，知识的最佳表示形式是通用且成熟的格式，这些格式应具备以下特点：

- 无需工具即可被人类读取。
- 无需定制SDK即可被Agent解析。
- 可在版本控制中进行差异比较。
- 可跨工具、组织和时间移植。

如今，知识库不再是一次性编写后阅读的，而是由各种主体持续编写和维护的。当大多数**概念**都是机器生成的，用户需要的答案，仅仅依靠简单的Markdown加Frontmatter格式是无法提供的，比如这些信息：

- 这是从什么来源创建的？
- 如何验证的？（来源）
- 我应该有多信任它？（信任度）
- 它仍然有效吗？（时效性）
- 它是最新版本吗？（生命周期）
- 这个数字是否按照我们规定的方式生成？（证明）

OKF v0.2将来源、信任、生命周期和证明置于首位，同时保持格式的极简风格。该格式的风格非常简洁，仅标准化了使知识库能够自描述所需的少量结构约定——除此之外的任何内容都留给了生产者自行决定。其目标是：

- 定义一种通用格式，供生产者（人员、Agent、导出管道）写入。、
- 明确消费者（Agent、用户界面、搜索索引、确定性代码）应如何读取和遍历该格式。
- 促进跨系统和组织的知识交流。
- 标准化少量使Agent维护的语料库可信的前置元数据字段，而无需规定任何运行时环境。

## 2. 灵活自由的目录结构

OKF v0.2将定义在某个目录下的Markdown文档称为`Bundle`。规范并为对目录的结构做任何约束，并且此结构与领域无关，我们可以按照对所捕获知识最合理的方式来组织**概念文档**。这是OKF v0.2规范提供的一种典型的目录结果，其中`index.md`和`log.md`是两个保留的文件名。

```text
path/to/bundle/
  index.md          # Optional. Directory listing for progressive disclosure.
  log.md            # Optional. Chronological history of updates.
  <concept>.md      # A concept at the bundle root.
  <subdirectory>/   # Subdirectories organize concepts into groups.
    index.md
    <concept>.md
    <subdirectory>/
      ...
```

这个被称为Bundle的文件夹可以采用如下的分发方式：

- 一个Git仓库（推荐，因为它提供历史记录、归属信息和差异比较）。
- 一个目录的 tarball 或 zip 压缩包。
- 一个大型仓库中的子目录。

## 3. 概念文档的定义

上面内容多次提及**概念（Concept）文档**这个词，它是知识包（Bundle）里承载知识的最小单元。每一个概念对应一个独立的Markdown文件，文件由如下两部分组成：

- 一个YAML前置元数据块，以单独一行的`---`分隔，位于文件开头，并以单独一行的`---`结束。
- 一个Markdown正文，包含自由格式的内容。

### 3.1 常规元数据

虽然OKF定义了很多YAML元数据，但是只有这个命名为type的元数据采用必需的。这个元数据被指定为一个简短的字符串，用于标识概念的类型。用户使用它来进行路由、筛选和展示。比如BigQuery表、BigQuery数据集、API端点、指标、剧本、参考、已验证的计算。类型值并非集中注册，但推荐：

- 生产者应选择描述性强且不加解释的类型值；
- 消费者必须能够优雅地容忍未知类型，通常将其视为通用概念。

其他推荐添加的元数据包括：

- **title**：人类可读的显示名称。如果省略，用户可以根据文件名推断标题。
- **description**：概括概念的一句话。用于`index.md`生成器、搜索摘要和预览。
- **resource**：唯一标识概念所描述的底层资产的URI。描述抽象概念而非物理资源的概念缺少此项。
- **tags**：用于跨领域分类的短字符串YAML列表。

这是OKF v0.2规范提供的一种典型的元数据列表。

```yaml
---
type: <Type name>                  # REQUIRED
title: <Optional display name>
description: <Optional one-line summary>
resource: <Optional canonical URI for the underlying asset>
tags: [<tag>, <tag>, ...]          # Optional
# ... trust, lifecycle, provenance, and computation families
# ... other producer-defined key/value pairs
---
```

### 3.2 正文主体

正文采用标准 Markdown格式。制作人员应该优先选择结构化的Markdown 格式（标题、列表、表格、代码块等），而不是自由散文，因为结构化的内容有助于人类阅读和搜索引擎检索。正文没有必选章节。下列标题具有约定俗成的含义，在适用时应当使用：

-`# Schema`：对数据的列/字段进行结构化描述。
-`# Examples`：具体使用示例，通常以带围栏的代码块形式出现。
-`# Computation`：经认可的计算。

正文主体内容使用标准的Markdown链接来表示概念之间的链接，并支持如下两种形式：

- **绝对**：以`/`开头，相对Bundle根解析。这是推荐形式，因为文档在子目录内移动时仍然稳定，比如`See the [customers table](/tables/customers.md) for the join key`。
- **相对**：标准Markdown相对路径，比如`See the [neighboring concept](./other.md)`。

从概念A到概念B的链接表明两者之间存在某种关系。具体的关系类型（父子关系、引用关系、连接关系、依赖关系）由链接周围的文字描述，而非链接本身。关系图的消费者通常将所有链接视为无类型关系的有向边。

## 4. 三个元数据簇

除了上面介绍的几个常规的YAML元数据，OKF还定义了如下三个重要的**元数据簇**，它们回答了如下的问题：

- **Provenance**： 这个信息来自哪里？
- **Trust**：我应该相信它多少？
- **Lifecycle**：它是否仍然有效。

如果具体元数据涉及时间戳，OKF采用`iso-8601`日期时间格式。这总格式具有明确的UTC偏移量，例如`2026-06-30T14:00:00Z`。

### 4.1 Provenance

Provenance元数据簇的`sources`记录了概念所源自的材料，可以来源于Bundle概念内部，也可以来源于Bundle外部。每个`sources`条目又包含如下的字段：

- **resource**：可以是消费者可以具体定位某个`artifact`的地址（可以是`artifact`的绝对URL，也可以是基于Bundle的相对路径或`references/`子目录的路径），也可以是消费者无法具体定位的的某个群体或范围的描述符（例如`all queries in BigQuery project X`）。
- **id**：资源的唯一标识。当正文引用来源时，必须包含`id`。
- **title**：一组人类可读标签。
- **author**：`sources`的创建者或创建者。
- **usage_count**：在usage_window指定的时间窗口内的使用频率（仪表盘查看次数、查询执行次数、页面读取次数）。
- **last_modified**：源本身的最后修改时间。
- **usage_window**：给`usage_count`（使用次数）标一个统计时间段，告诉读者*这个次数是在哪段时间里数出来的*。它以`{ from, to }`日期时间范围框定每个`usage_count`。

这些字段记录了概念文档来源可信度信号（Source credibility signals），消费者能够根据它们评估概念文档的来源，进而判断其可信度。OKF不存储可信度评分，因为在它看来评分是主观的，无法在不同消费者之间通用，而且会过时。可信度是从信号中推断出来的，就像**信任等级**的推断方式一样。`author`、`usage_count`和`last_modified`分别提供了如下所示的可信度信号：

- **author**：权威性（authority ）信号；
- **usage_count**：采用度与活跃度（adoption and liveness）信号。
  - 对于单个`artifact`而言，它是该`artifact`自身被使用的次数。
  - 对于范围描述符而言，它是范围内涉及该概念的数量。
- **last_modified**：通过最近一次被使用的时间戳提供了时效性（recency）信号。

`usage_count`是一个粗略的信号。它在区分活跃用户与已失效用户以及数量级层面上具有可比性，并且可以与数据源自身的历史数据进行比较，但它并非精确的跨类型排名：计划查询的执行次数和用户主动查看仪表盘的次数权重并不相同。用户应该将其视为活跃度和趋势的指标，而不是一个分数。上述这些字段在概念文档的YAML元数据中类似于如下的定义方式。

```yaml
sources:
  - id: ga4-schema
    resource: https://developers.google.com/analytics/bigquery/export-schema
    title: GA4 BigQuery Export schema
    author: team:ga4-docs
    usage_count: 5000
    last_modified: 2026-05-30T00:00:00Z
usage_window: { from: 2026-06-01T00:00:00Z, to: 2026-06-30T00:00:00Z }
```

### 4.2 Trust

Trust元数据簇包含`generated`和`verified`两个字段。

- **generated**： 记录内容是怎么产生的，它具有如下两个子字段：
  - by：产出者，采用actor约定，如`reference_agent/gemini-2.5-pro`、`human:ahormati`、`process:finance-nightly`。
  - at: 内容的最后一次有意义变更时间。消费者用它区分*最近编辑过*和*陈旧事实*。
- **verified**: 记录谁/什么确认过内容，具体内容是一个验证事件列表，每个事件含by和at两个字段：
  - 多条记录表示独立的多次检查（例如人工签核 + 每夜自动流程）。
  - 最近一次验证取列表中最大的`at`。

如下的Yaml片段提供了`generated`和`verified`的标准定义。

```yaml
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
verified:
  - { by: human:ahormati, at: 2026-06-25T09:00:00Z }
  - { by: process:finance-nightly, at: 2026-06-26T02:00:00Z }
```

如果`verified`只有一条记录，也可以写成generated一样的形式，比如

```yaml
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
```

消费者从`verified`字段**推导**出来概念文档的信任等级（Trust tiers）。信任等级有三个选项，从低到高分别是：

- **unverified**: 没有`verified`字段。
- **machine-confirmed**:`verified`中只有非人类Actor（如`process:...`、`agent/version`）验证过。
- **human-reviewed**：`verified`中有通过`human:<id>`表示的人类验证过。

针对信任等级具有如下的规则：

- 只由`verified`推导，与`generated`无关。`generated`回答*谁写的*，信任层级只看*谁确认的*。
- 按最高层级算：只要列表里出现一次`human:<id>`，整体就是`human-reviewed`。
- 分类靠`human: 前缀`，消费者做信任分类时以 human: 前缀为准，所以生产者必须对人类撰写或人工确认的内容使用这个前缀。
- 有多个验证事件时，层级取验证者类型中的最高者；多新则取最新的`at`。
- 无Trust不拒收。概念没有`verified`时只是`unverified`，消费者不能拒绝。
- 只是提示信号，不是访问控制。
- 即使没有信任层级，概念仍然可以被理解；消费者绝不能拒绝它。信任层级是建议性信号，而非访问控制。

`generated.at`和`verified.at`承载的主体对象在OKF中被统称为Actor，并采用如下的约定来表示不同的类型：

-`<producer>/<version>`：用于Agent和工具，例如`reference_agent/gemini-2.5-pro`。
-`human:<id>`：用于人，例如`human:ahormati`。
-`process:<id>`：用于自动化流程，例如`process:finance-nightly`。

### 4.3 Lifecycle

Lifecycle元数据簇`status`字段是记录概念生命周期状态的可选字段，它具有如下三个选项：

- **draft**: 尚未审阅；可能不完整。
- **stable**: 默认；可供消费使用。
- **deprecated**: 为链接和历史保留；不再是最新内容。

另一个`stale_after`字段提供一个时间戳。当`now >= stale_after`时，概念即为过时。由于采用绝对的瞬间，而非相对的TTL，使得过时判断仅基于简单的比较，不考虑概念的阅读时间。

## 5. 索引和日志

作为索引的`index.md`文件可以出现在任何目录中，包括Bundle根目录。它列举了目录的内容，以支持渐进式披露：让用户或Agent人在打开单个文档之前先了解目录内容。索引文件不包含Frontmatter，但有一个例外：Bundle根目录下的`index.md`文件可以包含`okf_version`字段来表示OKF版本。正文使用一个或多个章节，每个章节将概念归类到一个标题下。如下就是典型索引文件的定义：

```markdown
# Section / Group Heading

* [Title 1](relative-url-1) - short description of item 1
* [Title 2](relative-url-2) - short description of item 2

# Another Section

* [Subdirectory](subdir/) - short description of the subdirectory
```

来记录日志的`log.md`文件也可以出现在层级结构的任何级别，用于记录该作用域的变更历史记录。其格式为按日期分组的扁平列表，最新条目在前：

```markdown
# Directory Update Log

## 2026-05-22
* **Update**: Added a BigQuery table reference for [Customer Metrics](/tables/customer-metrics.md).
* **Creation**: Established the [Dataplex Playbook](/playbooks/dataplex.md).

## 2026-05-15
* **Initialization**: Created foundational directory structure.
```

## 6. 经证实的计算概念

**经认证的计算概念（Attested Computation）**不仅包含数值的含义，还包含一种经认可的计算方法，因此消费者可以确认Agent执行的是经过认证的计算，而不是自行摸索。Provenance用来回答*这个说法从哪来*，Attested Computation用来回答*这个数字是否按我们说的方式产生*。


### 6.1 为什么需要这个独立的概念

这是一个独立的具有`type: Attested Computation`YAML元数据的概念。需要该值（例如Metric、BigQuery表）的概念通过普通的Markdown链接与其关联。使用这个独立的概念类型出于如下的目的：

- **运行时定义了参数的含义**：根据运行时的不同，参数可以是SQL绑定变量、dbt变量或Python参数。将运行时和参数放在同一个Frontmatter中，可以使绑定语义一目了然。
- **一次计算，多次消费**。同一个计算可以支持指标、仪表盘概念和报告；作为一个概念，它只需引用一次即可重复使用。
- **信任状态按计算独立**：`verified`、`stale_after`、`attester`这些信任相关的元数据，描述的是**某一个计算**的状态，而不是**一份文档**的状态。`verified`（谁确认过、何时确认）、`stale_after`（何时变陈旧）、单个`attester`（用什么确定性代码核对）这三者共同描述同一个东西：某个具体计算的可信状态。它们是一个整体，绑在一个计算上。

最后一点很重要。以收入、利润、利润率三个指标的计算为例。假设你偷懒，把三个计算都写进一个Metric概念的Frontmatter里：

```yaml
type: Metric
verified: { by: human:ahormati, at: ... }   
stale_after: 2026-09-23T00:00:00Z 
attester:
  resource: references/attesters/xxx.py
```

问题在于：

-`verified`指代不清：一个`verified`无法表达*收入已人工审阅、利润还没*。
-`stale_after`无法分级：收入计算的定义可能半年不变，利润计算的定义可能每月更新，不该共用一个过期时间。
-`attester`无法一一对应：BigQuery SQL用SQL相等`attester`，`dbt`模型用绑定相等`attester`，一个字段装不下三种核对逻辑。

拆成三个Attested Computation概念后，每个概念各自带自己的`verified`、`stale_after`和`attester`，状态互不干扰。而那份讨论三个数字的"利润表概览"文档，只负责叙述并链接到这三个计算概念。信任状态的最小粒度是**一个计算**，不是一个文档。**三个数字 = 三套独立的信任状态 = 三个概念**。硬塞进一份Frontmatter会让 三个字段都失去明确指代，所以规范要求拆开。

### 6.2 相关字段

如下这个是OKF规范提供的表示一个"财年收入"的计算概念。它不只声明"收入是什么"，还携带被批准的计算方式（一段BigQuery SQL），让消费者能确认数字是按这个批准方式算出来的，而不是Agent临时编的。

```yaml
---
type: Attested Computation
title: Revenue for fiscal year
description: Recognized revenue for a fiscal year, per Finance's definition.
status: stable
runtime: bigquery
parameters:
  - { name: year, type: integer, required: true }
executor:
  resource: references/skills/run-on-bq.md
  receipt: [job_id, executed_sql, result]
attester:
  resource: references/attesters/revenue.py
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
stale_after: 2026-09-23T00:00:00Z
sources:
  - id: rev-policy
    resource: https://wiki.acme/finance/revenue-recognition
    title: Revenue recognition policy
---

# Computation

    SELECT SUM(amount) AS revenue
    FROM finance.recognized_revenue
    WHERE fiscal_year = @year

The computation binds only the declared `parameters`, per the recognition
policy.[^rev-policy]

[^rev-policy]: Revenue recognition policy
```

这个计算概念涉及到Attested Computation相关的字段：

- **runtime**：说明如何运行计算的字段，从而决定`executor`和`attester`如何解释它、以及参数是什么含义。采用的值包括`bigquery`、`postgres`、`dbt`、`python`和`Looker`等。
- **parameters**：参数列表。每项采用`{ name, type, required }`格式定义。绑定语义随`runtime`而定。
- **computation**：指向保存计算的文件路径，如果缺省，意味着正文章节`# Computation`定义的代码块就是计算。
- **executor**：计算如何运行。`resource`指向运行说明或代码；运行者（agent或确定性消费者代码）照此执行。`receipt`声明一次运行必须返回的字段，即`attester` 要检查的证据（例如BigQuery的`job_id`和实际执行的SQL）。
- **attester**：确定性检查。`resource`指向接收`receipt`并返回裁决的代码。它意在消费者侧运行。

### 6.2 如何在其他概念文档中使用

一个需要某个计算值的概念（例如一份讨论收入、利润、利润率的利润表概览），只需要为每个数字链接一个 Attested Computation：

```yaml
type: Metric
title: Revenue
description: Recognized revenue for a fiscal year.
tags: [finance, revenue]
status: stable
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }

# Definition

Recognized revenue sums `amount` over rows booked to the fiscal year,
computed by [the revenue computation](../computations/revenue.md).
```
